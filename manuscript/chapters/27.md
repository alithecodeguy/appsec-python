## 1. Randomness for identifiers and tokens with secrets

An **identifier** names a record. A **bearer token** grants a defined capability to whoever presents it. An identifier may be public. A bearer token must remain secret and needs a lifetime, scope, secure transport and a revocation or single-use rule where appropriate.

An **unpredictable** value cannot feasibly be guessed from previous values or easily known state. Python's `random` module is intended for simulations and similar work. Use `secrets`, backed by the operating system's secure random source, for security-sensitive tokens. Do not use the current time, a username, an incrementing integer or a seeded simulation generator as a password-reset secret.

`secrets.token_bytes(32)` returns 32 random bytes. A byte has eight bits, so this requests 256 random bits. `secrets.token_urlsafe(32)` encodes that amount of randomness into URL-friendly text; its argument is a byte count, not a promised text length. Encoding represents bytes. It does not encrypt them.

## 2. Digests, keyed message authentication codes (HMACs) and digital signatures

A **cryptographic digest** is a fixed-size value computed from bytes by a hash function such as SHA-256. It is useful for comparing content against a trusted expected value. It has no secret input. An attacker who can replace both a file and its accompanying unprotected digest can calculate a new matching digest.

A **message authentication code**, or **MAC**, depends on a secret key as well as the message. **HMAC** is a standard MAC construction built from a cryptographic hash function. A valid HMAC tag authenticates the message under that shared key. It does not conceal the message.

A **digital signature** uses a private signing key and a corresponding public verification key. It supports verification without distributing signing capability to every verifier. Use a maintained library or provider verifier for the actual signature protocol. Do not build one from low-level arithmetic or treat a JWT's declared algorithm/key URL as trusted configuration.

**Table T05. Hashing, message authentication, signatures and encryption**

| Tool | Key arrangement | What a successful check establishes | What it does not establish | Casebook decision |
| --- | --- | --- | --- | --- |
| SHA-256 digest | No secret | Bytes match a trusted expected digest, subject to the hash's security assumptions | Sender identity if an attacker can replace the expected digest; confidentiality | Content comparison and the stored webhook receipt digest after authentication |
| HMAC-SHA-256 | Sender and verifier share a secret | Exact message is authenticated under that secret | Confidentiality, freshness by itself, or which secret holder created the tag | Synthetic partner webhook |
| Digital signature, for example Ed25519 in a suitable protocol | Private signing key; trusted public verification key | Signature verifies under the configured public key | Confidentiality, current authorization or automatic proof of a person's/legal actor's intent | Choose when verifiers should not hold signing authority; no signature implementation needed for these two jobs |
| AES-256-GCM authenticated encryption | Authorized encryptor/decryptor holds a secret AES key | Plaintext is released only if ciphertext and associated data verify | Application membership, protection after decryption, or detection of every replay of an old valid record | Small private stored export |

A signature's identity claim depends on how the public key was bound to an identity and how the private key was protected. HMAC deliberately does not distinguish its holders: the receiving application also has enough key material to create a tag. Neither tool alone creates non-repudiation or a legal proof.

Passwords are a separate job. Use chapter 21's maintained password-hashing framework with a suitable slow password hash and salts. Fast SHA-256 is not a password storage scheme. Encrypting passwords so the application can recover them is not the login design.

The demo imports this existing function from `examples/ch26/integrations.py`. This is the complete primitive wrapper, shown here to make the signed bytes explicit; keep the established source unchanged.

```python
import hashlib
import hmac


def signature(secret, partner_id, timestamp, raw):
    message = b"casebook-webhook-v1\n" + partner_id.encode("ascii") + b"\n" + timestamp.encode("ascii") + b"." + raw
    return hmac.new(secret, message, hashlib.sha256).hexdigest()
```

The prefix identifies the protocol purpose. The trusted route selects partner `reports`. The canonical timestamp text and exact raw body are authenticated together. This is an explicitly synthetic envelope, not a general recipe for an unknown provider. For a real partner, follow its exact protocol and maintained SDK/verifier, including its prescribed canonicalization and signed fields.

Do not parse and reserialize the incoming body before verification. Do not calculate the expected tag with a key sent in the request. Chapter 26 looks up the untrusted key ID in a trusted, per-partner keyring and compares fixed-format tags using `hmac.compare_digest`. It never tries a request-supplied key location.

## 3. Authenticated encryption, associated data and nonce requirements

**Encryption** transforms plaintext into ciphertext under a key. **Authenticated encryption** also detects unauthenticated changes before releasing plaintext. **AEAD** means authenticated encryption with associated data: some context is authenticated along with the ciphertext but is not itself encrypted.

The local export uses `AESGCM` from `cryptography`. AES is the underlying cipher; GCM is the authenticated mode. A 256-bit key is 32 bytes. The high-level `encrypt` operation returns ciphertext with a 16-byte authentication tag appended. Use the library's `decrypt` operation to verify and open that output. Do not write a separate custom tag construction around it or implement AES yourself.

The library module path includes `hazmat`. Here we select its documented high-level AEAD class, not low-level cipher/mode composition. This still requires a correct protocol for keys, nonces, context and failures.

A **nonce** is a per-encryption value. For this AES-GCM protocol it is 12 bytes and must never repeat with the same actual key. A nonce need not be secret. Reusing a key/nonce pair can break confidentiality and authentication. Reusing the plaintext with a fresh nonce is a different situation and is allowed within the algorithm's usage limits.

### Concrete job B: protect a stored export

We want a copy of Mina's Alpha export to remain confidential and tamper-evident if someone reads or modifies its stored ciphertext without the key. An application attacker who can invoke authorized decryption or steal the key is outside that protection. The user-facing release path must still enforce current permission.

**Table T27-03. Small encrypted-record contract**

| Property | Local choice |
| --- | --- |
| Primitive | AES-256-GCM using `cryptography`'s `AESGCM` |
| Plaintext | Chapter 23's JSON export payload, capped at 4,096 bytes before encryption |
| Export authority | Stored requester, workspace and selected note IDs; active membership and note visibility rechecked before creation and each read |
| Metadata | Export ID, workspace, requester, selected note IDs, format version, generation and key ID |
| Associated data | Deterministic JSON of that metadata, fixed purpose and algorithm label |
| Nonce | 12 random bytes per encryption; local committed-pair ledger refuses a repeated `(key_id, nonce)` before calling AES |
| Stored object | Metadata, nonce, ciphertext and tag; no plaintext column and no key material |
| Read | Authorize first, select a configured key, authenticate/decrypt, then return plaintext |
| Failure | Generic `CannotOpen("export_unavailable")`; no plaintext returned and no repair/write attempted |
| Migration | Verify old record, increment generation, encrypt with active key and fresh nonce, replace atomically |

**Associated data** binds ciphertext to its intended context. Moving Beta's nonce/ciphertext to Alpha's row while leaving Alpha's metadata causes verification failure. Changing an authenticated workspace or requester also fails, even if the encrypted bytes are untouched.

This binding is not authorization. AAD is public metadata, not a secret or a permission grant. The service constructs it from stored records. A client does not send replacement workspace, requester or generation values for decryption. The selected-note representation is stored JSON text and becomes part of the exact AAD: changing its whitespace also changes the authenticated context.

AEAD also does not prevent restoration of an entire old, valid record together with its original metadata. The generation field binds a particular version, but detecting rollback requires a trusted record of which version is current outside the attacker's rollback scope. Do not describe an authenticated generation number alone as anti-replay storage.

### The nonce ledger's precise limit

The local table records committed nonce use per key ID. `encrypt` attempts its unique insert before invoking AES. A test forces a repeat of a committed nonce and verifies refusal with no new committed export.

Key IDs must be immutable names for particular key material. Giving one AES key two IDs would split its nonce history; the local keyring rejects duplicate material within a configuration. It cannot discover a key reused under another name in another service or a previously discarded configuration. All users of that key need one coherent nonce and usage policy.

This is a bounded learning model, not a production nonce allocator. Random 96-bit values have a collision probability that grows with use. Set per-key data/invocation limits and rotate before the selected construction's security bounds are exceeded. The ledger retains history for committed records even when an export is migrated; do not delete old reservations merely because the active row changed.

If a transaction fails after encryption, the demo discards its ciphertext and rolls back its reservation. The ledger therefore does not preserve every failed encryption attempt or ciphertext that an instrumented process might expose. Do not reuse this transactional table as proof of lifetime nonce uniqueness across crashes, external publication, multiple stores or backup restoration. A deployed nonce strategy must cover all those cases. Restoring a ledger that has lost history while continuing the same key is unsafe; select a reviewed recovery strategy, such as activating fresh key material before new writes. Never reset a nonce counter under an existing key.

**Listing L27-02. Bounded encrypted storage and atomic key migration**

Filename: `examples/ch27/export_crypto.py`.

```python
"""Local encrypted-export laboratory. Keyring arguments are trusted service configuration."""
from dataclasses import dataclass, field
import json
import re
import secrets
from types import MappingProxyType

from cryptography.exceptions import InvalidTag
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

from examples.ch23.authorization_service import (
    AccessDenied, build_export, require_member, seed, unit, visible_rows,
)

MAX_PLAINTEXT = 4096


class CannotOpen(ValueError):
    pass


@dataclass(frozen=True)
class Keyring:
    keys: dict = field(repr=False)
    active: str

    def __post_init__(self):
        copied = dict(self.keys)
        if (self.active not in copied or any(not isinstance(k,str) or re.fullmatch(r"[a-z0-9-]{1,32}",k) is None
                or not isinstance(v,bytes) or len(v) != 32 for k,v in copied.items())
                or len(set(copied.values())) != len(copied)):
            raise ValueError("Use distinct 256-bit keys with immutable key identifiers")
        object.__setattr__(self,"keys",MappingProxyType(copied))


def initialize(database):
    seed(database)
    with unit(database,write=True) as db:
        db.execute("""CREATE TABLE encrypted_exports (
            id INTEGER PRIMARY KEY, workspace_id INTEGER NOT NULL REFERENCES workspaces(id),
            requested_by INTEGER NOT NULL REFERENCES users(id), note_ids TEXT NOT NULL,
            format_version INTEGER NOT NULL, generation INTEGER NOT NULL,
            key_id TEXT NOT NULL, nonce BLOB NOT NULL, ciphertext BLOB NOT NULL)""")
        db.execute("""CREATE TABLE used_nonces (
            key_id TEXT NOT NULL, nonce BLOB NOT NULL, PRIMARY KEY(key_id,nonce))""")


def associated_data(record):
    if record["format_version"] != 1:
        raise CannotOpen("export_unavailable")
    context={"purpose":"casebook-private-export", "algorithm":"AES-256-GCM",
             **{field:record[field] for field in ("id","workspace_id","requested_by","note_ids",
                                                "format_version","generation","key_id")}}
    return json.dumps(context,sort_keys=True,separators=(",",":"),ensure_ascii=True).encode("ascii")


def encrypt(db,record,plaintext,keyring):
    if len(plaintext) > MAX_PLAINTEXT:
        raise ValueError("export_too_large")
    record={**record,"key_id":keyring.active}
    nonce=secrets.token_bytes(12)
    # Reserve before encrypting: a repeated key-ID/nonce pair refuses this operation.
    # All uses of this key must share this ledger/policy; it is not a global KMS allocator.
    db.execute("INSERT INTO used_nonces VALUES (?,?)",(keyring.active,nonce))
    ciphertext=AESGCM(keyring.keys[keyring.active]).encrypt(nonce,plaintext,associated_data(record))
    return keyring.active,nonce,ciphertext


def decrypt(record,keyring):
    if (record["key_id"] not in keyring.keys
            or not isinstance(record["nonce"],bytes) or len(record["nonce"]) != 12
            or not isinstance(record["ciphertext"],bytes)
            or not 16 <= len(record["ciphertext"]) <= MAX_PLAINTEXT+16):
        raise CannotOpen("export_unavailable")
    try:
        return AESGCM(keyring.keys[record["key_id"]]).decrypt(
            record["nonce"],record["ciphertext"],associated_data(record))
    except InvalidTag as exc:
        raise CannotOpen("export_unavailable") from exc


def authorize_record(db,record,user_id):
    require_member(db,user_id,record["workspace_id"])
    if user_id != record["requested_by"]:
        raise AccessDenied()
    ids=json.loads(record["note_ids"])  # Trusted stored intent, not a browser claim.
    if len(visible_rows(db,user_id=user_id,workspace_id=record["workspace_id"],note_ids=ids,limit=10)) != len(ids):
        raise AccessDenied()


def create_export(database,*,user_id,workspace_id,note_ids,keyring):
    artifact=build_export(database,user_id=user_id,workspace_id=workspace_id,note_ids=note_ids)
    with unit(database,write=True) as db:
        intent={"workspace_id":workspace_id,"requested_by":user_id,"note_ids":json.dumps(artifact.note_ids)}
        authorize_record(db,intent,user_id)  # Current permission again before storing a copy.
        cursor=db.execute("""INSERT INTO encrypted_exports
            (workspace_id,requested_by,note_ids,format_version,generation,key_id,nonce,ciphertext)
            VALUES (?,?,?,1,1,? ,X'',X'')""",
            (workspace_id,user_id,intent["note_ids"],keyring.active))
        record=dict(db.execute("SELECT * FROM encrypted_exports WHERE id=?",(cursor.lastrowid,)).fetchone())
        kid,nonce,ciphertext=encrypt(db,record,artifact.payload,keyring)
        db.execute("UPDATE encrypted_exports SET key_id=?,nonce=?,ciphertext=? WHERE id=?",
                   (kid,nonce,ciphertext,record["id"]))
    return record["id"]


def read_export(database,*,user_id,export_id,keyring):
    if user_id is None:
        raise AccessDenied(403,"access_denied")
    with unit(database) as db:
        row=db.execute("SELECT * FROM encrypted_exports WHERE id=?",(export_id,)).fetchone()
        if row is None:
            raise AccessDenied()
        record=dict(row)
        authorize_record(db,record,user_id)
        return decrypt(record,keyring)


def rotate_export(database,*,export_id,keyring):
    # Privileged internal maintenance, not a user-callable operation or a read grant.
    with unit(database,write=True) as db:
        row=db.execute("SELECT * FROM encrypted_exports WHERE id=?",(export_id,)).fetchone()
        if row is None:
            raise CannotOpen("export_unavailable")
        previous=dict(row)
        plaintext=decrypt(previous,keyring)  # Verify old record BEFORE any replacement.
        current={**previous,"generation":previous["generation"]+1}
        kid,nonce,ciphertext=encrypt(db,current,plaintext,keyring)
        changed=db.execute("""UPDATE encrypted_exports SET key_id=?,nonce=?,ciphertext=?,generation=?
            WHERE id=? AND generation=?""",
            (kid,nonce,ciphertext,current["generation"],export_id,previous["generation"])).rowcount
        if changed != 1:
            raise RuntimeError("export_generation_changed")


def inventory(database):
    # Privileged verifier/nonce inspection, never an HTTP response or log payload.
    with unit(database) as db:
        return {name:[dict(row) for row in db.execute(f"SELECT * FROM {name} ORDER BY 1,2")]
                for name in ("encrypted_exports","used_nonces")}
```

`Keyring` is trusted service configuration, never request data. `MappingProxyType` prevents ordinary mutation of its copied mapping; it is not protected key custody or memory isolation. `inventory` and `decrypt` are privileged laboratory helpers. Do not expose them as HTTP endpoints or log their returned rows.

The first insert in `create_export` establishes the database ID needed by AAD. Its empty nonce/ciphertext exist only inside the same uncommitted write transaction; an exception rolls back the whole creation. There is no committed placeholder or plaintext file. The 4,096-byte cap constrains encryption input, but `build_export` has already materialized the authorized payload. It is not a general streaming or whole-request memory bound.

`read_export` reuses chapter 23's current active-member and note-visibility checks. Its decision is made within the read transaction. A later request observes a committed revocation; this synchronous helper does not recall plaintext already returned or implement an interruptible download. A future queued/delayed release must check current authority at its own release boundary.

`rotate_export` is privileged internal maintenance. It is not an ordinary user's access grant and must not be routed directly from a browser request. It opens and verifies the old ciphertext before creating a replacement. A database error during replacement rolls back the new row values and nonce reservation. The old row remains readable with its old key. Chapter 28 will examine concurrency; this test does not establish distributed migration safety.

## 4. Key custody, separation, rotation, backup and algorithm migration

A good algorithm does not decide who can use its key. **Key custody** covers generation, storage, access, distribution, backup, audit and destruction. A **key ID** is a non-secret selector. It is not the key, proof of trust or an authority to load secrets from an arbitrary address.

**Table T27-04. Ownership and custody decisions for the two jobs**

| Item | Responsible owner | Allowed use and separation | Recovery/retirement requirement |
| --- | --- | --- | --- |
| Webhook verification secret | Integration service owner, coordinated with partner | Verify this partner's protocol in one environment; holder can also forge tags, so restrict access | Approved overlap/retry policy; immediate revocation procedure for compromise; audit configured versions without logging secrets |
| Export data key | Storage service under platform/security key policy | Encrypt/decrypt the defined export format; separate from webhook, session and recovery keys | Keep needed decrypt versions until records and retained backups are migrated, expired or deliberately made unrecoverable |
| Export migration job | Authorized storage maintenance identity | Read old plaintext in process and write authenticated replacement; no user download grant | Resume/reconcile by record version; stop on verification failure; retain counts and failures without plaintext |
| Key-encryption key in a deployed envelope scheme | Platform/KMS owner with restricted service grants | Wrap/unwrap data keys under access controls; separate management and use privileges where supported | Protected backup/recovery, key-version availability and tested restore; not implemented in this lab |
| Encrypted export and nonce history | Storage/backup owner | Retain record metadata, authenticated bytes and required nonce history under data-retention policy | Restore must preserve a safe key/nonce/version strategy, not merely produce a readable database |

A **key management service** (KMS) provides controlled key operations and lifecycle management. A **hardware security module** (HSM) can protect key operations within hardware. Neither name alone proves a correct permission policy or an accessible recovery path.

In **envelope encryption**, a data encryption key (DEK) encrypts data and a key-encryption key (KEK) protects that DEK. Store the wrapped DEK and relevant versions with the protected object; restrict unwrap authority through the selected KMS. Rotating a KEK may allow rewrapping data keys without re-encrypting every export, depending on that system's protocol. Rotating a DEK requires the corresponding data migration. Our code uses in-memory AES keys directly and implements neither KMS integration nor envelope encryption.

Keep real keys out of source control, fixtures, database rows, command-line arguments, error reports and ordinary logs. Use a secret manager or reviewed KMS integration with narrowly scoped service identity. Environment injection may be a delivery mechanism, but it does not by itself solve process exposure, logging or key lifecycle. Python byte objects do not provide a reliable application-level zeroization guarantee; this lab makes no such claim.

### Two distinct rotation procedures

For webhook authentication:

1. Generate and provision a new independent shared secret over the approved channel.
2. Configure receiver acceptance for the old and new versions during an approved overlap.
3. Have the partner switch signing to the new version. Monitor version-level verification outcomes without recording secret values.
4. Retire old verification according to the protocol's delivery/retry horizon and compromise policy.
5. Verify that old signatures fail and new signatures succeed, while duplicate-event effects remain unchanged.

For stored export encryption:

1. Add a new independent AES key; make it active for new writes. Keep old keys available for existing reads.
2. Verify and decrypt each old record in the trusted migration process.
3. Re-encrypt with the new active key, fresh nonce and updated authenticated generation.
4. Replace atomically. Read the result with the intended remaining key set and reconcile every record, including failed migrations.
5. Retire old decrypt capability only after the retained-data and backup policy is resolved and tested.

Changing a key ID in a row without re-encryption does not rotate the record. Removing the old key first makes old records unreadable. For a compromised key, a normal gradual rotation may be too slow; the incident decision must account for forgery/decryption exposure, recovery and required revocation. New encryption cannot make an already disclosed plaintext secret again.

The demo's old/new AES keys are fresh disposable values from `AESGCM.generate_key(bit_length=256)`. They are not printed or saved. Temporary databases disappear at exit. These are dummy exercise keys, even though they have the correct cryptographic length. Losing them is intentional here and would be data loss for real exports.

### Backup and algorithm migration

An encrypted backup needs its usable key versions, authenticated metadata and recovery permissions. Storing ciphertext and its keys under the same broad access grant weakens the intended separation. Losing every recoverable key can permanently lose the data. Keeping keys forever can also defeat a stated retirement or deletion goal.

Test a restore with approved recovery identities and verify both data access and nonce safety for subsequent writes. Include backup copies, replicas, pending migrations and retained old formats in the inventory. Removing a key from one process does not erase copies, plaintext downloads or backup keys and is not proof of cryptographic erasure.

**Algorithm migration** changes the supported construction or record protocol. Use an explicit format version, trusted version-to-implementation mapping and a reviewed migration. This version-1 code accepts only AES-256-GCM with its fixed AAD rules. Unknown format versions fail. It never catches authentication failure and tries unauthenticated decryption or a caller-selected algorithm. A future migration needs tests for reading approved old versions, writing only the new version, rejecting unknown versions and preserving old state after a failed replacement.

## Worked answers

### Exercise 1

The receiver lacks an authenticated expected digest. The attacker can calculate SHA-256 of a replacement and provide both. A digest obtained through a separately authenticated trusted manifest can establish content equality against that manifest. An HMAC with a protected shared key can authenticate the specified bytes, but freshness, replay and business authority still need their own protocol rules. Neither hides the report.

### Exercise 2

Every holder of the HMAC key can produce tags. Public-key signature verification allows services to verify without receiving the publisher's private signing key. The public key must still be bound to the correct publisher through trusted configuration or a validated identity/certificate protocol. Accepting a key supplied beside the message would not establish that binding. Use the publisher's actual maintained verification protocol and constrain algorithms and key selection.

### Exercise 3

Ravi's Alpha request is refused by current workspace permission before decryption. Mina's request passes Alpha/requester checks, but Beta's bytes do not verify under Alpha's associated data, so no plaintext is returned. Replacing an entire row with a valid old Alpha copy can still authenticate if the old key is accepted. Preventing that rollback needs a trusted current-version reference or equivalent storage protocol outside the replaced state. The AAD generation field by itself is insufficient.

### Exercise 4

Removing the old key makes its ciphertext unreadable, so migration cannot verify/decrypt it. Keep old and new keys during migration and use the new key for new encryption. Verify, re-encrypt with new context/nonce, replace atomically and confirm all retained data/backups before retirement. If replacement fails, the export's old key ID, generation, nonce and ciphertext must remain unchanged, and the attempted new reservation must not become committed in this local transaction. The test reopens the database and compares the complete export/nonce snapshot, then reads using the old key.

### Exercise 5

Successful decryption says nothing about whether a restored writer might repeat a previously used key/nonce pair or obey lifetime usage limits. The storage owner must reconcile nonce history and key versions with the platform/key owner. One recovery design activates fresh independent key material before resumed writes while preserving approved old decrypt capability. Its access, restore and retention implications must be tested; this chapter does not implement that recovery system. A reset timestamp/counter or a new key ID pointing to the same old key does not solve lost nonce history.
