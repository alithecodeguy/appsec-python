This chapter follows one package through declared intent, dependency metadata, a hashed lock, a wheel and installed Python code. We will then compare the installed version with an advisory and record an update decision with a compatibility check and an owner.

- Read pins, constraints, hashes and package-source selection as different controls.
- Produce an inventory from an installed sample build and trace an indirect component into it.
- Compare an advisory's package identity and affected range with the installed version.
- Plan an update using maintainer trust, provenance, reachability, tests and a bounded rollback decision.

## 1. Direct and transitive dependencies, build backends, wheels and source distributions

A **direct dependency** is one the application declares itself. A **transitive dependency**, also called an **indirect dependency**, is needed through another dependency. The distinction is relative to the root project: the codec is direct for the client, but transitive for this sample application.

**Table T31-02. Read the sample dependency tree as relationships**

| Requiring component | Declared requirement | Meaning |
| --- | --- | --- |
| Sample `requirements.in` | `casebook-ch31-client==1.0.0` | The client is the application's declared direct dependency. |
| Client distribution metadata | `casebook-ch31-codec>=1.0.0,<2` | Installing the client requires a compatible codec even though the root input omits its name. |
| Codec distribution metadata | No further runtime dependencies | This fictional runtime branch ends here. |
| Source projects' build configuration | `setuptools==84.2.1`, `wheel==0.48.0` | These are builder requirements, separate from the two-package application graph. |

The package metadata may reorder a specifier to `<2,>=1.0.0`; that is the same requirement. Real trees can have shared dependencies, optional extras, platform markers and multiple constraints on one package. This exercise deliberately uses one simple branch and no conditional requirements.

### Know which artifact you are reading

A **distribution package** is an installable release identified by a distribution name and version. An **import package** is the Python name used in code. Here `casebook-ch31-codec` installs `ch31_codec`. Searching application imports for the distribution's full hyphenated name would miss it.

A **wheel** is a built distribution in a `.whl` archive. It contains installable files and metadata, including `METADATA`, `WHEEL` and `RECORD` under a `.dist-info` directory. A **source distribution**, or **sdist**, is a source release archive from which a frontend may build a wheel. PyPA specifies the [wheel format](https://packaging.python.org/en/latest/specifications/binary-distribution-format/) and [source distribution format](https://packaging.python.org/en/latest/specifications/source-distribution-format/).

Our filenames end in `py3-none-any.whl` because the examples are pure Python and declare those compatibility tags. Other wheels can be tied to a Python implementation, ABI or platform. A wheel is not automatically compatible with every runtime, nor trustworthy merely because it is already built.

A **build frontend**, such as the pip command used here, coordinates a build. A **build backend**, here `setuptools.build_meta`, produces metadata and the wheel. The source project's `[build-system]` table names that backend and its required tools; `[project].dependencies` names runtime requirements. These are separate parts of the [pyproject specification](https://packaging.python.org/en/latest/specifications/pyproject-toml/).

**Listing L31-01. Authored source fixtures for three local wheels**

Filename: `examples/ch31/make_sources.py`.

```python
from pathlib import Path


CLIENT = "casebook-ch31-client"
CODEC = "casebook-ch31-codec"


def project(folder, name, version, module, source, dependencies=()):
    folder.mkdir(parents=True)
    (folder / "pyproject.toml").write_text(
        '[build-system]\n'
        'requires = ["setuptools==84.2.1", "wheel==0.48.0"]\n'
        'build-backend = "setuptools.build_meta"\n\n'
        '[project]\n'
        f'name = "{name}"\nversion = "{version}"\n'
        'requires-python = ">=3.12"\n'
        f'dependencies = {list(dependencies)!r}\n\n'
        '[tool.setuptools]\n'
        f'packages = ["{module}"]\n', encoding="utf-8")
    package = folder / module
    package.mkdir()
    (package / "__init__.py").write_text(source, encoding="utf-8")


def make_sources(root):
    root = Path(root)
    common = '''import json


def read_title(raw):
    if not isinstance(raw, bytes):
        raise TypeError("record must be bytes")
{bound}    document = json.loads(raw)
    if not isinstance(document, dict) or set(document) != {{"title"}}:
        raise ValueError("invalid_record")
    if not isinstance(document["title"], str) or not document["title"].strip():
        raise ValueError("invalid_title")
    return document["title"]
'''
    for version, bound in (("1.0.0", ""),
                            ("1.0.1", '    if len(raw) > 256:\n        raise ValueError("record_too_large")\n')):
        project(root / f"codec-{version}", CODEC, version, "ch31_codec",
                common.format(bound=bound))
    client = '''from ch31_codec import read_title


def preview_title(raw):
    return read_title(raw)
'''
    project(root / "client-1.0.0", CLIENT, "1.0.0", "ch31_client", client,
            (f"{CODEC}>=1.0.0,<2",))
```

The helper writes two codec source trees and one client tree, each with `pyproject.toml` and its import package. `common.format(bound=...)` inserts the size check into only `1.0.1`. Doubled braces in that template preserve the literal `{"title"}` set in the generated Python source.

Both versions reject invalid schema and blank titles. Only the newer version rejects an oversized byte record before `json.loads`. The client does not know which codec version the environment selected; it calls the installed `read_title` implementation. That call establishes a concrete reachability path in this sample.

The driver builds from these reviewed local directories. It does not create or consume an sdist archive. Source-archive extraction, native compilation and their toolchains remain outside the executed exercise.

### Retain a useful application contract

The compatibility checks call the public client function. They do not call the codec directly, so an import or interface change in the client/codec relationship can affect the result.

**Listing L31-02. Compatibility and regression checks through the client**

Filename: `examples/ch31/test_contract.py`.

```python
import json
import unittest

from ch31_client import preview_title


def record_of_size(size):
    overhead = len(b'{"title":""}')
    raw = json.dumps({"title": "x" * (size - overhead)}, separators=(",", ":")).encode()
    assert len(raw) == size
    return raw


class CompatibilityTests(unittest.TestCase):
    def test_unicode_title_round_trip(self):
        title = "برنامه انتشار"
        raw = json.dumps({"title": title}, ensure_ascii=False).encode("utf-8")
        self.assertEqual(preview_title(raw), title)

    def test_exact_byte_boundary_remains_accepted(self):
        raw = record_of_size(256)
        self.assertEqual(preview_title(raw), json.loads(raw)["title"])

    def test_invalid_schema_remains_refused(self):
        for raw in (b'[]', b'{"title":4}', b'{"title":""}', b'{"title":"a","extra":1}'):
            with self.subTest(raw=raw), self.assertRaises(ValueError):
                preview_title(raw)


class SizeRegressionTests(unittest.TestCase):
    def test_one_byte_over_is_refused(self):
        with self.assertRaisesRegex(ValueError, "record_too_large"):
            preview_title(record_of_size(257))


if __name__ == "__main__":
    unittest.main()
```

There are four test methods: three compatibility checks and one new regression. The exact 256-byte record remains permitted; 257 bytes must be refused under the fictional update contract. The Persian title checks a real UTF-8 round trip. The byte limit applies to the encoded record, not the number of characters in its title.

The driver runs these tests under each installed sample environment. Expected and observed: the before environment passes the three compatibility methods but fails the new regression with `ValueError not raised`. The after environment passes all four methods. We do not send a huge payload or measure an actual denial of service. The observed regression is the missing byte-bound behavior described by the fictional advisory.

## 2. Pins, constraints, hashes, index selection and isolated builds

A package name is only the beginning of an installation decision. Which version, which file, which source and which build environment produced it are separate questions.

**Table T31-03. Controls with different jobs**

| Control | What it does | What it does not establish |
| --- | --- | --- |
| Pin, such as `codec==1.0.0` | Select an exact version for that requirement. | Which release file was used, whether its code is safe, or who authorized it. |
| Constraint, such as a codec pin in a constraints file | Restrict versions when that package is otherwise required. | Cause the package to be installed by itself. |
| Artifact hash | Compare the selected file with the expected digest. | Whether the expected file itself is malicious or vulnerable. |
| Approved index or local wheel source | Constrain where candidates are obtained. | Establish package ownership or safe behavior without further evidence. |
| Build isolation | Separate build requirements from the caller's ordinary environment. | Sandbox arbitrary build code or automatically lock all build inputs. |
| Installed inventory | Record components found in a particular inspected environment. | Prove that every code copy, native library or other deployed environment was covered. |

A **constraint** changes selection without acting as an installation request. For example, a root client requirement plus `-c constraints.txt`, where that file contains `casebook-ch31-codec==1.0.1`, can narrow the client's allowed codec range. Installing an otherwise empty requirement set with that constraint does not mean the codec must ship. pip's [constraints documentation](https://pip.pypa.io/en/stable/user_guide/#constraints-files) explains this distinction.

### Read a hashed lock as a reviewed selection

The driver creates `before.lock` and `after.lock` as **pip requirements-format files with complete pinned application dependency selections and hashes**. The `.lock` suffix is an exercise convention. These files are not `pylock.toml`, and they are not output from a general resolver or a multi-platform lock generator.

The sample chooses known local releases deliberately. A maintained application normally resolves its actual dependency graph for each supported target and reviews changes to versions, sources and artifacts. A new OS, Python version, extra or platform marker may select different dependencies or wheels.

The client version and hash stay the same. Only the codec selection changes. The later version is still inside the client's declared range. Copying a digest from the book is not the workflow: the driver calculates hashes from the wheels produced in the reader's run. The values above identify this recorded run, not every possible rebuild with other toolchains.

pip's [secure installation guidance](https://pip.pypa.io/en/stable/topics/secure-installs/) describes hash-checking mode and its requirement for fully specified dependencies. The installation command uses `--require-hashes`, so the indirect codec must also have a pinned version and allowed artifact hash. A pin only for the root client is insufficient.

The SHA-256 values authenticate equality with the expected files only to the extent that the expected hashes are trusted. If an attacker can alter both a package and its reviewed lock record, the comparison no longer protects that choice. Review and protect the selection input as well as retaining the file.

`pip freeze` can help record versions in an environment. It is not, by itself, the original root declaration, an artifact-hash policy, a dependency explanation or a complete deployment inventory. An installed state and an intended state answer different questions.

### Make source selection explicit

`--no-index` prevents package-index lookup. `--find-links ./wheelhouse` supplies the local candidates. `--only-binary :all:` requires wheels for the sample installation. The driver runs with a known working directory, so these relative paths have a defined meaning.

Do not treat a private index plus `--extra-index-url` as a guaranteed private-first fallback. pip's [installation reference](https://pip.pypa.io/en/stable/cli/pip_install/) describes the dependency-confusion concern when a public index can supply the same package name. A production policy needs intentional namespace, source and artifact controls. The offline exercise avoids that selection ambiguity rather than demonstrating a registry attack.

### Distinguish three kinds of isolation

The command's `--isolated` option ignores environment variables and user configuration for pip. A pip **isolated build environment** is a different feature that prepares build requirements. An operating-system sandbox is different again. Neither pip option alone establishes one.

The sample uses `--no-build-isolation` because the exact backend tools are already present in a controlled builder and no download is needed. The runner verifies the setuptools/wheel versions and records the builder's other tool versions. pip's [build-system documentation](https://pip.pypa.io/en/stable/reference/build-system/#disabling-build-isolation) states that callers disabling build isolation own those build dependencies.

This is a bounded offline teaching choice, not an instruction to run unknown source projects in a developer's general environment. Build hooks execute code. A production isolated build must also control its backend requirements, toolchain, permissions and network access. A runtime lock does not automatically lock dynamic build requirements or the underlying OS/compiler inputs.

The driver sets `SOURCE_DATE_EPOCH` to a fixed timestamp to reduce timestamp variation in the fixture wheels. That alone is not a claim of reproducible builds. We record the actual files and their hashes; we do not prove that arbitrary builders will produce byte-identical artifacts.

**Listing L31-03. Offline sample build and evidence driver**

Filename: `examples/ch31/build_lab.py`.

```python
import hashlib
from importlib import metadata
import json
import os
from pathlib import Path
import shutil
import subprocess
import sys
import venv
from zipfile import ZipFile

from make_sources import CLIENT, CODEC, make_sources


HERE = Path(__file__).resolve().parent


def sha256(path):
    return hashlib.sha256(path.read_bytes()).hexdigest()


def build(root):
    root = Path(root).resolve()
    root.mkdir(parents=True, exist_ok=False)
    (root / "logs").mkdir()
    wheelhouse = root / "wheelhouse"
    wheelhouse.mkdir()
    tools = {name: metadata.version(name) for name in ("pip", "setuptools", "wheel", "packaging")}
    assert tools["setuptools"] == "84.2.1" and tools["wheel"] == "0.48.0", tools
    (root / "builder.json").write_text(json.dumps({"python": sys.version, "tools": tools}, indent=2))
    environment = os.environ.copy()
    environment.pop("PYTHONPATH", None)
    environment.update(SOURCE_DATE_EPOCH="1700000000", PYTHONNOUSERSITE="1")

    def command(arguments, label, expected=0):
        result = subprocess.run([str(value) for value in arguments], cwd=root, env=environment,
                                text=True, capture_output=True)
        (root / "logs" / f"{label}.log").write_text(result.stdout + result.stderr)
        if expected is not None and result.returncode != expected:
            raise RuntimeError(f"{label}: unexpected exit {result.returncode}; inspect its log")
        return result

    def pip(python, *arguments):
        return [python, "-m", "pip", "--isolated", "--disable-pip-version-check", *arguments]

    def fresh_python(name):
        folder = root / name
        venv.EnvBuilder(with_pip=True).create(folder)
        return folder / "bin" / "python"  # macOS/Linux laboratory.

    make_sources(root / "sources")
    for project in sorted((root / "sources").iterdir()):
        command(pip(sys.executable, "wheel", "--no-index", "--no-deps", "--no-build-isolation",
                    "--no-cache-dir", "--wheel-dir", wheelhouse, project), f"build-{project.name}")

    def wheel(name, version):
        return wheelhouse / f"{name.replace('-', '_')}-{version}-py3-none-any.whl"

    def lock(variant, codec_version, links="./wheelhouse", include_codec=True):
        records = [(CLIENT, "1.0.0")]
        if include_codec:
            records.append((CODEC, codec_version))
        text = "# Fictional local sample; reviewed teaching selection, not resolver output.\n"
        text += f"--no-index\n--only-binary :all:\n--find-links {links}\n"
        for name, version in records:
            text += f"{name}=={version} --hash=sha256:{sha256(wheel(name, version))}\n"
        path = root / f"{variant}.lock"
        path.write_text(text)
        return path

    (root / "requirements.in").write_text(CLIENT + "==1.0.0\n")
    for variant, codec_version in (("before", "1.0.0"), ("after", "1.0.1")):
        selected_lock = lock(variant, codec_version)
        python = fresh_python(f"venv-{variant}")
        command(pip(python, "install", "--no-index", "--require-hashes", "--no-compile",
                    "--no-cache-dir", "--report", root / f"install-{variant}.json",
                    "-r", selected_lock), f"install-{variant}")
        command(pip(python, "check"), f"check-{variant}")
        inspected = command(pip(python, "inspect", "--local"), f"inspect-{variant}")
        (root / f"inspect-{variant}.json").write_text(inspected.stdout)
        captured = command([python, HERE / "capture_inventory.py", root, variant], f"capture-{variant}")
        inventory = root / f"inventory-{variant}.json"
        inventory.write_text(captured.stdout)
        command([python, HERE / "test_contract.py", "-v"], f"tests-{variant}",
                expected=1 if variant == "before" else 0)
        print(f"{variant}: codec {codec_version}; compatibility/regression exit "
              f"{1 if variant == 'before' else 0}; inventory SHA-256 {sha256(inventory)}")

    bad = root / "tampered-wheels"
    bad.mkdir()
    for name in (CLIENT, CODEC):
        shutil.copy2(wheel(name, "1.0.0"), bad)
    with ZipFile(bad / wheel(CODEC, "1.0.0").name, "a") as archive:
        archive.writestr("tampered.txt", "synthetic integrity-test marker")
    tampered_lock = lock("tampered", "1.0.0", links="./tampered-wheels")
    omitted_lock = lock("omitted", "1.0.0", include_codec=False)
    for variant, selected_lock in (("tampered", tampered_lock), ("omitted", omitted_lock)):
        python = fresh_python(f"venv-{variant}")
        result = command(pip(python, "install", "--no-index", "--require-hashes", "--no-cache-dir",
                             "-r", selected_lock), f"install-{variant}", expected=None)
        assert result.returncode != 0
        assert "hash" in (result.stdout + result.stderr).lower()
        probe = command([python, "-c", "import importlib.metadata as m,json; "
                         "print(json.dumps(sorted(d.metadata['Name'] for d in m.distributions())))"],
                        f"remaining-{variant}")
        remaining = json.loads(probe.stdout)
        assert not any(name.startswith("casebook-ch31-") for name in remaining), remaining
        print(f"{variant}: refused; no sample application packages installed")
    # Keep the old environment: no in-place update was used.
    command([root / "venv-before/bin/python", HERE / "test_contract.py", "CompatibilityTests", "-v"],
            "retained-before-compatibility")
    print("Retained before environment: three compatibility checks still pass; security regression remains.")
    print("Local sample complete:", root)


if __name__ == "__main__":
    if len(sys.argv) != 2:
        raise SystemExit("usage: python build_lab.py NEW_OUTPUT_DIRECTORY")
    build(sys.argv[1])
```

## 3. SBOM, advisory matching and software composition analysis

A **software bill of materials**, or **SBOM**, records software components and their relationships for a stated subject and scope. Standard formats such as [CycloneDX](https://cyclonedx.org/specification/overview/) support component identities, versions and dependency relationships. An SBOM should identify which artifact or environment it describes and how it was collected.

An **inventory** can be simpler and still useful. This chapter emits `casebook-ch31-inventory-v1`, an explicitly custom teaching JSON format. It is **not** a validated CycloneDX or SPDX document. A `.json` suffix does not make a file a standard SBOM. A production interchange workflow should choose a supported schema, validate it and retain its collection scope and subject identity.

**Software composition analysis**, or **SCA**, uses component information for work such as advisory matching and dependency policy checks. A known-advisory match is a useful lead. It is not an exploit demonstration, and a zero-match result does not establish absence of malicious or unknown behavior.

### Worked example 1: follow the indirect package into installed code

We will follow four distinct records:

1. The root input explains which package the sample chose directly.
2. The client's `Requires-Dist` metadata explains why the codec is required.
3. The lock and installation report identify the codec version and wheel bytes selected.
4. Installed distribution metadata and source-byte checks establish what is present in the captured environment.

pip's [installation-report specification](https://pip.pypa.io/en/stable/reference/installation-report/) describes selected artifacts and metadata. Its [`pip inspect` specification](https://pip.pypa.io/en/stable/reference/inspect-report/) describes installed distributions. The driver retains both reports; neither is silently relabeled as a standard lock or SBOM.

**Listing L31-04. Capture the installed sample and verify the artifact chain**

Filename: `examples/ch31/capture_inventory.py`.

```python
import hashlib
from importlib import metadata
import json
from pathlib import Path
import re
import sys
from urllib.parse import unquote, urlsplit
from zipfile import ZipFile


def normalize(name):
    return re.sub(r"[-_.]+", "-", name).lower()


def digest(path):
    return hashlib.sha256(path.read_bytes()).hexdigest()


def capture(root, variant):
    assert sys.prefix != sys.base_prefix, "capture must run inside the sample venv"
    root = Path(root).resolve()
    lock = root / f"{variant}.lock"
    pins = {}
    for line in lock.read_text().splitlines():
        if not line or line.startswith(("#", "--")):
            continue
        package, sha = line.split(" --hash=sha256:")
        name, version = package.split("==")
        pins[normalize(name)] = (version, sha)
    report = json.loads((root / f"install-{variant}.json").read_text())
    selected = {normalize(item["metadata"]["name"]): item for item in report["install"]}
    assert set(selected) == set(pins)
    packages = []
    for distribution in sorted(metadata.distributions(), key=lambda d: normalize(d.metadata["Name"])):
        name = normalize(distribution.metadata["Name"])
        row = {"name": name, "version": distribution.version,
               "requires_dist": distribution.metadata.get_all("Requires-Dist") or [],
               "requested_marker": distribution.read_text("REQUESTED") is not None,
               "role": ("application dependency" if name in pins else
                        "bootstrap tooling" if name == "pip" else "unclassified distribution")}
        if name in pins:
            version, sha = pins[name]
            item = selected[name]
            assert distribution.version == version == item["metadata"]["version"]
            address = urlsplit(item["download_info"]["url"])
            assert address.scheme == "file"
            wheel = Path(unquote(address.path)).resolve()
            assert wheel.parent == (root / "wheelhouse").resolve()
            assert digest(wheel) == sha == item["download_info"]["archive_info"]["hashes"]["sha256"]
            code = []
            with ZipFile(wheel) as archive:
                for member in archive.namelist():
                    if member.endswith(".py"):
                        installed = Path(distribution.locate_file(member))
                        actual = digest(installed)
                        assert actual == hashlib.sha256(archive.read(member)).hexdigest()
                        code.append({"path": member, "sha256": actual})
            assert code
            row.update(wheel_file="wheelhouse/" + wheel.name, wheel_sha256=sha,
                       installed_code=code)
        packages.append(row)
    assert set(pins) <= {row["name"] for row in packages}
    return {"schema": "casebook-ch31-inventory-v1", "sample": variant,
            "fictional_application_packages": True,
            "scope": "all installed venv distributions; excludes Python, OS and system libraries",
            "runtime": sys.version.split()[0], "lock_file": lock.name,
            "lock_sha256": digest(lock), "packages": packages}


if __name__ == "__main__":
    print(json.dumps(capture(sys.argv[1], sys.argv[2]), indent=2))
```

The collector runs under each sample environment's interpreter. It requires a virtual environment, reads the selected lock and installation report, then enumerates installed distributions. For the locked application packages it checks:

- Installed name/version agree with the selected records.
- The reported artifact is a file in this sample's wheelhouse.
- The actual wheel digest matches both the lock and the installation report.
- Every Python source file in each fixture wheel matches the installed copy's bytes.

The source comparison establishes more than a matching version label: the installed `ch31_codec/__init__.py` is the file from the selected wheel at capture time. It does not establish that the wheel was produced by a trusted external maintainer, or that nobody can modify the environment later.

Compare versions using their ecosystem's version rules, not string ordering. `1.0.10` is not earlier than `1.0.1` merely because of character positions. PyPA's [version-specifier specification](https://packaging.python.org/en/latest/specifications/version-specifiers/) and packaging's [specifier API](https://packaging.pypa.io/en/stable/specifiers.html) define the relevant Python behavior.

Real advisories may express affected versions, range events, aliases, withdrawals, platform conditions or distributor-specific backports. Match the ecosystem, canonical package identity and actual version/build. Do not feed arbitrary commit ranges or another ecosystem's range syntax into `SpecifierSet`. The [OSV schema](https://ossf.github.io/osv-schema/) documents one standard advisory format; the miniature matcher below accepts only this exercise's labeled fictional record.

**Listing L31-06. Trace the installed parent edge and match the fictional range**

Filename: `examples/ch31/review_build.py`.

```python
import json
from pathlib import Path
import re
import sys

from packaging.requirements import Requirement
from packaging.specifiers import SpecifierSet
from packaging.version import Version


def normalize(name):
    return re.sub(r"[-_.]+", "-", name).lower()


def assess(inventory, advisory):
    if advisory.get("fictional") is not True:
        raise ValueError("this exercise accepts only its labeled fictional advisory")
    packages = {normalize(row["name"]): row for row in inventory["packages"]}
    target = normalize(advisory["package"])
    package = packages[target]
    client = packages["casebook-ch31-client"]
    edges = [Requirement(value) for value in client["requires_dist"]]
    edge = next(value for value in edges if normalize(value.name) == target)
    assert edge.marker is None and not edge.extras  # Scope of this two-package example.
    assert Version(package["version"]) in edge.specifier
    affected = Version(package["version"]) in SpecifierSet(advisory["affected_specifier"])
    return {"sample": inventory["sample"], "advisory": advisory["id"], "fictional": True,
            "path": ["sample requirements.in", client["name"], package["name"]],
            "installed_version": package["version"], "parent_specifier": str(edge.specifier),
            "affected_range_match": affected, "wheel_sha256": package["wheel_sha256"],
            "installed_code": package["installed_code"], "owner": advisory["owner"]}


if __name__ == "__main__":
    root = Path(sys.argv[1])
    advisory = json.loads(Path(__file__).with_name("advisory.json").read_text())
    affected = SpecifierSet(advisory["affected_specifier"])
    for version, expected in (("0.9.9", False), ("1.0.0", True), ("1.0.1", False), ("1.0.10", False)):
        assert (Version(version) in affected) == expected
    for variant in ("before", "after"):
        inventory = json.loads((root / f"inventory-{variant}.json").read_text())
        result = assess(inventory, advisory)
        assert result["affected_range_match"] == (variant == "before")
        (root / f"decision-{variant}.json").write_text(json.dumps(result, indent=2))
        print(f"{variant}: {result['installed_version']}; fictional affected-range match: "
              f"{result['affected_range_match']}; parent constraint satisfied")
```

Run under the builder interpreter, which has packaging installed:

```shell
python examples/ch31/review_build.py "$LAB"
```

Expected output, also observed locally:

```text
before: 1.0.0; fictional affected-range match: True; parent constraint satisfied
after: 1.0.1; fictional affected-range match: False; parent constraint satisfied
```

The script checks four version boundaries, reads the parent requirement from installed metadata and writes `decision-before.json` and `decision-after.json`. Those files record a range assessment and component evidence. They are not automatic production approvals or signed attestations.

The matcher handles one known parent edge with no extras or markers. That is enough to make this dependency decision concrete. It is not a complete dependency resolver, an SCA engine or a live advisory-feed client. The lack of another match says nothing about real pip or about unknown vulnerabilities in any component.

## 4. Maintainer trust, provenance, reachability, update testing and rollback

Finding a package in an affected range is one part of an update decision. The reviewer still needs to ask where it came from, whether the relevant path is used, which fix is acceptable and how to verify the resulting build.

### Keep identity, integrity and provenance distinct

**Maintainer trust** concerns the people and processes controlling a package release. For a real dependency, examine the canonical project/repository relationship, release history, account or ownership changes, published security information and the actual release being selected. Popularity and a familiar name alone do not establish that relationship.

**Provenance** records where and how an artifact was produced. SLSA's [provenance description](https://slsa.dev/spec/v1.2/provenance) separates verifiable build/source history from a bare filename or version. Verifying an attestation requires an expected subject digest and trusted signer/builder policy. A valid signature from an untrusted identity does not solve that selection problem, and trusted provenance does not prove the code contains no vulnerability.

Here the source is the book's authored fixture, the backend and its versions are recorded, and the wheels are retained. No external maintainer authentication, package signature, registry attestation or SLSA level is established. The hashes prove the specific byte comparisons we performed. They do not transform the fictional release into a trusted third-party product.

### Establish reachability without turning absence of evidence into safety

**Reachability** asks whether the application can execute the relevant code under the advisory's stated conditions. In this sample the path is concrete: `preview_title(raw)` calls imported `read_title(raw)`, and the public-client regression passes a 257-byte valid record through that path. The old code accepts it; the fixed code rejects it before JSON parsing.

That observation supports the fictional missing-bound claim. It does not measure practical memory exhaustion, network ingress limits, worker concurrency or production exploitability. The record bytes were already allocated by the caller before the codec checks their length. An upstream component still needs bounded acquisition; a post-acquisition decoder limit cannot reclaim memory already spent receiving an unbounded request.

For a real advisory, record the relevant feature, entry point, configuration and argument restrictions. “We did not see the function called” is weaker than an established disabled feature or a reviewed call-path exclusion. A reachability-based exception needs evidence, an owner, an expiry/review trigger and a response if the assumptions change. An SBOM records presence; it does not by itself prove or disprove reachability.

### Make the update decision concrete

**Table T31-07. Filled decision for FICTIONAL-CH31-001**

| Decision field | Evidence and action |
| --- | --- |
| Component and path | The root client requires the codec. `before.lock`, the installer report and installed source-byte checks agree on codec `1.0.0`. |
| Advisory status | Authored fictional advisory; affected range `>=1.0.0,<1.0.1`. No real vulnerability identifier or external feed result is asserted. |
| Reachable condition | The public client accepts record bytes and reaches the unbounded old decoder. The 257-byte boundary regression fails under the before environment. |
| Candidate correction | Select codec `1.0.1` and its new wheel hash in a fresh environment. The client remains `1.0.0`; its version range permits this release. |

| Regression evidence | The 257-byte input raises `record_too_large` in the after environment. All four methods pass there. |
| Artifact evidence | New lock, install report, installed inventory and wheel/source digests are retained for the after environment. |
| Owner | Casebook integration maintainer, the fictional exercise's accountable role. |

| Remaining review | Real deployment authentication/authorization, ingress bounds, broader resource limits, actual advisory feeds and builder/OS provenance remain outside this exercise. |

A patch-version number alone is not compatibility evidence. The new size refusal is an intentional contract change: callers that previously supplied larger records must now bound or reject them. Check legitimate data and exception handling at the actual call site. If a parent's constraints excluded the fixed codec, do not force an incompatible install and treat a quiet resolver as success; find a compatible parent release or another reviewed correction.

The sample's three compatibility checks are appropriate for its one-function adapter. An actual Casebook dependency update should also run the relevant service, browser and worker checks. This standalone adapter did not import Django or cryptography, so its successful update does not close chapter 30's unexecuted HTTP/Hypothesis gap or verify a cryptographic-library upgrade.

### Preserve rollback evidence without restoring the weakness blindly

The driver constructs `venv-before` and `venv-after` separately. It does not update one environment in place. The retained-before compatibility run proves the original sample environment still performs the three earlier contract behaviors after the candidate is built.

That is preservation evidence, not a deployment rollback rehearsal. Virtual environments are not generally relocatable deployment artifacts, and no production switch occurs here. A real release should retain the approved previous artifact and its identity, configuration compatibility, data/schema compatibility and tested switching procedure.

For a security fix, returning to the affected build can also return the weakness. If the new build has an operational regression, a reviewed fallback may require disabling the reachable feature or another verified mitigation before restoring service. Record who owns that decision and how long the fallback may remain. “The old tests pass” does not authorize indefinite operation of an affected reachable component.

The demonstration's sample data and advisory are fictional, so no live mitigation or incident action is required. Its purpose is to make the decision record inspectable before chapter 32 connects those results to a gate.

## What you can now explain

A root dependency file describes intent. Parent metadata explains an indirect requirement. A reviewed lock and installer report identify selected release files. An installed inventory, with source-byte comparisons, establishes the observed code copy for its stated subject and scope.

An advisory decision combines identity, version range, reachability, compatibility, regression evidence and an owner. No one pin, hash, inventory or successful metadata check supplies all of those facts.
