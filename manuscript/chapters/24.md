## 1. HTML, templates, context-sensitive encoding and cross-site scripting

**HTML** is a document language. A browser parses markup into a **Document Object Model**, or **DOM**, a tree of elements, attributes and text. Source bytes and the text a user sees are different evidence.

A **template** combines fixed document structure with values supplied by the service. The service must authorize the note before sending it into the template. Correct rendering of Ravi's unauthorized Alpha note would still be a privacy failure.

**Cross-site scripting**, or **XSS**, occurs when attacker-controlled content is interpreted as executable browser content in an application's context. Stored note titles and bodies are untrusted for HTML interpretation even when only signed-in members can write them. Authentication does not make a member's text safe markup.

### Worked example 1: `A & B` through source and text

Predict the source inside the heading and the text shown to Mina. The stored title is the plain string `A & B`, not a pre-escaped string.

```html
<h1 id="note-title">A &amp; B</h1>
```

The browser interprets the character reference `&amp;` as an ampersand in a text node, so the heading's `textContent` is `A & B`. Encoding preserved the intended value while keeping it in a text context. It did not alter the stored note.

An **output context** is the place in the document where a value is inserted. HTML text, an attribute, a URL, JavaScript and CSS have different interpretation rules. **Context-sensitive encoding** uses the right protection for that place.

**Table T24-02. Context determines the protection**

| Destination | Example in this chapter | Required decision |
| --- | --- | --- |
| HTML text node | Heading and note body in a `pre` element | Keep template autoescaping on |
| Quoted ordinary attribute | `value="{{ note.title }}"` | Quote the attribute and preserve escaping; do not use arbitrary attribute names |
| URL | Form action | Generate the application route from validated IDs; validate allowed schemes/destinations for user-supplied links |
| JavaScript or CSS | None in the note page | Do not paste arbitrary note strings into executable code or styles |
| Rich HTML | Not supported by this note contract | Needs a reviewed maintained sanitizer and an explicit allowed-content policy; escaping and sanitizing are different operations |

HTML escaping does not make `javascript:` a permitted link destination. It does not turn arbitrary input into safe JavaScript. If structured data must be supplied to an approved script later, Django's `json_script` is a maintained data-embedding tool to consider; it is not a reason to interpolate strings into executable script bodies.

### Let the template preserve the context

**Listing L24-01. The private note template**

Filename: `examples/ch24/templates/notes/detail.html`.

```html
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Casebook note</title>
</head>
<body>
  <main>
    <h1 id="note-title">{{ note.title }}</h1>
    <pre id="note-body">{{ note.body }}</pre>
    <form method="post" action="{% url 'title' note.workspace_id note.id %}">
      {% csrf_token %}
      <input type="hidden" name="expected_version" value="{{ note.version }}">
      <label for="title">Title</label>
      <input id="title" name="title" value="{{ note.title }}" maxlength="200" required>
      <button type="submit">Save title</button>
    </form>
    <form method="post" action="/accounts/logout/">
      {% csrf_token %}
      <button type="submit">Sign out</button>
    </form>
  </main>
</body>
</html>
```

`{{ note.title }}` inserts a value with Django's normal HTML autoescaping. The input value is quoted. The `pre` element preserves useful body whitespace but does not disable escaping. The URL tag generates the title-update path; the user does not supply a form destination in a hidden field.

`{% csrf_token %}` inserts a hidden token for the framework's CSRF check. It does not establish note access, and its presence alone does not show that middleware is enforcing anything. We test both allowed and refused submissions later.

Do not add `|safe`, use `mark_safe` on stored note content, or turn autoescaping off merely to fix display. Those operations change whether the template treats data as already safe for HTML. If the stored value were the literal text `<img src=x onerror="alert(1)">`, the page must show that text rather than create an image element. A CSP that happens to block the handler would not repair the broken rendering contract.

Do not store `A &amp; B` as a replacement for `A & B`. Escaping belongs at the output boundary; storing an escaped value can cause repeated encoding and corrupt the intended text in other formats.

### Inspect expected HTML without pretending it came from Django

The following helper also extracts hidden form inputs from real rendered responses when the Django tests run. Its standalone mode parses a **hand-authored expected HTML fragment**. That mode tests HTML entity interpretation in Python's parser, not template execution, browser layout or JavaScript behavior.

**Listing L24-02. Source and parsed-text evidence**

Filename: `examples/ch24/html_evidence.py`.

```python
"""Parse expected HTML syntax; this does not execute Django or a browser."""
from html.parser import HTMLParser


class PageEvidence(HTMLParser):
    def __init__(self):
        super().__init__(convert_charrefs=True)
        self.in_title = False
        self.title_text = ""
        self.inputs = {}
        self.active_tags = []

    def handle_starttag(self, tag, attrs):
        attributes = dict(attrs)
        if tag == "h1" and attributes.get("id") == "note-title":
            self.in_title = True
        if tag == "input" and "name" in attributes:
            self.inputs[attributes["name"]] = attributes.get("value", "")
        if tag in ("script", "img", "iframe"):
            self.active_tags.append(tag)

    def handle_endtag(self, tag):
        if tag == "h1":
            self.in_title = False

    def handle_data(self, data):
        if self.in_title:
            self.title_text += data


if __name__ == "__main__":
    expected_html = '<h1 id="note-title">A &amp; B</h1><input name="title" value="A &amp; B">'
    page = PageEvidence()
    page.feed(expected_html)
    print("HTML source:", expected_html)
    print("parsed title:", page.title_text)
    print("parsed input:", page.inputs["title"])
    assert page.title_text == page.inputs["title"] == "A & B"
```


## 2. Origins, the same-origin policy and cross-origin resource sharing

An **origin** usually combines a scheme, host and port. Paths are not part of this tuple. The **same-origin policy**, or **SOP**, restricts one origin's script access to another origin's protected resources and document state.

A **site** is a different browser concept, used by controls such as SameSite cookies. Modern schemeful site comparisons include scheme and a registrable-domain relationship. Same-site does not necessarily mean same-origin.

**Table T24-03. Compare origins with `https://casebook.example`**

| Other URL | Same origin? | Important consequence |
| --- | --- | --- |
| `https://casebook.example/notes/101/` | Yes | Changing the path does not create an origin boundary |
| `https://casebook.example:443/other/` | Yes | Explicit default HTTPS port represents the same origin |
| `https://casebook.example:8443/` | No | Different port; cookie matching is not isolated by port |
| `https://api.casebook.example/` | No | Different host, even if it is in the same site |
| `http://casebook.example/` | No | Different scheme; Secure cookie behavior also changes |
| `https://other.example/` | No | Different origin and site in this fictional example |

### CORS controls response sharing with browser scripts

**Cross-origin resource sharing**, or **CORS**, is a protocol through which a server permits specified cross-origin browser scripts to access a response. The browser enforces the sharing decision. It is not an account login or workspace permission mechanism.

An `Access-Control-Allow-Origin` response header names an allowed requesting origin or, for suitable public noncredentialed responses, a wildcard. Credentialed cross-origin sharing requires the appropriate specific origin and credential permission; `*` is not a valid replacement for the specific origin when the credentials mode is `include`.

Our note application needs no cross-origin script consumer. It emits no CORS permission headers. A same-origin browser form does not need them. The notes API and any future approved partner browser client would need their own reviewed contract; do not add broad CORS headers to every private response to silence a browser error.

For some cross-origin requests, the browser first sends a **preflight**, an OPTIONS request asking whether the proposed method and headers are allowed. Other requests can be sent without that preflight. A normal cross-site form submission is one reason not to equate “no CORS permission” with “no request can arrive.”

If a request reaches the service, the service still needs its own authentication, authorization and state-change protections. Non-browser clients do not enforce the browser's CORS response-read restriction and can supply or omit an Origin header. Never rely on CORS as the private-data gate.

### Trusted origins for CSRF are a separate setting

Django's `CSRF_TRUSTED_ORIGINS` affects its trusted-origin check for unsafe requests. It does not emit CORS headers, authenticate the caller or remove the CSRF token requirement. Conversely, a CORS response header does not tell Django to authorize a form submission.

The lab uses `Referrer-Policy: same-origin`, preserving a same-origin Referer for the HTTPS fallback check when Origin is absent while avoiding cross-origin referrer disclosure. Its prepared test includes that fallback. Stripping Referer globally can break legitimate unsafe HTTPS requests without Origin; do not treat that failure as a reason to disable CSRF.

The lab leaves `CSRF_TRUSTED_ORIGINS=[]` and uses same-origin form posts. A valid-token POST from `https://other.example` should fail the origin check. A test client that submits an authenticated cross-origin **GET** can still receive a 200 body with no CORS header; the test client is not a browser enforcing CORS. That distinction is intentional evidence in the prepared tests.

## 3. Cookies, cross-site request forgery and framework checks

Browsers attach matching cookies automatically under their cookie and request rules. That convenience creates the CSRF risk: another site may cause a request to be sent while the browser supplies a credential the attacker cannot read directly.

**CSRF**, or cross-site request forgery, causes an unwanted authenticated action. A defense must connect the unsafe request to the legitimate interaction rather than merely observe that a session cookie exists. The state-changing route must also check current workspace authority and input/business rules.

### Cookie flags solve specific problems

**Table T24-04. Cookie decisions for the default HTTPS/test profile**

| Attribute or setting | Choice | What it controls; what it does not |
| --- | --- | --- |
| Session cookie | `__Host-casebook-session` | Browser session handle; not a note permission flag |
| Secure | True | Transport restriction; does not validate the action |
| HttpOnly | True | Restricts ordinary JavaScript cookie reads; does not prevent a script from causing authenticated requests |
| SameSite | Lax | Limits some cross-site cookie sending; does not mean same-origin or replace CSRF checks |
| Path / Domain | `/`, no Domain | Host-prefix-compatible scope; paths/ports are not a general tenant security boundary |
| CSRF cookie HttpOnly | True in this form-only lab | Forms obtain the submission token from rendered HTML; code must not assume JavaScript can read the cookie |
| CSRF cookie Secure | True | Default profile uses HTTPS test requests |

The CSRF token is not the session identifier. Django can mask a submission token, so it need not be byte-for-byte equal to the cookie value. Use the framework's validation rather than writing a string comparison. Sign-in rotates relevant CSRF state; obtain a fresh token from the note form after login rather than reusing the login page's token.

XSS can often read the same-origin form token and submit actions even when it cannot read an HttpOnly session cookie. CSRF protection therefore does not replace XSS prevention. Both remain separate from current object authorization.

```python
class TitleForm(forms.Form):
    title = forms.CharField(max_length=200, strip=False)
    expected_version = forms.IntegerField(min_value=1, max_value=2**63 - 1)

    def clean_title(self):
        title = self.cleaned_data["title"]
        if not title.strip() or any(ord(c) < 32 or 127 <= ord(c) <= 159
                                    or 0xD800 <= ord(c) <= 0xDFFF for c in title):
            raise forms.ValidationError("Enter a valid title.")

def identity(request):
    if not request.user.is_authenticated or not request.user.is_active:
        raise PermissionDenied
    return request.user.pk


def scoped_note(db, user_id, workspace_id, note_id):
    if not positive_id(note_id):
        raise Http404
    try:
        require_member(db, user_id, workspace_id)
        rows = visible_rows(db, user_id=user_id, workspace_id=workspace_id,
                            note_ids=[note_id], limit=1)
        if not rows:
            raise AccessDenied()
    except AccessDenied as exc:
        raise Http404 from exc
    # Read extra state only after the scoped note check, in this same short transaction.
    state = db.execute("SELECT state,version FROM notes WHERE workspace_id=? AND id=?",
                       (workspace_id, note_id)).fetchone()
    return {**rows[0], "state": state["state"], "version": state["version"]}

    return render(request, "notes/detail.html", {"note": note})

    if (set(request.POST) - {"title", "expected_version", "csrfmiddlewaretoken"}
            or any(len(values) != 1 for _, values in request.POST.lists())):
```

### Enable CSRF enforcement in the test client

Django's ordinary test client disables CSRF enforcement by default. A passing POST through that default client would not prove that the middleware accepts or rejects a real CSRF-protected interaction. Use `Client(enforce_csrf_checks=True)` for these cases.

The helper first GETs the login page, extracts its hidden token, posts real fixture credentials, then GETs the permitted note form for fresh submission fields. Positive POSTs specify a same-origin HTTPS Origin header. Negative cases remove the token or change Origin while preserving the other facts.

## 4. Content Security Policy, framing policy, caching and browser evidence

**Content Security Policy**, or **CSP**, lets a response constrain browser resource loading and certain execution/navigation behavior. It reduces the consequences of some injection failures, but is not a substitute for output encoding or object permission.

This lab needs no JavaScript, external images, fonts or styles. Its enforced policy starts with `default-src 'none'`, explicitly refuses scripts and objects, restricts form actions to self, forbids base-URL substitution and forbids framing. Django 6.1 provides maintained CSP middleware and the `SECURE_CSP` setting used in the listing.

A **report-only** CSP reports potential violations without enforcing the same blocking behavior. Check whether the response header is `Content-Security-Policy` or `Content-Security-Policy-Report-Only`; a report-only header is not evidence that a script was blocked.

If a future page needs scripts, design a narrow policy using appropriate approved sources, hashes or fresh response nonces through maintained framework support. A CSP **nonce** authorizes a script/style instance under a policy; it is not the CSRF token or chapter 22's OIDC transaction nonce. Do not add broad inline-execution permission as an unexplained fix.

### Compare the controls in one table

**Table T04. What escaping, cookies, CSRF checks, CORS and CSP each control**

| Control | Question it answers | Where enforced | Casebook example | What it does not decide |
| --- | --- | --- | --- | --- |
| Context-sensitive escaping | Will this value remain data in this output context? | Template/output handling, then parser interpretation | Title source uses `A &amp; B`; markup-like title remains literal text | Whether Mina may read the note; whether a write was intended |
| Cookie settings | When may this browser store/send the cookie, and may ordinary script read it? | Browser | Secure, HttpOnly, SameSite and host-only session scope | Current workspace access or complete CSRF protection |
| CSRF checks | Does this unsafe cookie-authenticated request satisfy the framework's token and origin policy? | Server middleware | Missing token/wrong Origin refused before title write | Whether Ravi may change Alpha; whether output is safe HTML |
| CORS | May a requesting cross-origin browser script access this response? | Browser following server response permissions | No cross-origin script consumer, so no CORS permission headers | Authentication, non-browser access, or preventing every cross-site request from arriving |
| CSP | Does this document permit the attempted resource, script, form destination or framing context? | Browser following the response policy | Script-free note page; inline probe should be blocked; frames forbidden | Current membership, valid form data or a complete XSS fix |

All five controls can be configured correctly while the service accidentally returns another workspace's private note. Chapter 23's object gate therefore remains the first private-data decision.

### Prevent framing and unintended copies

**Clickjacking** tricks a user into interacting with a concealed or misleading framed page. CSP `frame-ancestors 'none'` limits who may embed the protected response. `X-Frame-Options: DENY` supplies an additional framing policy. `frame-src` would instead constrain frames loaded by the page; it does not replace `frame-ancestors`.

Framing policy is sent as a response header. Do not assume placing a meta tag in a template supplies the same protection for directives that require a header. Browser tests should attempt the actual embedding and inspect its refusal.

The private page also sends `Cache-Control: no-store`. `no-cache` has a different meaning: it allows storage while requiring appropriate validation before reuse. `private` alone does not forbid a browser cache from storing a response. Select the policy deliberately and verify it through any deployment proxy or CDN.

No-store does not erase data a legitimate user already saw or copied. A membership change must still affect the next service request, and a cache or alternate artifact route must not bypass current authorization. A browser Back/Forward restoration is also a separate observation from a new network request; record what actually happened rather than treating every old screen as a fresh server release.

### Separate server evidence from browser evidence

Django's test client exercises framework request handling, not a browser engine. It can check response bytes, middleware failures, cookie attributes and stored rows. It does not enforce SameSite/Secure cookie sending like a browser, execute CSP, perform CORS response filtering or establish that text is visibly laid out.

The HTML parser helper can check the response's text/attribute interpretation and absence of raw active tags. It cannot establish a browser's script execution or CSP decision. The standalone expected-HTML mode is even narrower: it is not actual template output.

## Worked answers

### Exercise 1

A quoted ordinary attribute preserves a defined value boundary; an unquoted attribute creates additional parsing hazards. Autoescaping is designed for its HTML contexts, not arbitrary JavaScript, CSS, attribute names or URL semantics. A heading needs text encoding so an ampersand stays text. A link destination also needs an allowed scheme/destination policy, because HTML escaping does not make a dangerous URL scheme acceptable. The supplied template keeps values quoted and generates its form destination from validated application IDs.

### Exercise 2

CORS governs whether a cross-origin browser script may read a response. Some requests, including ordinary form submissions, can arrive without a successful CORS read permission. The service must authenticate, enforce CSRF token and origin policy for the unsafe cookie-authenticated action, authorize the stored note/workspace relationship and validate fields/state/version. A non-browser client also cannot be constrained by relying on browser CORS enforcement.

### Exercise 3

The request is refused with the generic unauthorized-object 404 and no stored mutation. Ravi's active membership belongs to Beta, while note `101` belongs to Alpha. The shared scope cannot match that relationship. A valid session establishes Ravi's identity; CSRF validates the submission context. Neither grants Alpha access. `CSRF_TRUSTED_ORIGINS` changes an origin-validation condition, not membership, and does not emit a CORS permission header.

### Exercise 4

For the initial fixture, expect 403 with version 1, then 303 with version 2, then 409 with version 2. Inspect the complete Alpha row, including title, body, owner, state, version and editor, and inspect Beta's unchanged row. A status alone cannot prove that a rejected request did not write first. The prepared valid-change test explicitly compares those saved fields and the repeat snapshot.

### Exercise 5

CSP can block one consequence without restoring the intended data boundary. An active tag created from user text means the value was parsed as markup. Keep escaping on and use the correct context even when the current policy stops the handler. Policies can change and injection can have effects beyond script execution.

Revocation affects subsequent authorization decisions, not a user's ability to remember, copy or keep already received bytes on screen. A fresh GET must consult current membership and refuse. Browser history restoration and cache behavior need their own observations; no-store is not a remote erase instruction.
