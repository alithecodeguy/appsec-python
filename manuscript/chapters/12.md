## 1. Arrange, act and assert with pytest

A **test** executes code and checks an expectation. A **regression test** stays with the project to detect the return of a previously corrected problem.

Use three steps when writing a test.

| Step | Question | Quota example |
| --- | --- | --- |
| Arrange | Which inputs establish the case? | Three stored notes and a limit of three |
| Act | Which behavior is being exercised? | Ask whether another note fits. |
| Assert | What must the result be? | The function must return `False`. |

An `assert` statement checks an expression. If it is false, Python raises `AssertionError`. Pytest reports the test and the values involved. Use assertions for test expectations. Application permission checks must remain ordinary executable conditions, since Python optimization can disable ordinary assertions.

### Prepare the deliberately faulty quota function

The function below extracts chapter 04's boundary into a reusable interface. Its final line deliberately uses the wrong comparison. It accepts nonnegative integer counts, including a count already above the limit, and a positive integer limit.

Before saving the example, create a branch in the learning repository and inspect your starting changes.


**Listing L12-01. The quota exercise's starting point**

Filename: `quota_rules.py`.

```python
def can_add_note(*, current_count: int, note_limit: int = 3) -> bool:
    if type(current_count) is not int or current_count < 0:
        raise ValueError("current_count must be a nonnegative integer")
    if type(note_limit) is not int or note_limit < 1:
        raise ValueError("note_limit must be a positive integer")
    return current_count <= note_limit
```

The exact-type checks exclude booleans, as in the earlier record validators. The return value describes quota capacity. A creation operation also needs current permissions and a consistent storage update, developed in later chapters.

### Write the boundary expectation first

**Listing L12-02. The failing boundary test**

Filename: `tests/test_quota_boundary.py`.

```python
from quota_rules import can_add_note


def test_full_workspace_refuses_another_note():
    current_count = 3
    note_limit = 3

    allowed = can_add_note(current_count=current_count, note_limit=note_limit)

    assert allowed is False
```

Pytest calls the test function. The blank lines divide arrangement, action and assertion. `is False` checks that the result is the boolean refusal specified by the contract.

Run only this file on Windows.

```powershell
.\.venv\Scripts\python.exe -m pytest -q tests/test_quota_boundary.py
```

On macOS and Linux, use the following.

```shell
./.venv/bin/python -m pytest -q tests/test_quota_boundary.py
```

The test should fail. A shortened output excerpt has the following form; timing and path details vary.

```text
>       assert allowed is False
E       assert True is False

FAILED tests/test_quota_boundary.py::test_full_workspace_refuses_another_note
```

Read the assertion and its observed value. The function returned true at count three. The product rule says a fourth note would exceed the limit. This is the intended failure, with the test successfully exposing the bug.

A collection or import error would be different evidence. If pytest cannot import `quota_rules`, fix the file placement or invocation before treating the run as a demonstrated quota failure. [Assertions and failure reports](https://docs.pytest.org/en/stable/how-to/assert.html)

### Correct the implementation and retain the test

Replace `quota_rules.py` with the following complete version. Only its final comparison changes.

**Listing L12-03. The corrected boundary**

```python
def can_add_note(*, current_count: int, note_limit: int = 3) -> bool:
    if type(current_count) is not int or current_count < 0:
        raise ValueError("current_count must be a nonnegative integer")
```

Run the same test command again. It should now report one passing test. Keep the assertion unchanged. Your evidence connects the product expectation to both the failure and its correction.

```diff

+    return current_count < note_limit
```

## 2. Cover related cases with fixtures and parameters

One boundary case establishes one important behavior. Add ordinary and invalid-input cases that distinguish neighboring outcomes.

**Parametrization** runs a test with several supplied input sets. Pytest treats each parameter set as a separate case. A **fixture** supplies named setup to a test that requests it through a parameter.

### Check the quota neighborhood and expected exceptions

**Listing L12-04. A quota table and invalid-input checks**

Filename: `tests/test_quota_cases.py`.

```python
import pytest

from quota_rules import can_add_note


@pytest.mark.parametrize(
    "current_count, expected",
    [(0, True), (2, True), (3, False), (4, False)],
)
def test_quota_capacity(current_count, expected):
    assert can_add_note(current_count=current_count, note_limit=3) is expected


@pytest.mark.parametrize("current_count", [None, -1, True, "2", 2.5])
def test_invalid_count_is_rejected(current_count):
    with pytest.raises(ValueError, match="current_count must be a nonnegative integer"):
        can_add_note(current_count=current_count)


@pytest.mark.parametrize("note_limit", [0, None, True])
def test_invalid_limit_is_rejected(note_limit):
    with pytest.raises(ValueError, match="note_limit must be a positive integer"):
        can_add_note(current_count=2, note_limit=note_limit)
```

`pytest.raises` passes only if its block raises the expected exception. A normal return or different exception fails the check. `match` checks the message using a regular expression. These messages contain ordinary words, so the patterns are straightforward.

This file produces twelve test cases: four capacities, five invalid counts and three invalid limits. Together with the original regression, the quota tests contain thirteen cases. Expected values come from the stated policy, independently of the implementation's chosen operator. [Parametrization](https://docs.pytest.org/en/stable/how-to/parametrize.html)

### Worked example 1. Test the access rule across roles

Use the unchanged `may_read` interface from chapter 06. It requires explicit sign-in, active-membership, workspace and role facts.

**Listing L12-05. Fresh member facts for each permission case**

Filename: `tests/test_access_rules.py`.

```python
import pytest

from access_rules import may_read


@pytest.fixture
def member_facts():
    return {
        "signed_in": True,
        "membership_active": True,
        "reader_workspace": "Alpha",
        "note_workspace": "Alpha",
        "role": "member",
    }


@pytest.mark.parametrize(
    "changes, expected",
    [
        ({"role": "member"}, True),
        ({"signed_in": False, "membership_active": False, "role": "visitor"}, False),
        ({"role": "unknown"}, False),
        ({"reader_workspace": "Beta"}, False),
        ({"membership_active": False}, False),
        ({"role": "manager"}, True),
        ({"role": "manager", "reader_workspace": "Beta"}, False),
    ],
    ids=["member", "visitor", "unknown", "other-workspace", "revoked", "manager", "other-manager"],
)
def test_read_permission(member_facts, changes, expected):
    member_facts.update(changes)
    before = member_facts.copy()

    allowed = may_read(**member_facts)

    assert allowed is expected
    assert member_facts == before
```

`.update` applies each case's changed fields. `**member_facts` supplies dictionary entries as keyword arguments, the forwarding syntax used in chapter 11.

By default, this fixture runs afresh for each requesting test case. The mutable dictionary from one case is therefore separate from the next case's dictionary. The final comparison checks that the rule left its input facts intact.

The visitor is refused at sign-in. The unknown-role case deliberately retains active Alpha membership so it reaches the role fallback. The cross-workspace manager case protects the requirement that management applies inside the reader's own workspace.

The `ids` labels make a failing case easier to identify in pytest's report. They describe the policy scenario rather than exposing private user data. [Fixture behavior](https://docs.pytest.org/en/stable/how-to/fixtures.html)

## 3. Combine components while controlling files and time

A **unit test** focuses on a small operation, such as the quota comparison. An **integration test** checks cooperating components, such as a file reader, JSON parser and counting function. The distinction describes the scope being exercised, which should be clear from each test's arrangement.

A **test double** is a controlled replacement for a dependency. A fake clock is a useful example. Use the real component when the test needs its behavior, and substitute a dependency when the test needs precise control over it.

### Create a file inside a test-owned directory

Pytest's `tmp_path` fixture supplies a separate temporary directory for a test. Our fixture creates three valid records followed by malformed JSON. That fourth record distinguishes a bounded preview from accidental extra consumption.

**Listing L12-06. A shared file fixture for preview tests**

Filename: `tests/conftest.py`.

```python
import json

import pytest


@pytest.fixture
def note_inventory(tmp_path):
    records = [
        {"id": 1, "workspace": "Alpha", "title": "Release plan"},
        {"id": 2, "workspace": "Beta", "title": "Pricing review"},
        {"id": 5, "workspace": "Alpha", "title": "برنامه انتشار"},
    ]
    text = "\n".join(json.dumps(record, ensure_ascii=False) for record in records)
    path = tmp_path / "notes.jsonl"
    path.write_text(text + "\ninvalid JSON\n", encoding="utf-8")
    return path
```

Pytest discovers fixtures in `conftest.py` for tests in that directory and its descendants. A test requests `note_inventory` by naming it in its signature. The returned value is the fixture file's `Path`.

The file belongs to this test setup. It leaves the learning folder's ordinary `notes.jsonl` untouched. Pytest manages temporary-directory retention, so inspect its reported paths when investigating a failure. [Temporary paths](https://docs.pytest.org/en/stable/how-to/tmp_path.html)

**Listing L12-07. Checking the preview's actual read boundary**

Filename: `tests/test_preview_counts.py`.

```python
import json

import pytest

from preview_counts import count_records


def test_three_record_preview_stops_before_bad_fourth(note_inventory):
    assert count_records(note_inventory, limit=3) == 3


def test_requesting_four_reaches_invalid_json(note_inventory):
    with pytest.raises(json.JSONDecodeError):
        count_records(note_inventory, limit=4)


def test_zero_limit_does_not_parse_first_record(note_inventory):
    note_inventory.write_text("invalid JSON\n", encoding="utf-8")
    assert count_records(note_inventory, limit=0) == 0
```

The first case would fail if the counter parsed one extra record. The second proves the malformed input is actually detectable. The third places the malformed text first and establishes the zero-consumption boundary.

Those cases use real file reading and JSON parsing. They test more than a stub that simply returns the requested limit. The shared fixture is recreated per case, so the third test's file edit does not alter the other tests' input.

### Worked example 2. Replace a clock in an expiry check

An expiry result must be stable at a named boundary. For this exercise, a token is expired when the current instant is equal to or later than its expiry instant. Use timezone-aware datetimes so the instants can be compared deliberately.

**Listing L12-08. An expiry check with an explicit clock dependency**

Filename: `expiry.py`.

```python
from collections.abc import Callable
from datetime import datetime, timezone


def utc_now() -> datetime:
    return datetime.now(timezone.utc)


def token_expired(
    expires_at: datetime,
    *,
    clock: Callable[[], datetime] = utc_now,
) -> bool:
    if expires_at.tzinfo is None or expires_at.utcoffset() is None:
        raise ValueError("expires_at must be timezone-aware")
    now = clock()
    if now.tzinfo is None or now.utcoffset() is None:
        raise ValueError("clock must return a timezone-aware datetime")
    return now >= expires_at
```

`Callable[[], datetime]` describes a function taking no arguments and returning a datetime. The normal default reads the current UTC time. The test supplies its own clock instead, independently of the date on the computer running it.

**Listing L12-09. Before, at and after expiry without waiting**

Filename: `tests/test_expiry.py`.

```python
from datetime import datetime, timedelta, timezone

import pytest

from expiry import token_expired


@pytest.mark.parametrize("offset, expected", [(-1, False), (0, True), (1, True)])
def test_expiry_boundary(offset, expected):
    expiry = datetime(2026, 11, 26, 12, 0, tzinfo=timezone.utc)
    instant = expiry + timedelta(seconds=offset)

    def fixed_clock():
        return instant

    assert token_expired(expiry, clock=fixed_clock) is expected


def test_naive_expiry_is_rejected():
    expiry = datetime(2026, 11, 26, 12, 0)
    with pytest.raises(ValueError, match="expires_at must be timezone-aware"):
        token_expired(expiry)


def test_naive_clock_result_is_rejected():
    expiry = datetime(2026, 11, 26, 12, 0, tzinfo=timezone.utc)

    def naive_clock():
        return datetime(2026, 11, 26, 12, 0)

    with pytest.raises(ValueError, match="clock must return a timezone-aware datetime"):
        token_expired(expiry, clock=naive_clock)
```

These five cases include the exact equality boundary and two invalid-time representations. None needs a delay. The naive-expiry case raises before the default clock is called. No test outcome depends on the machine's current time.

### Control an existing timing wrapper

Chapter 11's wrapper imported `perf_counter` into the `timing` module. Patch the name where the wrapper looks it up: `timing.perf_counter`. Patching another module's name would not replace that existing binding.

**Listing L12-10. Deterministic duration and preserved metadata**

Filename: `tests/test_timing.py`.

```python
import pytest

from preview_counts import count_records
import timing


@pytest.fixture
def fixed_counter(monkeypatch):
    readings = iter((10.0, 10.25))

    def counter():
        return next(readings)

    monkeypatch.setattr(timing, "perf_counter", counter)


def test_timed_preview_preserves_result_and_metadata(
    note_inventory, fixed_counter, capsys
):
    wrapped = timing.timed(count_records)

    result = wrapped(note_inventory, limit=3)

    assert result == 3
    assert wrapped.__name__ == "count_records"
    assert wrapped.__doc__ == count_records.__doc__
    assert wrapped.__wrapped__ is count_records
    captured = capsys.readouterr()
    assert captured.out == "count_records duration_seconds=0.250000\n"
    assert captured.err == ""


def test_timer_preserves_the_operation_error(fixed_counter, capsys):
    failure = ValueError("synthetic operation failure")

    def failing_operation():
        raise failure

    wrapped = timing.timed(failing_operation)
    with pytest.raises(ValueError) as raised:
        wrapped()

    assert raised.value is failure
    assert capsys.readouterr().out == "failing_operation duration_seconds=0.250000\n"
```

`monkeypatch` restores the changed attribute after the test. Each `fixed_counter` fixture starts with fresh readings. A third unexpected counter call would exhaust that iterator and fail the test, making the observed interaction explicit.

`capsys` captures standard output and standard error. `.readouterr()` supplies the captured text and resets that capture buffer. The test can therefore compare the timing message without depending on real elapsed time.

The second case checks the actual exception object, not just its type. It verifies that the wrapper records duration and propagates the operation's failure when its diagnostic output succeeds. [Monkeypatch](https://docs.pytest.org/en/stable/how-to/monkeypatch.html)

## Worked answers

### Exercise 1

An import failure stops collection before the test can call the function. Resolve the module path and invoke pytest from the learning folder. The intended failure reaches `assert allowed is False` and shows an observed `True` result.

### Exercise 2

The function promises a boolean result, and the full limit must produce refusal. Returning true would admit a fourth note. The implementation's comparison needs correction while the policy-based assertion stays in place.

### Exercise 3

The sign-in refusal determines the result, leaving role checks untested. Supply signed-in, active Alpha membership for an Alpha note, then set the role to `"unknown"`. That reaches the role fallback and checks its default denial.

### Exercise 4

Replace `timing.perf_counter`, since that is the module binding read inside the wrapper. The expiry function has an explicit `clock` parameter, so the test passes a controlled callable through that interface. Both techniques keep actual time from deciding the assertion result.

### Exercise 5

Each test receives a fresh function-scoped `note_inventory` fixture and its own `tmp_path`. The write changes only that case's file. The next case builds its fixture again from the known records.

### Practice check
