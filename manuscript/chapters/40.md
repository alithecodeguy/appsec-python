The checker works, the queue has three priorities and the team wants to release. Who owns the remaining risk? Which evidence must exist before promotion, and what happens when an exception reaches its review date?

This chapter turns one Casebook release into a small, repeatable security program. We will give the work named owners, tie requirements to evidence, compare overdue work with meaningful denominators and write a bounded risk decision a product manager can use.

You need the release/evidence boundaries from chapter 32, the audit and recovery decisions from chapters 33–36, the packaged checker from chapter 37, the prioritized queue from chapter 38 and the cloud/grant review from chapter 39. The goal is to coordinate those activities so that another team can repeat them, not merely collect more reports.

By the end, you will be able to:

- Trigger a design review when a change affects a meaningful security boundary.
- Assign requirements, repair ownership, evidence and release authority separately.
- Use SSDF practices and SAMM improvement goals without claiming a maturity score from one release.
- Record a time-limited exception with compensating measures, residual risk and an expiry action.
- Explain why equal overdue counts can describe different workloads.
- Hand over a checker, a prioritized queue and a concrete next-release improvement.

The edition targets **CPython 3.12.14** and **Django 6.1.3**. The small arithmetic/record-checking example ran on **CPython 3.12.14**; all **12 test methods** passed. The release, people, dates, approvals and `FIX40-*` evidence references are **authored fictional records**. The checker evaluates those records; it does not authenticate approvals, inspect a real deployment or authorize a real release.

## 1. Secure software development lifecycle and design review triggers

A **secure software development lifecycle (SSDLC)** makes security work part of planning, implementation, verification, release and operation. A small program needs a repeated decision process: what changed, what matters, who acts, which evidence is required and how the team learns from the outcome.

For this release, keep a short linked record rather than a separate document for every meeting. It contains scope, requirement IDs, owner acceptance, evidence references, unresolved issues and the release decision. Keep sensitive reports in a restricted evidence store; the shared summary should not copy private notes, credentials or complete grant URLs.

### Give work and decisions named owners

**Table T40-01. Fictional release roster**

| Person | Responsibility | Decision boundary |
| --- | --- | --- |
| Nora, product owner | Own customer/business impact and authorized deadline-risk decisions | May accept the scoped patch delay under the exercise policy; cannot waive the mandatory behavior checks |
| Sam, application lead | Own public/dynamic setting investigation, repairs and application regressions | Supplies evidence; does not self-approve the business exception |
| Owen, platform lead and release coordinator | Own runtime/cloud configuration, promotion checks and operational handover | Executes the release procedure only when the required record is complete |
| Tess, AppSec reviewer | Review threat changes, evidence adequacy, exception scope and retests | Gives technical review; records unresolved gaps rather than manufacturing a pass |
| Dana, maintenance owner | Own parser update, disabled-operation controls and compatibility testing | Keeps the issue open until a verified update/removal is delivered |

One person can perform several tasks, but the authority boundaries still need to be explicit. If an owner is absent, record an agreed delegate. “The security team” is not an adequate repair assignment when nobody has accepted the next action.

The application lead's responsibility does not eliminate platform or product decisions. For example, Sam can demonstrate the effective debug setting, Owen can demonstrate runtime identity/host/scheme controls, and Nora can decide whether the specifically permitted schedule risk is worth accepting. None of those facts substitutes for the others.

### Trigger review from changes to a boundary

**Table T40-02. Design review triggers and requested evidence**

| Proposed change | Why review is triggered | Evidence to request before enabling it |
| --- | --- | --- |
| Gateway starts redirecting to direct object grants | Revocation and bearer lifetime change | Grant lifetime/copy tests, membership requirement and release-path decision |
| Worker gains another queue, object prefix or key operation | Workload authority expands | Updated access matrix, actual policy/resource mapping and allowed/denied tests |
| Cache key or authorization order changes | Cached data could bypass current permission | Cross-tenant, user-binding, version and warm-cache revocation checks |
| Archive parser accepts a new input source | Previously disabled/isolated path becomes reachable | Input origin, parsing boundary, version evidence and a new exposure assessment |
| Required audit/recording behavior changes | Failure can change what is committed or acknowledged | Fault-injection results and final stored-state comparison |
| Build/proxy/secret settings change | The running artifact or trust path may differ | Bound artifact/configuration identity and selected runtime checks |

Ask these questions during change planning, before the implementation makes a boundary difficult to alter. Routine work can use the existing requirements and regressions when those boundaries remain applicable. The team should know when to request deeper review without waiting for a scanner label.

## 2. Requirements, verification evidence, SSDF practices and SAMM maturity goals

### Write the behavior before choosing its report

A security requirement says what must hold. Evidence says what was checked, on which subject, by whom and with what limits. A scanner run, a test name or a green build does not automatically cover every requirement.

**Table T40-04. Required evidence for this release decision**

| Requirement/check ID | Required behavior or binding | Owner and review | Evidence required for an actual release |
| --- | --- | --- | --- |
| `artifact_binding` | Reviewed source, dependency inputs and output are linked to the selected candidate | Owen; Tess reviews Dec 3 | Build/check records, immutable artifact identity, selected configuration identity |
| `tenant_release` | Active Mina/Alpha and Ravi/Beta reads work; cross-workspace and post-revocation reads fail, including cache hits | Sam; Tess reviews Dec 3 | Permitted/denied tests, user/object binding and final state after revocation |
| `required_audit` | Required local recording failure blocks or rolls back the selected release/outcome path | Sam/Owen; Tess reviews Dec 3 | Fault injection, no premature acknowledgement/release and stored-state snapshots |
| `deployment_settings` | Effective debug, process identity, host and scheme boundaries match the design | Owen; Tess reviews Dec 3 | Loaded-setting checks and actual runtime/proxy observations on the selected instance |
| `cloud_permissions` | Actual workload roles perform only the needed queue/object/key operations | Owen; Tess reviews Dec 3 | Issuer/scope evidence and real allowed/denied provider operations |
| `recovery_rehearsal` | Restoration preserves intended data and access controls, including current revocations | Dana/Owen; Tess reviews Dec 3 | Backup identity, restored-content checks, negative access tests and required recovery record |

For this exercise these six checks are mandatory and cannot be waived by the dependency deadline exception. Both failure and missing evidence mean hold. An “approved” exception does not turn a missing provider test into a passed provider test.

For a real evidence record, retain check ID, candidate/configuration identity, environment, method, collection time, result, reviewer and a protected report reference. Record why the evidence remains applicable until its review time. A configuration change, different artifact or newly exposed path can invalidate it earlier.

The fixture below uses symbolic candidate/configuration labels and a two-hour evidence window at promotion. Those are authored simplifications. A real reviewer must inspect the referenced reports and their provenance; matching strings are not authentication or proof of test adequacy.

### Use frameworks to organize improvement

The syllabus uses **NIST SSDF 1.1**, documented in [SP 800-218](https://csrc.nist.gov/pubs/sp/800/218/final). It supplies practices that can be integrated into a team's development process. Use it to connect repeatable work to an objective, rather than treating a framework identifier as evidence of completion.

**Table T40-05. Selected SSDF practice links, with authored release evidence**

| Practice reference | Application to this release |
| --- | --- |
| `PO.1` | Maintain the explicit security requirements in T40-04 |
| `PO.4` | Define pass/fail/missing criteria and safeguard their evidence |
| `PW.8` | Test executable behavior against requirements and record results |
| `RV.2` | Assess findings, prioritize response and document the scoped exception |

These are selected links, not a full SSDF implementation assessment. The detailed practice definitions are in the [SSDF publication](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-218.pdf). The six checks, deadlines and exception authority are this chapter's authored policy.

**OWASP SAMM** organizes improvement across Governance, Design, Implementation, Verification and Operations. Its [model](https://owaspsamm.org/model/) contains security practices and maturity objectives. A team can select a small next improvement while acknowledging that a broader assessment needs representative evidence across its actual work.

**Table T40-06. Small improvement goals, not claimed maturity levels**

| SAMM practice | One-release goal | Evidence/review |
| --- | --- | --- |
| Strategy and Metrics | Agree the cohort and decision each metric supports | Nora/Tess review the metric definitions on Dec 1 and Dec 7 |
| Defect Management | All three inherited items have a repair/routing owner, reason, due date and traceable disposition | Sam/Dana supply the queue; Tess reviews original and changed dates |
| Requirements-driven Testing | Link all six selected check families to positive and negative evidence | Owners collect reports; Tess reviews before promotion |

SAMM's [Strategy and Metrics](https://owaspsamm.org/model/governance/strategy-and-metrics/), [Defect Management](https://owaspsamm.org/model/implementation/defect-management/) and [Requirements-driven Testing](https://owaspsamm.org/model/verification/requirements-driven-testing/) provide context for these choices. Completing this fictional release does not establish an organizational SAMM score or certification. Baseline what the real team does, then review whether the selected improvement worked over subsequent releases.

## 3. Vulnerability intake, risk acceptance, service-level targets and ownership

### Keep the queue connected to action

Use one intake path for tool findings, dependency reports, operational incidents and credible external reports, with restricted handling for sensitive evidence. Normalize identities and preserve origins as chapter 38 showed. Add the asset, exposure, current owner, confidence/uncertainty and next evidence needed.

A **service-level target** is an agreed response expectation for a defined class of work. State when its clock starts and what action satisfies it. Time to acknowledge, assign an owner, contain exposure, deliver a verified fix and review an exception are different measures. Acknowledging an urgent report does not mean it is remediated.

For the inherited queue, use the existing action deadlines and priority reasons. Preserve the distinction between a source candidate and a demonstrated runtime issue. Sam must determine the public settings, Dana owns the fictional dependency, and Nora resolves scope/capacity decisions. If an owner or deadline is missed, route it to the named escalation owner instead of silently making the target later.

**Table T40-07. Top-three handover for this release**

| Finding | Owner | Why it is next | Evidence/next action |
| --- | --- | --- | --- |
| `debug-public` | Sam | Selected public path handles private workspace data | Verify effective setting, apply needed containment/fix and retain runtime/regression evidence |
| `debug-dynamic` | Sam, replacing the proposed ownership gap | Public export configuration remains unresolved to the source rule | Record owner acceptance and safe loaded-setting/startup evidence; do not infer a value from the checker environment |
| `archive-offline` | Dana | Lower current exposure, but the High dependency issue remains open | Recheck disabled operation/input restrictions, deliver the reviewed update and use a scoped exception only when justified |

The new owner assignment belongs to the release plan. Keep chapter 38's earlier origin/disposition record as history. A newly assigned owner is not evidence that a defect was fixed, and an exception is not a closure.

### Worked example: a time-limited exception to a required control

The exercise's selected release policy requires High findings affecting the candidate to be fixed before promotion. That deadline/promotion rule is explicitly eligible for a narrowly approved exception. The six behavior/binding checks in T40-04 are not.

Dana reports that the compatibility update for `training-unpack@1.4.0` will not be verified by the Dec 3 release. The maintenance parser remains included but unavailable. The requested exception defers only that update for `CASEBOOK-R40`, not the public debug repair or current-membership requirement.

The compensating measures are:

1. The maintenance invocation is disabled through the reviewed operation/launch path.
2. Customer or other untrusted archives cannot reach it through an admitted input route.
3. Operator execution is restricted and monitored under the agreed procedure.

A statement that the tool is “offline” is insufficient. Confirm the actual entry point, input path and execution authority. A support upload or manual job could otherwise bypass the assumed isolation. The underlying parser weakness remains present even while these barriers reduce current exposure.

**Table T40-08. Completed fictional exception record**

| Field | Decision record |
| --- | --- |
| Exception | `EXC40-01` |
| Required control | `HIGH-FIX-BEFORE-PROMOTION`; only `archive-offline` is deferred |
| Scope | `CASEBOOK-R40`, `candidate-r40-7`, `policy-r40-3`, `maintenance-tool`, `training-unpack@1.4.0` |
| Request/repair owner | Dana |
| Business risk owner | Nora |
| Technical reviewer | Tess |
| Approval time | `2026-12-02T12:00:00Z`, fictional approval |
| Mandatory review | `2026-12-04T12:00:00Z`; Dana targets a verified update/removal before it |
| Expiry | `2026-12-05T12:00:00Z`; maximum seventy-two hours from approval |
| Reason | Ship public-path hardening while the unused maintenance operation remains unavailable |
| Residual risk | An overlooked invocation or input route could still reach the retained vulnerable parser |
| Evidence | Fresh candidate/configuration-bound checks for all three compensating measures, plus all mandatory release checks |
| Stop/review triggers | Changed artifact/policy/component, enabled parser, new untrusted input, failed/stale evidence or changed exploitation/impact information |
| Expiry action | Block new promotions relying on this exception; keep maintenance disabled; Dana patches/removes the utility and Nora owns escalation |

This is a new decision with fresh evidence, not an automatic renewal of chapter 38's expired suppression. The original remediation due date remains in the record. Nora may accept this schedule risk only under the exercise's delegated authority; neither a product title nor an approval string can override other mandatory obligations in a real organization.

### The decision in language a product manager can use

> I approve delaying this maintenance-parser update for this release only, through December 5 at 12:00 UTC. The maintenance feature must stay unavailable and must not receive customer archives. This lets us ship the public-path hardening while Dana finishes the compatible update. The parser is still vulnerable; the risk is that we missed another way to run it.
>
> Owen must verify the restrictions on the selected release, and Tess must review the evidence. Dana targets the update before our December 4 review. If a restriction fails, the release changes or a new input path appears, stop and reassess. This approval does not cover a failed membership check or missing required audit record. At expiry, no new promotion may use this exception, and Nora owns escalation if the update/removal is unfinished.

The business decision names the benefit, unavailable capability, remaining harm, accountable people and stop condition. The technical appendix binds the exact identities and tests. The product manager does not need to interpret a CVSS vector or an IAM policy to understand the choice.

Acceptance does not remove the finding from metrics or allow it to be marked fixed. It records who owns the residual risk and for how long. At expiry, keep the dangerous operation disabled and follow the agreed patch/removal/escalation action. Do not automatically roll back to an older unverified release or re-enable a feature because an exception clock ended.

## 4. Product-team coaching, risk communication and metrics with denominators

### Coach a decision, then improve the routine

Start a review with the customer behavior: a departing Alpha member must not start another private read; Ravi must not obtain Alpha content; a required audit failure must not turn into a completed private release. Ask the team to show the path and the negative case, then record the smallest change that restores the requirement.

Offer reusable examples: the chapter 37 checker for source review, the chapter 38 queue format, the chapter 39 access matrix and warm-cache revocation test. Explain which decision each supports and what it does not cover. This makes security work part of the team's implementation and release habits.

After release, review a specific cause of delay or rework. If evidence arrived for the wrong configuration, improve the binding step. If the owner gap delayed triage, fix assignment. If a manual provider check is repeatedly needed, plan an appropriately protected automated check. Do not measure coaching success only by attendance or the number of findings produced.

### Worked example: four overdue items in each team

Two teams each have four currently overdue open remediation obligations. Predict which is carrying more overdue work relative to its release volume, and which is missing a greater share of its due cohort.

The fixture defines a common window from `2026-11-01T00:00:00Z` inclusive to `2026-12-01T00:00:00Z` exclusive, with a snapshot at the end. A release is a completed production promotion of code or security-relevant configuration; retries are excluded. Emergency promotions count when they meet the same definition.

An overdue item here is a distinct obligation due within that window that remains open at the snapshot. Closed-late work requires a separate measure and is not captured by this count. Do not infer an on-time closure percentage by subtracting the following open-overdue fraction from one.

**Table T40-09. Same overdue count, different denominators**

| Team | Overdue-open items | Completed releases | Due items | Overdue items/release | Overdue-open/due cohort |
| --- | ---: | ---: | ---: | ---: | ---: |
| Web Platform | 4 | 20 | 40 | `4 / 20 = 0.2` | `4 / 40 = 10%` |
| Export Services | 4 | 2 | 5 | `4 / 2 = 2.0` | `4 / 5 = 80%` |

Export Services has ten times as many overdue-open items per release in this fixture. It also has a much larger overdue-open share of the defined due cohort. The count alone hid both differences.

The first ratio is **items per release**, not a probability. Two items per release could be written as 200 per 100 releases, but not as a 200% chance that a release is insecure. The due-cohort fraction answers a different question about outstanding deadline obligations.

For the combined ratio, sum the counts before dividing: eight overdue items across twenty-two releases is about `0.364` per release, and eight across forty-five due items is about `17.8%`. Averaging the two team ratios would weight a two-release team like a twenty-release team and answer a different question.

With zero releases, the per-release ratio is undefined. With zero due items and zero overdue items, the due fraction is undefined. Report the absence rather than silently displaying zero. A positive overdue count with a zero due cohort is inconsistent under this definition.

### What the numbers justify

The fixture supports asking Export Services about ownership, dependencies, capacity and the reason items remain open. It does not establish that its engineers are less capable or its current release is less secure. Release size, exposure, severity, inherited backlog, evidence gaps and small-sample variation still matter.

Nora should ask which delayed items could affect customers now and which support or scope change would improve the next decision. Sam should inspect the actual queue rather than trying to increase the release denominator. Tess should check whether suppression, reopening and closed-late work are being recorded consistently.

**Table T40-10. Useful measures and their limits**

| Measure | Decision it supports | Boundary to retain |
| --- | --- | --- |
| Open overdue obligations / due cohort | Where deadline follow-up is needed | Common window, eligible obligations and original due dates |
| Overdue obligations / completed releases | Context for workload and release cadence | Items/release is not a defect probability or a causal quality ranking |
| Requirements with current adequate evidence / selected requirements | Whether this candidate has reviewable coverage | A syntactic pointer or unrelated passing test is not adequate evidence |
| Current scoped exceptions / applicable release items | Where residual risk and review work remain | Accepted is not fixed; expired is not automatically renewed |
| Time to assign/contain/verify a fix | Which response stage needs improvement | Different clocks and populations; medians/tails do not replace individual urgent cases |

Keep a few measures connected to decisions. A larger count of scans, tickets or releases is not by itself a security outcome. Revisit the definitions with the team when they produce misleading incentives.

### Execute the arithmetic and record checks

Filename: `examples/ch40/program_review.py`.

```python
"""Arithmetic and record checks for the authored release exercise only."""
import argparse
from datetime import datetime, timedelta, timezone
import json
from pathlib import Path
import sys


REQUIRED = {"artifact_binding", "tenant_release", "required_audit",
            "deployment_settings", "cloud_permissions", "recovery_rehearsal"}
COMPENSATING = {"maintenance_disabled", "untrusted_archives_blocked",
                "operator_execution_restricted"}
WAIVABLE = "HIGH-FIX-BEFORE-PROMOTION"


def utc(value):
    instant = datetime.fromisoformat(value)
    if instant.tzinfo is None or instant.utcoffset() is None:
        raise ValueError("timestamp_requires_offset")
    return instant.astimezone(timezone.utc)


def count(value):
    if type(value) is not int or value < 0:
        raise ValueError("invalid_count")
    return value


def rates(row):
    releases, due, overdue = (count(row[key]) for key in
                              ("completed_releases", "due_items", "overdue_open"))
    if overdue > due:
        raise ValueError("incompatible_due_cohort")
    return {"overdue_per_release": overdue / releases if releases else None,
            "overdue_due_fraction": overdue / due if due else None}


def combined(rows):
    for row in rows:
        rates(row)
    totals = {key: sum(row[key] for row in rows)
              for key in ("completed_releases", "due_items", "overdue_open")}
    return rates(totals)


def current_record(record, plan, now, check_id):
    return bool(record and record["status"] == "passed" and record["record_ref"]
                and record["source_kind"] == "authored_fixture"
                and record["check_id"] == check_id
                and record["subject_id"] == plan["subject_id"]
                and record["config_id"] == plan["config_id"]
                and utc(record["checked_at"]) <= now < utc(record["valid_until"]))


def valid_exception(plan, now):
    exception = plan.get("exception")
    item = plan["open_item"]
    if not exception or item["required_control"] != WAIVABLE or item["severity"] != "High":
        return False
    if (exception["state"] != "approved_fixture"
            or not plan["risk_owner"] or not plan["security_reviewer"]
            or exception["approved_by"] != plan["risk_owner"]
            or exception["reviewed_by"] != plan["security_reviewer"]
            or exception["approved_by"] == exception["reviewed_by"]):
        return False
    expected = {key: plan[key] for key in ("release_id", "subject_id", "config_id")}
    expected.update({key: item[key] for key in
                     ("finding_id", "required_control", "asset_id", "component")})
    if any(exception[key] != value for key, value in expected.items()):
        return False
    approved, review, expires = (utc(exception[key]) for key in
                                 ("approved_at", "review_at", "expires_at"))
    if not (approved <= now < review < expires and expires - approved <= timedelta(hours=72)):
        return False
    if not all(exception[key] for key in
               ("id", "requested_by", "business_reason", "residual_risk", "expiry_action")):
        return False
    if (set(plan["compensating_checks"]) != COMPENSATING
            or set(exception["compensating_checks"]) != COMPENSATING):
        return False
    return all(current_record(plan["compensating_evidence"].get(key), plan, now, key)
               for key in COMPENSATING)


def evaluate(plan):
    if plan["schema_version"] != 1 or plan["synthetic"] is not True:
        raise ValueError("simulation_only")
    now = utc(plan["as_of"])
    if set(plan["required_checks"]) != REQUIRED:
        return "HOLD", ["required_control_catalog_changed"]
    blockers = [key for key in sorted(REQUIRED)
                if not current_record(plan["evidence"].get(key), plan, now, key)]
    if blockers:
        return "HOLD", blockers
    if plan["open_item"]["fixed"] is True:
        return (("EXERCISE_GO", []) if current_record(plan.get("fix_evidence"), plan, now, "fix_verification")
                else ("HOLD", ["fix_verification_missing"]))
    if valid_exception(plan, now):
        return "EXERCISE_GO_WITH_EXCEPTION", [plan["exception"]["id"]]
    return "HOLD", ["high_item_has_no_current_scoped_exception"]


def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("release", type=Path)
    parser.add_argument("metrics", type=Path)
    args = parser.parse_args()
    try:
        plan = json.loads(args.release.read_text())
        metrics = json.loads(args.metrics.read_text())
        if metrics["schema_version"] != 1 or metrics["synthetic"] is not True:
            raise ValueError("synthetic_metrics_required")
        if not (utc(metrics["window_start"]) < utc(metrics["window_end"]) <= utc(metrics["snapshot_at"])):
            raise ValueError("invalid_metric_window")
        for row in metrics["teams"]:
            result = rates(row)
            per_release = ("undefined" if result["overdue_per_release"] is None
                           else f"{result['overdue_per_release']:.3f}")
            due_fraction = ("undefined" if result["overdue_due_fraction"] is None
                            else f"{100 * result['overdue_due_fraction']:.1f}%")
            print(f"{row['team']}: overdue/release={per_release}; overdue-open/due={due_fraction}")
        total = combined(metrics["teams"])
        print("combined:", json.dumps(total, sort_keys=True))
        decision, references = evaluate(plan)
    except (OSError, ValueError, KeyError, TypeError):
        print("exercise_record_invalid", file=sys.stderr)
        return 2
    print("simulation decision:", decision, "; references:", ",".join(references) or "none")
    return 1 if decision == "HOLD" else 0


if __name__ == "__main__":
    raise SystemExit(main())
```

The code returns `0` for an exercise go result, `1` for a valid record that leads to hold and `2` for an invalid input/invocation. The evidence validity window is intentionally shorter than the exception window. A seventy-two-hour exception does not make a two-hour-old promotion check current forever. A new promotion needs fresh adequate evidence, and the mandatory review time requires a recorded reassessment before further reliance. Do not merely move a date forward in the file and call that a review.

**Table T40-11. Evaluated exercise decisions**

| Scenario | Result | Meaning |
| --- | --- | --- |
| Mandatory checks and compensating evidence current; scoped approval valid | `EXERCISE_GO_WITH_EXCEPTION` | Model permits this one candidate with `EXC40-01`; item remains open |
| Required audit result failed | `HOLD` | The dependency exception cannot waive the required audit behavior |
| Tenant-release evidence missing | `HOLD` | Absence is not a pass or an accepted risk by default |
| Exception expired, scope changed or reviewer/owner invalid | `HOLD` | There is no applicable authorized exception |
| Issue marked fixed without specific current fix evidence | `HOLD` | A status flag or unrelated build report is insufficient |

### Independent practice answers

**1. Changed policy identity.** The old records no longer prove the new effective configuration. Revalidate the affected controls and collect fresh subject/configuration-bound reports. The exception's exact scope also no longer matches. A configuration-only change is still a meaningful trust-boundary change; do not copy the old approval ID onto it without review.

**2. Enabling the parser.** The compensating disabled-operation condition fails, so the existing exception cannot be used. ## What you can now explain

A small application security program connects requirements, people, evidence and repeatable decisions across one release. Review meaningful boundary changes early, preserve unresolved findings and make every next action accountable.

Risk acceptance records a specific choice under conditions; it does not make a failed behavior check pass or make an issue fixed. Metrics need a defined cohort and unit so the team can improve the response instead of optimizing a misleading score.

For chapter 41, carry forward the current-membership and private-release requirements, the access/ownership boundaries, required audit failure behavior, identity/evidence rules and explicit unresolved checks. The capstone design brief should turn those into a concrete export contract before implementation.
