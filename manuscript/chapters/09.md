# 09. Errors, debugging and cleanup

A settings load fails. Was the file missing, did the operating system refuse access, or did the file contain invalid JSON? After the failure, which resources are closed and what happened to the previous output?

Chapter 08 converted small inventories and reported rejected records. This chapter examines exceptions that interrupt those operations. You will read a traceback, handle specific expected failures and keep unexpected programming errors visible.

Begin in `casebook-learning` with its `.venv` interpreter. Keep `workspace_codes.py` and `note_records.py` from chapters 07–08 available for the debugging exercise. You need functions, `with` blocks and JSON reading.

By the end, you will be able to do four things.

- Read a traceback from its final error description toward the relevant call site.
- Handle missing files, permission failures and malformed JSON distinctly.
- Explain when files close and cleanup runs during exception handling.
- Preserve a previous summary during a failed replacement and investigate a small bug with a debugger.

## 1. Read the failure from the last line upward

Python distinguishes errors in source syntax from exceptions raised while code runs. A **syntax error** means Python cannot parse the source as written. An **exception** interrupts normal execution when an operation fails or explicitly signals a problem.

For example, the following damaged fragment is missing the colon required after an `if` header.

```text
if signed_in
    print("Signed in")
```

Python reports `SyntaxError`, normally with a source location and an indication of the missing syntax. Correct that source before investigating runtime behavior. Error wording and highlighting can vary between interpreter versions.

### Worked example 1. A missing settings file

Save the next listing in the learning folder. For this exercise, leave `missing-settings.json` absent. If a file with that name already exists, choose a fresh missing filename in the script instead.

**Listing L09-01. Following a failed open through two functions**

Filename: `trace_settings.py`.

```python
import json
from pathlib import Path


def load_settings(path):
    with path.open("r", encoding="utf-8") as source:
        return json.load(source)


def main():
    settings = load_settings(Path("missing-settings.json"))
    print(settings["workspace"])


main()
```

Run it once. It should fail when opening the missing path. Below is a shortened illustrative traceback. Standard-library frames are omitted, and the operating system's final message may differ on your computer.

```text
Traceback (most recent call last):
  File ".../trace_settings.py", line 15, in <module>
    main()
  File ".../trace_settings.py", line 11, in main
    settings = load_settings(Path("missing-settings.json"))
  File ".../trace_settings.py", line 6, in load_settings
    with path.open("r", encoding="utf-8") as source:
  ... standard-library frames omitted ...
FileNotFoundError: [Errno 2] No such file or directory: 'missing-settings.json'
```

A **traceback** records the calls involved in an exception. A **frame** identifies one execution context, including the file, function and source line. Start with the last line, then work upward to the nearest relevant line in your code.

**Table T09-01. Reading the missing-file traceback upward**

| Part to inspect | What it tells you | Next action |
| --- | --- | --- |
| Final line, `FileNotFoundError` | Opening the requested path failed because a required path component was absent. | Check the requested path. |
| `path.open(...)` in `load_settings` | The failure occurred while acquiring the input file. | Inspect `path` and the working directory. |
| Call to `load_settings` in `main` | The caller supplied a relative filename. | Confirm which directory gives that name meaning. |
| Call to `main()` | The script's entry point initiated this work. | Follow the inputs from the start if needed. |

The JSON parser was never reached. Editing the JSON content would not fix this failed open. From the learning folder, inspect `Path.cwd()` and the requested path's `.resolve()` value as you learned in chapter 08.

The earliest visible symptom and the underlying cause can also differ. A later `KeyError` might come from a record missing a field. A `TypeError` during arithmetic might come from a function returning `None`. Use the frame where the operation failed, then follow how its inputs were produced. [Python's error tutorial](https://docs.python.org/3.15/tutorial/errors.html)

## 2. Handle expected failures narrowly

A `try` block contains an operation that may raise an exception. An `except` clause handles a specified exception type. Python selects a matching handler when the exception leaves the protected block.

The handler also matches subclasses of its named exception type. For example, both `FileNotFoundError` and `PermissionError` belong under `OSError`. `JSONDecodeError` belongs under `ValueError`. A broad parent handler can therefore hide distinctions you need to preserve.

### Keep file loading in one small function

Save the following module beside the later callers.

**Listing L09-02. Loading a UTF-8 JSON document**

Filename: `json_files.py`.

import json


def load_json_document(path):

This function accepts a `Path` and returns the parsed JSON value. It lets the caller handle file or parsing exceptions. Its contract covers parsing; the inventory schema checks from chapter 08 are a further step.

### Give different failures different outcomes

**Listing L09-03. Reporting expected input failures**

Filename: `settings_check.py`.

```python
import json
from pathlib import Path

from json_files import load_json_document


def report_settings(path):
    try:
        load_json_document(path)
    except FileNotFoundError:
        print("Settings file not found")
        return False
    except PermissionError:
        print("Settings file is not readable")
        return False
    except UnicodeDecodeError:
        print("Settings file is not valid UTF-8")
        return False
    except json.JSONDecodeError as error:
        print("Settings contain invalid JSON")
        print(f"Line {error.lineno} column {error.colno}")
        return False
    else:
        print("Settings JSON loaded")
        return True


if __name__ == "__main__":
    for name in ("settings.json", "broken-settings.json", "missing-settings.json"):
        print(name)
        report_settings(Path(name))
```

`as error` gives the handler a name for the exception object. The JSON error provides line and column information for locating the syntax problem. The `else` block runs when the protected operation finishes without an exception.

With the exact fixtures above, the expected output is the following.

```text
settings.json
Settings JSON loaded
broken-settings.json
Settings contain invalid JSON
Line 1 column 15
missing-settings.json
Settings file not found
```

The `try` block contains only the operation whose expected failures this function handles. The caller receives `True` for a successfully parsed document and `False` for the handled refusals. An unexpected `NameError` or `TypeError` is still allowed to propagate, meaning it continues to a caller or becomes an unhandled traceback.

For example, temporarily misspelling `source` as `soruce` inside `json_files.py` produces `NameError`. None of these handlers claims to know how to recover from that programming mistake. Restore the name after observing it.

### Readability, encoding and syntax are separate checks

| Failure | Typical exception | What to investigate |
| --- | --- | --- |
| Missing file or parent directory | `FileNotFoundError` | Path, working directory and deployment contents |
| Operating system refuses access | `PermissionError` | Process identity and file or directory permissions |
| File bytes violate UTF-8 | `UnicodeDecodeError` | The agreed encoding and the original bytes |
| Decoded text violates JSON syntax | `json.JSONDecodeError` | The document around the reported position |
| Parsed inventory violates the schema | A rejection result or the documented schema exception | Required fields and value rules |

Checking whether a path exists before opening it cannot guarantee that a later open will succeed. File state can change between the check and the operation. Attempt the operation and handle its documented failure at the boundary. [Built-in exceptions](https://docs.python.org/3.15/library/exceptions.html)

### Raise a failure with application context

Use `raise` when an operation must signal failure to its caller. To add context while retaining the original cause, use exception chaining with `raise ... from error`.

**Listing L09-04. Preserving a cause while adding context**

Filename: `required_settings.py`.

```python
from pathlib import Path

from json_files import load_json_document


def load_required_settings(path):
    try:
        return load_json_document(path)
    except FileNotFoundError as error:
        raise RuntimeError("Required settings could not be loaded") from error


if __name__ == "__main__":
    load_required_settings(Path("missing-settings.json"))
```

Running this script shows the original `FileNotFoundError` followed by a message that it directly caused the `RuntimeError`. Read the final application-level failure, then inspect the earlier cause to identify the missing path.

The translation applies specifically to a missing required file. Other failures retain their own exception types. Inside a handler, a bare `raise` re-raises the current exception when you want to preserve its existing meaning. [Raising and chaining exceptions](https://docs.python.org/3.15/tutorial/errors.html#exception-chaining)

## 3. Give cleanup a clear owner

A **context manager** defines entry and exit behavior for a `with` block. A file's exit behavior closes its handle. A temporary-directory context removes its exercise directory when the block ends.

A `finally` block runs when control leaves its associated `try` statement through normal completion, a return or exception unwinding. Use it for required cleanup and observation. A `return` or new exception from `finally` can replace an earlier result or failure, so keep that block focused on its cleanup responsibility.

### Observe cleanup after success, parsing failure and opening failure

The next exercise creates its own temporary fixtures. `TemporaryDirectory` gives it a private exercise directory and removes that directory afterward.

**Listing L09-05. When a file is closed during error handling**

Filename: `cleanup_order.py`.

```python
import json
from pathlib import Path
from tempfile import TemporaryDirectory

with TemporaryDirectory() as directory:
    folder = Path(directory)
    (folder / "good.json").write_text("{}", encoding="utf-8")
    (folder / "bad.json").write_text('{"workspace": }', encoding="utf-8")

    for name in ("good.json", "bad.json", "missing.json"):
        source = None
        print("Opening", name)
        try:
            with (folder / name).open("r", encoding="utf-8") as source:
                print("Closed inside block", source.closed)
                json.load(source)
        except FileNotFoundError:
            print("Open failed")
        except json.JSONDecodeError:
            print("Parse failed")
        else:
            print("Read succeeded")
        finally:
            if source is None:
                print("No handle acquired")
            else:
                print("Closed at finally", source.closed)
```

Predict which paths acquire a file handle. The expected output is the following.

```text
Opening good.json
Closed inside block False
Read succeeded
Closed at finally True
Opening bad.json
Closed inside block False
Parse failed
Closed at finally True
Opening missing.json
Open failed
No handle acquired
```

For malformed JSON, the `with` block closes the file as the exception leaves it. The outer handler then prints `Parse failed`. For the missing path, opening fails before `as source` assigns an object, so the name retains `None`.

**Table T09-02. Cleanup ownership**

| Resource or obligation | Owner | When its work occurs |
| --- | --- | --- |
| Open input file | File context manager | As its `with` block exits |
| Per-attempt status observation | `finally` block | After the matching handler or successful `else` |
| Temporary exercise directory | `TemporaryDirectory` context | After all three attempts leave its block |

These observations describe ordinary Python control flow and exception unwinding. They give the resource a defined owner at each level. [Context-manager execution](https://docs.python.org/3.15/reference/compound_stmts.html#the-with-statement) · [Temporary resources](https://docs.python.org/3.15/library/tempfile.html)

### Worked example 2. A genuine file permission refusal

On macOS or Linux, an ordinary account can usually reproduce a read refusal by removing permission bits from a fixture it owns. This exercise changes only a file inside its temporary directory and restores its original mode in `finally`.

Windows access-control behavior differs, so the script reports that this particular mode-bit demonstration requires macOS or Linux. Accounts with elevated privileges or other access rules can also bypass the intended refusal. Inspect the observed result instead of assuming the error happened.

**Listing L09-06. Distinguishing access refusal from JSON syntax**

Filename: `permission_failure.py`.

```python
import os
from pathlib import Path
import stat
from tempfile import TemporaryDirectory

from json_files import load_json_document

if os.name != "posix":
    print("Permission demonstration requires macOS or Linux")
else:
    with TemporaryDirectory() as directory:
        path = Path(directory) / "private-settings.json"
        path.write_text('{"workspace": "alpha"}', encoding="utf-8")
        original_mode = stat.S_IMODE(path.stat().st_mode)
        try:
            path.chmod(0)
            load_json_document(path)
        except PermissionError:
            print("PermissionError: access refused")
        else:
            print("Read succeeded: this environment permitted access")
        finally:
            path.chmod(original_mode)
            print("Original permissions restored")
```

`stat.S_IMODE` extracts the permission-related mode bits. `chmod(0)` removes those bits for the exercise. The `finally` block restores the saved mode before the temporary-directory context cleans up.

On an ordinary macOS/Linux account where those permissions deny reading, the expected output is the following.

```text
PermissionError: access refused
Original permissions restored
```

The fixture contains valid JSON. The exception comes from the operating system's access check before JSON parsing can begin. For the malformed fixture in Listing L09-03, access succeeds and the parser then raises `JSONDecodeError`. Each failure calls for a different investigation. [Operating-system file operations](https://docs.python.org/3.15/library/os.html)

### Preserve a previous summary until its replacement is ready

Chapter 08 wrote directly to the summary's destination. Opening that destination with `"w"` truncates its earlier contents. If serialization then fails, closing the handle alone does not restore those contents.

Prepare the new document in a uniquely named temporary file in the destination directory. Close it successfully, then replace the destination in one filesystem operation. Keeping both paths on the same filesystem supports the atomic replacement operation.

**Listing L09-07. Publishing a completed JSON document**

Filename: `summary_writer.py`.

```python
import json
import os
from pathlib import Path
from tempfile import NamedTemporaryFile


def write_summary(destination, summary):
    temporary_path = None
    try:
        with NamedTemporaryFile(
            mode="w",
            encoding="utf-8",
            dir=destination.parent,
            prefix="summary-",
            suffix=".tmp",
            delete=False,
        ) as temporary:
            temporary_path = Path(temporary.name)
            json.dump(summary, temporary, ensure_ascii=False, indent=2)
            temporary.write("\n")
        os.replace(temporary_path, destination)
    finally:
        if temporary_path is not None:
            temporary_path.unlink(missing_ok=True)
```

The contract takes a destination `Path` whose parent directory exists and a JSON-serializable summary. It replaces a generated summary file. Serialization, closing or replacement failures propagate to the caller.

`delete=False` keeps the temporary file available after closing it. Closing before replacement also avoids replacing an open temporary file on platforms where that is restricted. If `os.replace` succeeds, the temporary pathname is gone. If it has not succeeded, `finally` removes that temporary file. `missing_ok=True` accepts the already-moved case.

The old output remains intact when preparation fails before replacement. Successful replacement publishes the completed file atomically on a filesystem supporting the operation. Power-loss durability and coordination between competing writers need additional design, addressed in later persistence and concurrency work. [Temporary-file behavior](https://docs.python.org/3.15/library/tempfile.html) · [Replacement semantics](https://docs.python.org/3.15/library/os.html#os.replace)

**Listing L09-08. Checking final state after a failed write**

Filename: `summary_failure.py`.

```python
import json
from pathlib import Path
from tempfile import TemporaryDirectory

from summary_writer import write_summary

with TemporaryDirectory() as directory:
    folder = Path(directory)
    destination = folder / "summary.json"
    destination.write_text('{"state": "previous"}\n', encoding="utf-8")
    before = destination.read_bytes()

    try:
        write_summary(destination, {"records": {1, 2}})
    except TypeError:
        print("Serialization failed")

    print("Previous output kept", destination.read_bytes() == before)
    print("Temporary files remaining", len(list(folder.glob("summary-*.tmp"))))

    write_summary(destination, {"records": []})
    print("New output", json.loads(destination.read_text(encoding="utf-8")))
```

The deliberately supplied set cannot be serialized by the default JSON encoder. The expected output is the following.

```text
Serialization failed
Previous output kept True
Temporary files remaining 0
New output {'records': []}
```

The handler in this exercise expects the deliberately introduced serialization `TypeError`. It then verifies the stored state. The subsequent valid write demonstrates that a corrected retry can publish a new document.

To use this in chapter 08, add `from summary_writer import write_summary` to `convert_notes.py`. Replace only its destination-writing `with` block with `write_summary(destination_path, summary)`. Retain `return summary` and the input validation above it. Re-running the original fixtures should still produce the same two summaries and counts.

## 4. Reduce a bug and inspect it with a breakpoint

A **reproduction** is a small set of inputs and steps that reliably demonstrates a problem. Start with one failing record, the function call and its result. Keep unrelated file operations out of the first investigation when the failure is already in a parsed record.

**Listing L09-09. Pausing before a record check**

Filename: `debug_record.py`.

```python
from note_records import validate_note

record = {"id": 5, "workspace": "alpha"}
breakpoint()
note, reason = validate_note(record)
print(reason)
```

With Python's default debugger hook, `breakpoint()` opens the interactive debugger, normally showing a `(Pdb)` prompt. It pauses before the next statement. Your environment can configure a different hook, so check the debugger configuration if it behaves differently.

| Debugger command | What to inspect |
| --- | --- |
| `p record` | The current fixture dictionary |
| `p "title" in record` | Whether the required key exists |
| `n` | Execute the next source line without stepping into the function |
| `p reason` | The rejection reason after that call |
| `c` | Continue execution |
| `q` | Quit the debugging session |

Enter the first two commands before stepping. The membership expression should show `False`. After `n` executes the validator call, `p reason` should show `'missing field title'`. Continuing prints `missing field title` and finishes the script.

The example narrows the investigation to the record that matters. Once the input problem is understood, return to the reader or fixture that produced it. Remove the temporary breakpoint when the investigation is complete. [Python debugger](https://docs.python.org/3.15/library/pdb.html)

### Match the error message to its reader

The command-line exercises run locally and show development details. An external API client needs a stable error outcome and enough information to correct the request. Developers may need the full traceback, exception cause and relevant source location in restricted diagnostic output.

| Audience | Example information |
| --- | --- |
| Person correcting a submitted JSON file | Invalid JSON with a line and column location |
| External client requesting an unavailable operation | A stable failure code and a request reference |
| Developer investigating a service failure | Traceback, exception chain and the associated request reference |

File paths, settings contents and credentials can appear in exception details. Choose public fields deliberately and keep detailed diagnostics under appropriate access. Chapter 33 develops structured logging and redaction. [OWASP error-handling guidance](https://cheatsheetseries.owasp.org/cheatsheets/Error_Handling_Cheat_Sheet.html)

## Worked answers

### Exercise 1

Opening failed before JSON parsing began. Inspect the process's working directory and the resolved requested path. Confirm the file and any required parent directories exist at that location.

### Exercise 2

An access refusal normally raises `PermissionError`, which can be reported as `Settings file is not readable`. The malformed readable document raises `json.JSONDecodeError`, which can be reported as `Settings contain invalid JSON` with the relevant position for its author.

### Exercise 3

The file is already closed when the handler prints `Parse failed`. The subsequent `finally` block observes `source.closed` as `True`. If opening had failed, no file object would have been assigned to `source`.

### Exercise 4

The newly created temporary file may contain an incomplete document. The function's `finally` removes it. Execution never reached `os.replace`, so the previous destination retains its original bytes. The demonstration checks both the destination and the remaining temporary paths.

### Exercise 5

The broad handler would also catch `NameError` from `soruce` and label it a JSON input problem. That message would direct the reader toward the wrong correction and hide the source-level failure. Narrow expected handlers let that unexpected bug propagate with its traceback.
