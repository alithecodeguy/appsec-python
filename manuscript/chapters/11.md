## 1. Follow one item through an iterator

An **iterable** can supply an iterator. An **iterator** keeps track of progress and supplies its next item when requested. Lists and tuples are iterable. A file object also supports iteration, supplying successive lines.

The built-in `iter` obtains an iterator. The built-in `next` requests one item. A `for` loop performs these steps for you and finishes when the iterator is exhausted.

**Listing L11-01. Consuming an iterator once**

Filename: `iterator_steps.py`.

```python
note_ids = [1, 2, 3]
cursor = iter(note_ids)

print(next(cursor))
print(list(cursor))
print(list(cursor))
print(next(cursor, "Finished"))
print(list(note_ids))
```

Predict which operation consumes more than one item. The expected output is the following.

```text
1
[2, 3]
[]
Finished
[1, 2, 3]
```

`list(cursor)` consumes all remaining items from that iterator. Once exhausted, it supplies no further items. `next(cursor, "Finished")` returns the chosen default at exhaustion. Without a default, `next` raises `StopIteration`.

The original list still contains all three identifiers. Iterating that list again obtains a fresh iterator. Passing an exhausted iterator to another operation continues from its exhausted position.

### A generator pauses at `yield`

A **generator function** contains `yield`. Calling it creates a generator iterator. Its body starts when the iterator is advanced. Each `yield` supplies a value and suspends execution, retaining the local state needed to resume afterward.

This is **lazy evaluation**: work is deferred until its result is requested. A generator can therefore produce records without first collecting the entire file into a list. Errors inside its body are also deferred until execution reaches them during consumption.

### Bound each read and yield one parsed object

**Listing L11-02. A generator over a text stream**

Filename: `note_streams.py`.

```python
import json


def read_note_records(source, *, max_line_chars=200, trace=False):
    if type(max_line_chars) is not int or max_line_chars < 1:
        raise ValueError("max_line_chars must be a positive integer")
    record_number = 0
    while True:
        line = source.readline(max_line_chars + 1)
        if line == "":
            return
        if len(line) > max_line_chars:
            raise ValueError("record line exceeds the character limit")
        record_number = record_number + 1
        if trace:
            print("Read record", record_number)
        record = json.loads(line)
        if not isinstance(record, dict):
            raise ValueError("each record must be a JSON object")
        yield record
```

`source` is an open text stream supplied by the caller. `.readline(size)` returns up to that many characters, ending earlier at a newline or end of file. The extra character lets the generator detect a line exceeding the budget. The limit includes a line ending when present.

An empty string signals end of file. A blank line containing a newline is still input, and JSON parsing rejects it under this fixture policy. An oversized line is rejected before parsing, so the program can stop instead of treating its remainder as another record.

The trace reports a logical record read before attempting its JSON parse. The generator checks that the result is an object. Further field and domain checks belong to the validators from chapters 08 and 10.

### Worked example 1. Request exactly three records

**Listing L11-03. Stepping through the generator by hand**

Filename: `three_steps.py`.

```python
from pathlib import Path

from note_streams import read_note_records

with Path("notes.jsonl").open("r", encoding="utf-8") as source:
    records = read_note_records(source, trace=True)
    print("Generator created")
    for step in range(1, 4):
        print("Request", step)
        note = next(records)
        print("Received", note["id"])

print("File closed", source.closed)
```

Write the expected ordering before running the file. Does creating `records` print a read message?

```text
Generator created
Request 1
Read record 1
Received 1
Request 2
Read record 2
Received 2
Request 3
Read record 3
Received 3
File closed True
```

**Table T11-01. The three requests and suspension points**

| Consumer action | Generator action | State after the action |
| --- | --- | --- |
| Call `read_note_records(...)` | Create the iterator; leave its body unexecuted. | No record requested from the stream. |
| First `next(records)` | Check the limit, read and parse record 1, then yield it. | Suspended at the first yield. |
| Second `next(records)` | Resume after yield, read and parse record 2, then yield it. | Suspended at the second yield. |
| Third `next(records)` | Resume after yield, read and parse record 3, then yield it. | Suspended at the third yield. |
| Leave the caller's `with` block | Close the file through its context manager. | File closed; abandon this iterator. |

The generator has not requested logical record four. Text-file buffering may fetch underlying bytes ahead of that position, so these observations describe logical reads and parsing. They do not measure individual operating-system disk requests.

The caller owns the file lifetime. Consume the iterator inside that lifetime and discard it afterward. Resuming it after the file closes would attempt a read through a closed stream. [Python's generator tutorial](https://docs.python.org/3.12/tutorial/classes.html#generators)

## 2. Limit, filter and batch consumption

`itertools.islice` selects a bounded section of an iterator. With a stop of three, it requests at most three items. If the input ends earlier, it stops normally. Unlike the three explicit `next` calls above, it handles a short input without an unhandled `StopIteration`.

A **generator expression** resembles a list comprehension with parentheses. It produces values lazily. `sum(1 for record in records)` counts items as they arrive without building a result list.

### Count without collecting the entire inventory

**Listing L11-04. A limited counting function**

Filename: `preview_counts.py`.

```python
from itertools import islice
from pathlib import Path

from note_streams import read_note_records


def count_records(path, *, limit=3):
    """Count at most limit JSON-line records."""
    if type(limit) is not int or limit < 0:
        raise ValueError("limit must be a nonnegative integer")
    with path.open("r", encoding="utf-8") as source:
        records = read_note_records(source)
        return sum(1 for record in islice(records, limit))


if __name__ == "__main__":
    print("Preview count", count_records(Path("notes.jsonl")))
```

The expected output is the following.

```text
Preview count 3
```

At most one parsed record is held for the count at a time. The reader also bounds the size of each decoded line. The function opens and closes its file for each call. A zero limit still opens the file, but requests no records. An empty readable file produces zero.

`count_records` is a preview count under its supplied limit. To count a larger known inventory, choose a corresponding limit. A successful preview establishes nothing about records that were never parsed.

### Put the limit at the intended boundary

Filtering before a limit can change how much input is consumed. To find three Alpha notes in our fixture, Python must read through note five.

**Listing L11-05. Limiting selected results or limiting input reads**

Filename: `filter_limits.py`.

```python
from itertools import islice
from pathlib import Path

from note_streams import read_note_records

print("Limit selected results")
with Path("notes.jsonl").open("r", encoding="utf-8") as source:
    records = read_note_records(source, trace=True)
    selected_ids = (
        note["id"] for note in records if note["workspace"] == "Alpha"
    )
    print(list(islice(selected_ids, 3)))

print("Limit input records")
with Path("notes.jsonl").open("r", encoding="utf-8") as source:
    records = read_note_records(source, trace=True)
    selected_ids = (
        note["id"]
        for note in islice(records, 3)
        if note["workspace"] == "Alpha"
    )
    print(list(selected_ids))
```

The expected output is the following.

```text
Limit selected results
Read record 1
Read record 2
Read record 3
Read record 4
Read record 5
[1, 3, 5]
Limit input records
Read record 1
Read record 2
Read record 3
[1, 3]
```

Both results are correct for their respective contracts. The first limits matches returned. The second limits records examined. State which budget your operation promises before placing the limit.

The same issue occurs with an early `break`. A `for` loop obtains its next item before entering the body. Checking an iteration counter inside the body can therefore discover the limit only after one extra record was read. `islice(records, 3)` expresses the consumption boundary directly.

### Batch only the permitted input

`itertools.batched` groups an iterator's items into tuples. Its final batch can be shorter than the requested batch size. Put the input limit before batching when you need a record budget.

**Listing L11-06. Three records in batches of two**

Filename: `preview_batches.py`.

```python
from itertools import batched, islice
from pathlib import Path

from note_streams import read_note_records

with Path("notes.jsonl").open("r", encoding="utf-8") as source:
    records = read_note_records(source)
    for batch in batched(islice(records, 3), 2):
        print([note["id"] for note in batch])
```

The expected output is the following.

```text
[1, 2]
[3]
```

Limiting the number of batches instead would establish a different budget. Two batches of two can request four records. Batching also retains a batch in memory, so its size belongs in the resource calculation. [Iterator tools](https://docs.python.org/3.12/library/itertools.html) · [Generator expressions](https://docs.python.org/3.12/reference/expressions.html#generator-expressions)

## 3. Wrap a function while preserving its identity information

Python functions are **first-class values**. You can assign them to names, pass them as arguments and return them from other functions. `operation = count_records` stores a reference to a function. Adding parentheses, as in `count_records(path)`, calls it and produces its result instead.

A **wrapper** is a function that calls another function while adding behavior around the call. A **closure** lets an inner function retain access to names from its enclosing function after that enclosing call has returned.

### Worked example 2. Measure duration without recording arguments

The wrapper below retains the supplied function in its closure. It records only the function's name and elapsed seconds. The file path, note data and other argument values stay out of the timing message.

**Listing L11-07. A timing decorator with preserved metadata**

Filename: `timing.py`.

```python
from functools import wraps
from time import perf_counter


def timed(function):
    @wraps(function)
    def wrapper(*args, **kwargs):
        started = perf_counter()
        try:
            return function(*args, **kwargs)
        finally:
            elapsed = perf_counter() - started
            print(f"{function.__name__} duration_seconds={elapsed:.6f}")

    return wrapper
```

`*args` collects positional arguments into a tuple. `**kwargs` collects keyword arguments into a dictionary. In `function(*args, **kwargs)`, the stars unpack those collections to forward the call. The wrapped function still applies its own argument rules.

`perf_counter` supplies a monotonic performance counter suitable for measuring elapsed time. Subtract the starting reading from the ending reading. The absolute counter value is not a wall-clock timestamp. The `.6f` formatting displays seconds with six digits after the decimal point.

`finally` records the duration on ordinary success or exception unwinding. The returned value comes from the wrapped function, and its exception propagates if it fails. This teaching observer uses `print`; if writing that diagnostic itself fails, that failure can also propagate. A service telemetry implementation needs an explicit policy for observer failures, developed with logging later in the book.

`@wraps(function)` copies useful metadata, including `__name__` and `__doc__`, onto the wrapper. It also sets `__wrapped__` to the original callable. It preserves identifying information while the wrapper remains a different function object. [Function wrapping](https://docs.python.org/3.12/library/functools.html#functools.wraps) · [Performance counter](https://docs.python.org/3.12/library/time.html#time.perf_counter)

### Verify the original name after wrapping

**Listing L11-08. Timing the consuming function**

Filename: `timed_preview.py`.

```python
from pathlib import Path

from preview_counts import count_records
from timing import timed

timed_count = timed(count_records)
result = timed_count(Path("notes.jsonl"), limit=3)

print("Count", result)
print("Name", timed_count.__name__)
print("Name preserved", timed_count.__name__ == count_records.__name__)
print("Original linked", timed_count.__wrapped__ is count_records)
print("Doc preserved", timed_count.__doc__ == count_records.__doc__)
```

A sample output is shown below. The duration is illustrative and varies between runs. The remaining lines should match exactly.

```text
count_records duration_seconds=0.000123
Count 3
Name count_records
Name preserved True
Original linked True
Doc preserved True
```

The wrapper measures the full call to `count_records`, including file reading, parsing and normal closure. Timing `read_note_records(...)` itself would measure generator creation. That call returns before its body reads a record. Choose the operation that actually consumes the stream when measuring that work.

### Recognize decorator syntax

Writing `@timed` directly above a function definition applies the wrapper when the definition executes. It corresponds to binding the function name to `timed(original_function)`. The wrapper's body still waits for a call.

You can use that syntax in `preview_counts.py` by importing `timed` and placing `@timed` immediately above its `def count_records(...)` line. Keep the explicit wrapping in `timed_preview.py` for this chapter's original metadata comparison. Choose one timing layer for a run so the observation appears once.

The decorator here targets ordinary synchronous functions. Iterating a generator or awaiting a coroutine happens at a different execution boundary. Chapter 28 will examine concurrent and asynchronous work.

## 4. Match the tool to the responsibility

An ordinary function describes an operation. A wrapper adds behavior around calls to an operation. A context manager owns entry, exit and cleanup for a block.

| Need | Suitable tool in this chapter |
| --- | --- |
| Parse one stream into successive records | Generator function |
| Count up to a supplied record limit | Ordinary consuming function |
| Measure one complete counting call | Timing wrapper |
| Keep a file open only during consumption | Context manager |

### Give a stream a managed lifetime

`contextlib.contextmanager` lets a generator define a context manager. Such a generator yields exactly once during a successful entry. Its yielded value becomes the name after `as`; resuming it performs the remaining exit work.

**Listing L11-09. A context-managed record stream**

Filename: `managed_notes.py`.

```python
from contextlib import contextmanager
from itertools import islice
from pathlib import Path

from note_streams import read_note_records


@contextmanager
def note_stream(path):
    with path.open("r", encoding="utf-8") as source:
        yield read_note_records(source)


if __name__ == "__main__":
    with note_stream(Path("notes.jsonl")) as records:
        for note in islice(records, 3):
            print(note["id"])
```

The expected output is the following.

```text
1
2
3
```

The outer `note_stream` generator yields one value: the record iterator. That inner iterator can yield many records. When the consumer's block exits early or with an exception, the context manager unwinds through the file's `with` block and closes it.

Keep consuming inside the managed block. Saving the iterator and using it after the block would outlive its file. This interface makes that lifetime visible at the call site. [Context-manager generators](https://docs.python.org/3.12/library/contextlib.html#contextlib.contextmanager)

### State each budget separately

The preview limits logical records consumed to three. The reader limits each decoded line to 200 code points, including a newline when present. The batching example adds a two-record batch. Those are different budgets.

A streaming implementation can still retain too much state by appending every result to a list, using an unbounded cache or collecting unlimited diagnostic events. Follow retained values as well as loop counts. Duration measurement observes elapsed time; it does not impose a timeout.

## Worked answers

### Exercise 1

The `ValueError` is raised on the first advancement, when execution enters the generator body. Creation alone runs none of those checks. A `try` block around the consuming loop or count catches that deferred failure.

### Exercise 2

The loop has requested four records, for indexes zero through three. Its body then decides to break. `islice(records, 3)` limits requests to three before the consumer enters its body for any fourth item.

### Exercise 3

The first expression produces batches containing identifiers `(1, 2)` and `(3,)`, consuming three records. The second produces `(1, 2)` and `(3, 4)`, consuming four. Limiting batch count establishes a different boundary from limiting source record count.

### Exercise 4

The measurement includes iterator creation and wrapper overhead around that call. Parsing happens later as the iterator advances. Time the consuming `count_records` operation to include the reads, parsing and file closure for its preview.

### Exercise 5

`functools.wraps` preserves the name and documentation, and `__wrapped__` points to the original callable. If JSON parsing raises, the timer's `finally` emits its duration and the original exception propagates. The timing message reports duration, with no claim that the operation succeeded.

## Glossary

| Term | Meaning in this chapter |
| --- | --- |
| Batch | A bounded group of items processed together |
| Closure | An inner function retaining access to names from its enclosing function |
| Decorator | A callable applied to a function or class definition to produce the bound result |
| Exhaustion | The state in which an iterator has no further items |
| First-class function | A function usable as a value, argument or result |
| Generator | An iterator whose function body can suspend at `yield` |
| Generator expression | A compact expression producing values lazily |
| Iterable | A value that can provide an iterator |
