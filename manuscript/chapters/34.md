Ten requests were denied. Is that unusual? Mina's export has not arrived. Is the worker slow, is permission being enforced, or has the evidence needed to answer the question stopped arriving?

By the end of this chapter, you will be able to calculate a denial fraction with the right denominator, follow an export request into its queue evidence and write a decision that names an owner and a next check. A number becomes useful when you can say what it counts, when it was collected and which action it supports.

You need chapter 8's JSON records, chapter 12's test assertions, chapter 28's bounded export queue and chapter 33's correlation and required-audit policy. Chapter 33 showed a service acceptance followed by a worker denial. It also showed that a failed required audit write can roll back the worker transaction and leave the request `queued`. We will distinguish those outcomes from an ordinary short wait.

The edition targets **CPython 3.12.14** and **Django 6.1.3**. The complete offline listings here ran with **CPython 3.12.14** and its standard library. No Django, metrics server, tracing SDK, broker or live deployment is needed. The dashboard export is **authored synthetic evidence**, not captured production telemetry. Executing its analyzer checks our calculations and routing rules; it does not establish that a running service emits these observations.

Keep the Casebook rule in view: Mina is an active member of Alpha, Ravi belongs to Beta and Lee manages Alpha only. An export checks current permission before releasing private data. Monitoring a delay never grants permission, extends the export deadline or permits skipping a required audit record.

Under that policy, Mina's current permitted Alpha read should succeed. Ravi's attempt to read the same Alpha note should be denied. If Lee revokes Mina's membership after admission, her later export should also be denied. A denial counter cannot distinguish those correct refusals from an incorrect refusal of an authorized reader without further evidence.

## 1. Logs, metrics, traces and the question each answers

### Start with a question

A **log event** describes an occurrence. A **metric** summarizes a measurement over time. A **trace** connects timed operations that participate in one piece of work. These forms of evidence help answer different questions.

**Table T34-01. Select evidence for the question**

| Question | Useful evidence | What it cannot establish alone |
| --- | --- | --- |
| How many HTTP authorization denials occurred in ten minutes? | A counter increase and matching completed-request count | Which private object was requested, or whether a denial was correct |
| Why did this export stop? | Its accepted event, trusted request row, worker attempt and committed outcome | The rate across all traffic |
| Where was elapsed time spent? | Service/worker spans or equivalent timestamped stage observations | Complete coverage if spans are missing or sampled |
| Is queued work accumulating? | Queue depth, age, progress and observation freshness | Whether this particular queued job is authorized |
| Did the required denial record commit? | Local audit outbox row joined to the request and outcome | Whether an external collector has acknowledged it |
| Can Mina download the result now? | The release path's current permission and expiry checks | A historical acceptance or a green dashboard is insufficient |

Suppose the service committed an accepted event at `09:00:00Z`. A worker attempt at `09:00:44Z` encountered a required-audit insertion failure. There is no committed worker outcome. A collector search for `export.process` may return nothing. That absence does not tell us whether the worker was never called, the transaction rolled back, the collector is late or our query used the wrong identifier.

Chapter 33 deliberately separated local recording from remote delivery. The locally committed event can exist while the collector is unavailable. Look at the local outbox's pending/parked state and delivery attempts before treating a missing central record as a missing business action.

### Three identifiers with three jobs

The numeric `request_id` returned by chapter 33's response adapter identifies an export request in the application database. The event's `correlation_id` links service and worker observations. Its `event_id` identifies one event and supports delivery deduplication. A worker event's `causation_event_id` can identify its service cause.

An operator starts with the numeric receipt, such as `request_id=1`, in a known Casebook deployment. The operator then finds its trusted correlation context. The value `1` is not globally unique across deployments or database restores. Scope the investigation to the right environment before joining records.

Do not infer identity from a line that merely contains the same number. Join the receipt to `export_requests.id`, then to the persisted audit context's request ID, service event ID and correlation ID. If those references disagree, stop the join and investigate the evidence error.

A correlation ID is also not an authorization credential. A person who knows it does not acquire access to Alpha. Keep the investigation interface restricted. The fixture below uses repeated hexadecimal characters to make identities easy to read. Real server-generated IDs should use the established generator; do not replace it with these teaching constants.

OpenTelemetry describes a trace as related spans with timing and context. A span represents an operation, such as accepting a request or processing a queued job. Our audit correlation string has a convenient length, but length alone does not make it an OpenTelemetry trace ID or provide parent/span semantics. This chapter uses a **manual evidence trace**, without claiming SDK or wire-format conformance. See the [OpenTelemetry trace concepts](https://opentelemetry.io/docs/concepts/signals/traces/).

If tracing is later added, propagate trusted context through the queued message or stored job context. Record producer/consumer relationships appropriate to the worker model. Keep queue waiting time separate from active processing time. A service can respond with `202` in 50 milliseconds while the job waits 45 seconds. Measuring only the HTTP handler would miss the user's delay.

Diagnostic spans may be sampled. Required audit facts from chapter 33 are not discarded because a trace was not sampled. Do not estimate an exact authorization-denial fraction from whichever sampled spans happen to reach a dashboard.

## 2. Counters, rates, percentiles, denominators and label cardinality

### Define the counted population first

Our synthetic HTTP metric counts **completed attempts to `POST /exports` in one region during one 600-second window**. An attempt includes a retry that reaches this boundary. A final HTTP response classified internally as an authorization refusal contributes one denial. The same refusal may have a public `403` or a deliberately generic `404`; classify it from the controlled application outcome, not every `404` on the site.

A `202` admission is a completed HTTP attempt, but it is not a completed export. A worker denial after that admission belongs to a separate worker-outcome population. Queue-full responses, audit-store unavailability and malformed input also need distinct classifications. Adding worker denials to HTTP denials would mix different boundaries and could count one user interaction twice.

Before dividing, write down the numerator, denominator, interval and scope. Prometheus's [instrumentation guidance](https://prometheus.io/docs/practices/instrumentation/) recommends pairing failures with attempts and counting at a consistent boundary. Our route, interval and outcome contract are authored choices for this exercise.

### Worked example 1: the same ten denials

Predict the answer before calculating: which row has the larger denial percentage? Which has the larger number of denials per second?

For a window containing `D` denials and `N` completed requests:

```text
denial fraction = D / N                 when N > 0
denial percentage = 100 × D / N
denials per second = D / window_seconds
```

**Table T34-02. Exact counts in two synthetic 600-second windows**

| Window | Denials D | Completed requests N | Denial percentage | Denials/second |
| --- | ---: | ---: | ---: | ---: |
| Quiet | 10 | 20 | 50% | 10 / 600 = about 0.0167 |
| Busy | 10 | 10,000 | 0.1% | 10 / 600 = about 0.0167 |

The quiet fraction is `0.5`; the busy fraction is `0.001`. The quiet percentage is 500 times the busy percentage. Their denial arrival rates are equal because both contain ten denials in the same interval. The overall request rates differ: about `0.0333` and `16.6667` completed requests per second.

The word **rate** can mean an event arrival rate or a proportion. Name the unit in a chart: `denials/second` and `denial percent` answer different questions.

Ten denials among twenty attempts deserve inspection. The small sample makes the percentage sensitive to a few retries, a training exercise or one misconfigured client. Ten denials among ten thousand attempts may fit a baseline. Neither calculation establishes whether an attacker tried to cross a tenant boundary or whether an authorized user was incorrectly denied.

For `N=0, D=0`, the fraction is **undefined**. Display no traffic or no observations, according to the collection evidence. Do not replace it with `0%`. For `N=0, D=1`, the inputs cannot describe the same completed-request population. Investigate incompatible filters, windows or duplicate accounting rather than manufacturing a percentage.

### Counters and gauges

A **counter** accumulates occurrences. A **gauge** reports a current value that can rise or fall, such as queued jobs. Our dashboard's window counts have already been calculated from a complete, unsampled training ledger. They are not cumulative counter samples.

If a cumulative denial counter moves from `100` to `110` within one uninterrupted series, its increase is ten. If a process restarts and the counter moves from `100` to `3`, subtracting gives a misleading negative result. Even an endpoint increase can hide a restart: `1` before restart and `10` afterward does not establish nine new events during the interval.

The listing's `counter_delta` accepts only an unchanged counter epoch and a nondecreasing value. An epoch identifies the continuous counter lifetime in this exercise. It refuses intervals it cannot reconstruct. A real metrics backend needs its documented reset handling and sufficient intermediate samples; this two-point helper is deliberately more limited.

Do not sum cumulative counter values from successive scrapes. Do not subtract a queue gauge to estimate completed jobs: admissions and completions can happen between observations. Report queue depth together with last progress and job age.

### Percentiles describe a distribution

A **percentile** is a position in ordered observations. With the nearest-rank method used in our listing, the p95 is the value at rank `ceil(0.95 × N)`, counting ranks from one. Different systems may use different interpolation or histogram approximations; record the method.

Predict the p95 and p99 of twenty synthetic durations: nineteen are one second and one is ten seconds. The mean is `29 / 20 = 1.45` seconds. The p95 is one second, because its rank is nineteen. The p99 is ten seconds, because its rank is twenty. An acceptable p95 can coexist with a delayed request. For small samples, tail percentiles are especially coarse.

Do not average per-host percentiles to obtain a service percentile. Suppose host A has one hundred observations at `0.1` seconds, and host B has one at ten seconds. The average of their p95 values is `5.05` seconds, while the combined nearest-rank p95 is `0.1` seconds. Aggregate compatible distribution observations or histogram buckets before estimating a service quantile. Prometheus explains these aggregation and estimation distinctions in its [histograms and summaries guidance](https://prometheus.io/docs/practices/histograms/).

Always give a latency chart's population. A histogram of **finished** exports excludes work still waiting. During a stall, that chart can look healthy because only quick jobs finish. Pair it with queue depth, oldest queued age, expiry count and source freshness. Measure elapsed durations inside one process with a monotonic clock; wall-clock UTC timestamps across hosts require clock synchronization and an uncertainty bound.

### Keep labels bounded

**Label cardinality** is the number of distinct label combinations represented by a metric. Request IDs create a new value for almost every request. A route template such as `/notes/{id}` has bounded choices; a raw URL with query text does not.

**Table T34-03. Proposed measurements; these are not installed collectors**

| Measurement | Boundary or meaning | Suitable bounded labels |
| --- | --- | --- |
| HTTP completed-attempt counter | One increment at final response | Route template, method, controlled outcome, region |
| Worker committed-outcome counter | One increment for a new committed terminal job outcome | Controlled outcome and worker role |
| Worker attempt counter | Includes retries; distinct from committed outcomes | Controlled attempt result |
| Queue depth and oldest queued age | Snapshot of trusted queue state | Queue name and region |
| Audit undelivered and parked counts | Local outbox health, including retained failures | Outbox name and region |
| End-to-end export duration distribution | Explicitly defined admission-to-terminal boundary | Controlled terminal outcome |

Keep numeric request IDs and correlation IDs in restricted event/trace lookup fields, rather than ordinary metric labels. Do not label metrics with note titles, bodies, tokens, email addresses or raw client keys. With two routes, four outcomes and two regions, there are at most sixteen combinations before other dimensions. Adding ten thousand request IDs can expand that space to 160,000 combinations for one period and keep growing. Bounded controlled labels reduce both resource cost and accidental exposure.

Retries need deliberate counting. Replaying an already committed audit event does not create another business outcome. Counting collector deliveries would inflate outcomes after a lost acknowledgement. An in-process metric increment can also be lost around a crash; if exact durable business counts are required, define a deduplicated source and reconciliation procedure. The complete fixture counts avoid this delivery problem; the chapter does not implement production exactly-once metric increments.

## 3. Baselines, alert thresholds, quiet traffic and false alarms

A **baseline** is a comparison drawn from relevant past behavior. The fixture includes an authored baseline denial percentage of `0.2%`. Imagine that it summarizes comparable weekday windows for this route and region. It is training context, not a measured history or a universal security threshold.

Ask whether the comparison still fits. A new access policy, a changed client retry behavior, a release, scheduled training or a traffic shift can change the expected population. Keep the definition stable when comparing windows. A whole-site baseline may conceal trouble on one sensitive operation. A global percentage can dilute a small targeted attempt.

The busy row's `0.1%` is below this fictional baseline. That supports a lower-priority aggregate review, not a statement that the system is safe. The quiet row's `50%` is above it, but has only twenty attempts. Check the controlled outcomes and whether the denials came from expected activity. Avoid exposing identifiers in broad dashboards merely to split the data more finely.

### A deliberately small alert policy

An **alert** requests attention. A **page** interrupts an on-call owner for an urgent action. A review item can wait for the agreed response period. Give each an owner and an actionable next step.

**Table T34-04. Authored training rules and their owners**

| Signal | Decision | Reason and owner |
| --- | --- | --- |
| Credible evidence of unauthorized release | Immediate security and application escalation | Containment cannot wait for a minimum traffic sample |
| HTTP denominator is zero | Report undefined fraction; verify traffic and telemetry | Application/observability owner checks whether the absence is real |
| HTTP window has fewer than 100 completed attempts | Review low-volume evidence; no automatic ratio page | A few attempts can dominate the proportion |
| HTTP denials are at least 2% in two consecutive eligible 600-second windows | Route a security review | AppSec and application owner classify causes and impact |
| HTTP denials are at least 2% in only one eligible window | Inspect the next window and current event evidence | Persistence is unconfirmed |
| Queued export is under 30 seconds old with fresh evidence and a healthy heartbeat | Watch and recheck | Worker owner has time within the 60-second deadline |
| At least 30 seconds old, recent matching audit failure, full required buffer | Page application owner; engage audit delivery/storage owner | Worker liveness cannot overcome the required recording boundary |
| At least 30 seconds old with missing/stale sources | Page application owner to restore evidence and triage the delay | The request is approaching expiry and cannot be cleared |
| At least 30 seconds old with worker inactivity | Page worker owner | Progress or liveness evidence is insufficient |
| At most 10 seconds remain before expiry | Page application owner | Little time remains even if other jobs are progressing |
| Deadline has elapsed | Enforce no release; page application owner for expiry handling | Waiting does not renew the original intent |

The ratio path checks no traffic and minimum volume before persistence. For a queued fixture, the code checks identity and contract first, then expiry, evidence completeness and state consistency, then a near deadline, an audit blockage and worker progress. Direct evidence of unauthorized release uses the incident path outside this helper. The table describes the response policy; the listing makes overlapping queued conditions deterministic.

For the ratio rules, **eligible** means a complete, correctly scoped window with at least 100 completed attempts. `consecutive_high_windows` in the supplied export is an authored upstream result over successive, nonoverlapping windows using that same definition. It does not mean two refreshes of the same rolling chart. The analyzer consumes that value; it does not reconstruct earlier windows or verify the supplied baseline.

These rules are intentionally easy to inspect. A real policy needs agreement on impact, response times and acceptable notification load. Google's [SRE workbook discussion of alerting](https://sre.google/workbook/alerting-on-slos/) explains the tradeoffs among significant user impact, detection speed and noisy low-traffic alerts. Our denial threshold is a security-review heuristic, not an availability service-level objective. A correctly refused cross-workspace request is not automatically an availability error.

### Quiet traffic and false reassurance

A **false alarm** asks for action when the apparent condition does not justify it. A misaligned denominator can produce one. A **miss** fails to call attention to a consequential condition. Requiring a large traffic sample can create one for targeted attacks.

Use the sample minimum only on the aggregate rule. A reproducible cross-tenant disclosure, a secret appearing in telemetry or a stored result contradicting the expected transaction state needs direct investigation regardless of volume. A minimum of 100 requests must never become permission to ignore a concrete report from one user.

Separate no traffic from no data. A fresh zero count can reflect an idle service. An absent or stale scrape can reflect a failed exporter, permissions, network trouble or a stalled collector. Pair the traffic series with scrape/collection health and an independent synthetic request or access observation if that is part of the deployment. Do not send a real private note through a health probe.

Repeat notifications need coordination. Group the application and audit symptoms under one incident or investigation owner when they share evidence. Keep the underlying conditions visible. Silencing a duplicate page is different from marking the condition resolved. Record who will recheck it and when.

## 4. Runbooks, ownership and evidence that justifies escalation

A **runbook** is a short procedure for a known operational question. It names the evidence to collect, the permitted actions, the owner and the condition for stopping or escalating. It should work when the person reading it did not write the queue.

### Worked example 2: request 1 is still queued

The supplied export contains three independent scenarios. Each uses an isolated database where the export's numeric ID happens to be `1`. Do not join the scenarios together. For the blocked scenario, the trusted context maps request `1` to correlation ID `bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb` and service event ID `11111111111111111111111111111111`.

Predict the decision before looking at the table: does a heartbeat one second ago prove that this export is making progress?

**Table T34-05. Blocked request timeline and current snapshots**

| UTC time | Evidence | Interpretation |
| --- | --- | --- |
| `09:00:00Z` | Accepted service event, object ID `1`, matching persisted context | Admission committed; the export has not completed |
| `09:00:02Z` | Last committed worker progress in this worker scope | Other work progressed early in the interval |
| `09:00:44Z` | Fresh heartbeat and a matching attempt classified `deferred_required_audit` | Worker is alive; this attempt could not commit required recording |
| `09:00:45Z` | Request `1` is `queued`; global queue depth `2/2` | The admission capacity is occupied |
| `09:00:45Z` | Audit undelivered `4/4`, parked `0` | The required local buffer is full |
| `09:00:45Z` | Zero slots, encrypted exports and nonce reservations | No result committed in this isolated snapshot |
| `09:01:00Z` | Stored request deadline | There are 15 seconds left at the observation time |

The strongest conclusion is operational: **page the application owner now and engage the audit delivery/storage owner**. The matching attempt and full buffer support a required-recording blockage. The evidence does not show an unauthorized release or prove the underlying collector/storage fault. A disk problem or transaction failure is still an alternative explanation for the failed write. Collect the bounded local failure classification, outbox delivery attempts and storage health next.

Do not clear the condition because the worker heartbeat is fresh. A heartbeat reports liveness, while the last committed transition and matching attempt describe progress. Do not increase retries without checking whether they can succeed. Do not drain the required buffer by deleting records, disabling its hook or marking undelivered records as sent.

If delivery can safely resume, the audit owner uses the bounded delivery procedure and inspects acknowledgements and retained state. The application owner then checks whether the original request still has time, current permission and a valid processing path. After expiry, the original request cannot be released; a new user action must create a new intent if appropriate. Chapter 28's idempotent retry keeps the original deadline, so reusing the same client key does not extend it.

Compare two boundaries:

**Table T34-06. Same symptom, different evidence**

| Scenario | Evidence at observation | Decision |
| --- | --- | --- |
| `fresh_wait` | Age 8 seconds, 52 seconds remaining, queue `2/2`, recent heartbeat/progress, no result, outbox `1/4` | Watch; collect another snapshot by age 18 seconds, and earlier if symptoms change |
| `audit_blocked` | Age 45 seconds, 15 seconds remaining, matching deferred attempt, full outbox | Page application owner now; audit owner investigates the recording/delivery path |
| `missing_worker` | Age 45 seconds, 15 seconds remaining, fresh database/queue/audit snapshots but no worker evidence | Page application owner now; recover dispatch/worker evidence rather than assuming a normal wait |

The first case can become urgent at its next observation. A `watch` is a timed decision, not a permanent suppression. Queue depth `2/2` already indicates no spare admission capacity. Check rejected admissions separately, and do not assume that another tenant's queued work is visible to Mina.

### Where these observations come from

Chapter 28's `export_requests` table stores `expires_at`, state and intent references. It does **not** store `accepted_at` or worker heartbeat fields. Chapter 33 adds the persisted audit context and accepted event. This exercise uses that event's occurrence time as the admission-time reference. Its fixture timestamps match the admission clock used for the 60-second expiry.

The JSON uses redacted projections rather than full chapter 33 event documents. `acceptance` contains just the join fields and time needed here; do not pass it to chapter 33's full event validator. `request.expires_at` is a UTC rendering of the stored epoch value, not a schema change. `result_counts` is an administrative inventory from the same isolated database snapshot as `request`; it is not a per-user API response. There are no committed result rows for any job in these small scenarios.

`worker`, including its attempt envelope, is an **additional authored supervisor observation**. Chapter 33's fixed diagnostic message alone does not supply a request-linked worker timeline. A deployment would need trusted dispatch context to attach an attempt to the request/correlation pair, plus timestamps, freshness checks and tests. `deferred_required_audit` is an attempt classification, not a committed audit outcome. A failed transaction cannot supply its own successfully committed denial event.

Likewise, queue depth, health refresh timestamps and worker progress must be exported by a real implementation. The original chapter 28 laboratory has no persistent scheduler or broker acknowledgement API. These fixtures do not add one. The analyzer never calls a worker, changes a row, acknowledges a message or releases a file.

### A short procedure an on-call reviewer can follow

1. Confirm environment, operation and impact. Obtain the numeric export receipt through a permitted support path. Record the UTC observation time. Ask whether the delay concerns admission, processing, download or central event visibility.
2. Join the receipt to the request and persisted context. Verify the accepted event's ID, object ID and correlation ID. A mismatched join is an evidence problem, not a healthy request.
3. Inspect current state and deadline. If a worker outcome already committed, distinguish `denied`, `expired`, `failed` and `ready`. A committed denial requires explanation of the permission decision; it does not require restarting the queue. A ready result still requires current release authorization.
4. If queued, compare age, remaining lifetime, queue capacity, heartbeat, last committed progress and the matching attempt. Check local required-audit health separately from collector visibility. Include each source's observation time.
5. Choose a decision and owner from the agreed policy. Record an alternative explanation and the specific next evidence that could distinguish it. Use a short follow-up time when the deadline is close.
6. Verify recovery from stored state. Inspect the final request state, result inventory, local audit outcome and delivery state. A restarted process or cleared chart alone does not show that the request completed correctly.

An operator must be allowed to inspect this evidence. Ordinary workspace users should not gain global queue inventory or another workspace's audit facts through an incident endpoint. Share a minimized triage note rather than a raw database dump.

There is no need to invent a root cause to escalate. State the supported blockage and the unanswered question. If later evidence shows unauthorized release, notify the security incident owner immediately and preserve the relevant redacted timeline. If it shows only an expected current-permission denial, explain that outcome and check whether the alert classified denials correctly.

### Calculate and classify

`denial_fraction` returns `None` when the denominator is zero. Its caller prints `undefined`; it does not coerce that result to zero. Counts reject negative values and booleans, even though Python treats `bool` as an integer subclass.

`assess_delay` first joins identities and checks the queued-request contract. It calculates age from the accepted event and remaining lifetime from the original deadline. Each source is allowed to be at most five seconds old in this exercise. Missing or older evidence cannot produce `watch`. A timestamp from the future is refused as a clock/order error. These five seconds are an authored tolerance, not a guarantee supplied by the timestamp format.

For a known queued fixture at its deadline, the no-release decision remains in force even if newer worker evidence is missing. The function's `deadline_elapsed_no_release` reason is a policy instruction; it is not a measurement proving that no disclosure occurred. Current stored state still needs verification.

The final branches distinguish a fresh short wait, a stalled worker, an old individual job despite other progress and a matching required-audit blockage. A result row in an otherwise queued/no-result fixture triggers joint application/security investigation. An unexpected encrypted row is an integrity concern; encryption or row existence alone does not prove plaintext release.

Filename: `examples/ch34/triage.py`.

```python
"""Offline calculations over the authored chapter 34 evidence contract."""
import argparse
import json
import math
import re
from dataclasses import dataclass
from datetime import datetime, timezone
from pathlib import Path


MIN_REQUESTS = 100
REVIEW_FRACTION = 0.02
MAX_SOURCE_AGE = 5
STALL_SECONDS = 30
URGENT_REMAINING = 10


def count(value):
    if type(value) is not int or value < 0:
        raise ValueError("invalid_count")
    return value


def counter_delta(start, end, *, start_epoch, end_epoch):
    count(start)
    count(end)
    if not start_epoch or start_epoch != end_epoch or end < start:
        raise ValueError("counter_interval_unusable")
    return end - start


def denial_fraction(denied, completed):
    count(denied)
    count(completed)
    if denied > completed:
        raise ValueError("incompatible_denominator")
    return None if completed == 0 else denied / completed


def assess_window(window):
    # Counts are exact completed-window totals, not sampled trace counts.
    fraction = denial_fraction(window["denied"], window["completed"])
    seconds = count(window["seconds"])
    if seconds == 0:
        raise ValueError("empty_interval")
    consecutive = count(window["consecutive_high_windows"])
    if fraction is None:
        decision = "no_traffic"
    elif window["completed"] < MIN_REQUESTS:
        decision = "low_volume_review"
    elif fraction >= REVIEW_FRACTION and consecutive >= 2:
        decision = "route_security_review"
    elif fraction >= REVIEW_FRACTION:
        decision = "inspect_next_window"
    else:
        decision = "within_training_threshold"
    return fraction, window["denied"] / seconds, decision


def nearest_rank(values, percentile):
    if not values or not 0 < percentile <= 100:
        raise ValueError("invalid_percentile_input")
    if any(type(v) not in (int, float) or not math.isfinite(v) or v < 0
           for v in values):
        raise ValueError("invalid_duration")
    ordered = sorted(values)
    return ordered[math.ceil(percentile / 100 * len(ordered)) - 1]


def instant(value):
    # Exercise timestamps deliberately require UTC and whole seconds.
    parsed = datetime.strptime(value, "%Y-%m-%dT%H:%M:%SZ")
    return parsed.replace(tzinfo=timezone.utc)


def elapsed(later, earlier):
    seconds = int((instant(later) - instant(earlier)).total_seconds())
    if seconds < 0:
        raise ValueError("clock_or_order_error")
    return seconds


@dataclass(frozen=True)
class DelayAssessment:
    decision: str
    age_seconds: int
    remaining_seconds: int
    reason: str


def assess_delay(case):
    now = case["observed_at"]
    receipt = case["receipt"]
    row = case["request"]
    context = case["context"]
    accepted = case["acceptance"]
    request_id = count(receipt["request_id"])
    correlation = context["correlation_id"]
    if (request_id == 0
            or row["id"] != request_id
            or context["request_id"] != request_id
            or accepted["object_id"] != request_id
            or accepted["event_id"] != context["service_event_id"]
            or accepted["correlation_id"] != correlation
            or re.fullmatch(r"[0-9a-f]{32}", correlation) is None
            or accepted["action"] != "export.request"
            or accepted["outcome"] != "accepted"):
        raise ValueError("identity_join_failed")
    age = elapsed(now, accepted["occurred_at"])
    lifetime = elapsed(row["expires_at"], accepted["occurred_at"])
    if lifetime != 60 or row["state"] != "queued":
        raise ValueError("outside_queued_fixture_contract")
    remaining = max(0, lifetime - age)

    def result(decision, reason):
        return DelayAssessment(decision, age, remaining, reason)

    # An expiry is not renewed merely because observation is incomplete.
    if remaining == 0:
        return result("page_application", "deadline_elapsed_no_release")

    sources = [row, case["queue"], case["audit"], case["worker"]]
    incomplete = any(source is None for source in sources)
    for source in sources:
        if source is not None:
            incomplete |= elapsed(now, source["observed_at"]) > MAX_SOURCE_AGE
    if incomplete:
        decision = "page_application" if age >= STALL_SECONDS else "collect_evidence"
        return result(decision, "missing_or_stale_source")

    queue, audit, worker = case["queue"], case["audit"], case["worker"]
    for value in (queue["queued"], queue["capacity"], audit["undelivered"],
                  audit["capacity"], audit["parked"]):
        count(value)
    if (queue["capacity"] != 2 or queue["queued"] > 2
            or audit["capacity"] != 4 or audit["parked"] > audit["undelivered"]):
        raise ValueError("incompatible_capacity_snapshot")
    if queue["queued"] == 0:
        raise ValueError("queued_row_missing_from_gauge")
    if set(case["result_counts"]) != {"slots", "encrypted_exports", "used_nonces"}:
        raise ValueError("incomplete_result_inventory")
    if any(count(n) for n in case["result_counts"].values()):
        return result("page_application_and_security", "unexpected_result_state")
    heartbeat_age = elapsed(now, worker["heartbeat_at"])
    progress_age = elapsed(now, worker["last_progress_at"])
    attempt = worker["attempt"]
    blocked = False
    if attempt is not None:
        if (attempt["request_id"] != request_id
                or attempt["correlation_id"] != correlation):
            raise ValueError("attempt_join_failed")
        attempt_age = elapsed(now, attempt["at"])
        blocked = (attempt["result"] == "deferred_required_audit"
                   and attempt_age <= MAX_SOURCE_AGE)
    if remaining <= URGENT_REMAINING:
        return result("page_application", "deadline_near")
    if age >= STALL_SECONDS and blocked and audit["undelivered"] >= audit["capacity"]:
        return result("page_application", "required_audit_blocked_buffer_full")
    if age >= STALL_SECONDS and (heartbeat_age > MAX_SOURCE_AGE
                                or progress_age >= STALL_SECONDS):
        return result("page_worker", "worker_stalled_or_unavailable")
    if age >= STALL_SECONDS:
        return result("investigate_application", "old_job_despite_worker_progress")
    if heartbeat_age > MAX_SOURCE_AGE:
        return result("collect_evidence", "heartbeat_old")
    return result("watch", "fresh_short_wait")


def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("export", type=Path)
    args = parser.parse_args()
    report = json.loads(args.export.read_text(encoding="utf-8"))
    if report["schema_version"] != 1 or report["synthetic"] is not True:
        raise ValueError("not_the_training_export")
    for window in report["windows"]:
        fraction, per_second, decision = assess_window(window)
        percent = "undefined" if fraction is None else f"{100 * fraction:.3f}%"
        print(f"{window['name']}: {window['denied']}/{window['completed']} "
              f"= {percent}; denied/s={per_second:.4f}; {decision}")
    for case in report["delays"]:
        result = assess_delay(case)
        print(f"{case['name']}: request={case['receipt']['request_id']}; "
              f"age={result.age_seconds}s; remaining={result.remaining_seconds}s; "
              f"{result.decision}; {result.reason}")


if __name__ == "__main__":
    main()
```

### Regression checks for decisions that could mislead a reviewer

The tests exercise meaningful boundaries: the same numerator with different denominators, zero traffic, minimum sample/persistence, counter restarts, tail durations, a fresh heartbeat with no committed progress, bad joins, stale/missing evidence and a deadline that does not move.

The tests also ensure that analysis does not mutate the blocked input. This read-only tool cannot repair queue state. Chapter 33's transaction tests remain the evidence for actual rollback; a synthetic snapshot saying zero results is not a new execution of those transactions.

```python
import json
import unittest
from pathlib import Path

from triage import (
    assess_delay, assess_window, counter_delta, denial_fraction, nearest_rank,
)


REPORT = json.loads(Path(__file__).with_name("dashboard.json").read_text())


class TriageTests(unittest.TestCase):
    def case(self, index=0):
        return copy.deepcopy(REPORT["delays"][index])

    def test_same_numerator_changes_fraction_not_denials_per_second(self):
        quiet = assess_window(REPORT["windows"][0])
        busy = assess_window(REPORT["windows"][1])
        self.assertEqual(quiet[0], 0.5)
        self.assertEqual(busy[0], 0.001)
        self.assertEqual(quiet[1], busy[1])
        self.assertEqual(quiet[2], "low_volume_review")
        self.assertEqual(busy[2], "within_training_threshold")

    def test_empty_denominator_is_not_zero_percent(self):
        self.assertIsNone(denial_fraction(0, 0))
        self.assertEqual(assess_window(REPORT["windows"][2])[2], "no_traffic")
        for denied, completed in [(1, 0), (21, 20), (-1, 10), (True, 10)]:
            with self.subTest(denied=denied, completed=completed):
                with self.assertRaises(ValueError):
                    denial_fraction(denied, completed)

    def test_review_requires_volume_and_persistence(self):
        window = dict(REPORT["windows"][3])
        self.assertEqual(assess_window(window)[2], "route_security_review")
        window["consecutive_high_windows"] = 1
        self.assertEqual(assess_window(window)[2], "inspect_next_window")
        window.update(completed=99, denied=99, consecutive_high_windows=2)
        self.assertEqual(assess_window(window)[2], "low_volume_review")
        window.update(completed=100, denied=2)
        self.assertEqual(assess_window(window)[2], "route_security_review")

        with self.assertRaises(ValueError):
            assess_window(window)

    def test_reset_and_restart_are_not_valid_counter_deltas(self):
        self.assertEqual(counter_delta(100, 110, start_epoch="a", end_epoch="a"), 10)
        for start, end, epoch in [(100, 3, "a"), (1, 10, "b")]:

                counter_delta(start, end, start_epoch="a", end_epoch=epoch)

    def test_quantiles_expose_tail_and_do_not_average_across_hosts(self):

        self.assertEqual(nearest_rank(values, 95), 1)
        self.assertEqual(nearest_rank(values, 99), 10)
        self.assertEqual(nearest_rank([0.1] * 100 + [10], 95), 0.1)
        with self.assertRaises(ValueError):
            nearest_rank([float("nan")], 95)

    def test_fresh_wait_has_time_and_no_artifact(self):

        self.assertEqual((result.decision, result.age_seconds,

    def test_fresh_heartbeat_does_not_clear_blocked_audit_write(self):
        case = self.case(1)
        result = assess_delay(case)
        self.assertEqual(result.decision, "page_application")
        self.assertEqual(result.reason, "required_audit_blocked_buffer_full")
        self.assertEqual(result.remaining_seconds, 15)
        self.assertEqual(case, REPORT["delays"][1])  # Analysis changes no stored state.

    def test_missing_and_stale_sources_cannot_clear_a_delay(self):
        self.assertEqual(assess_delay(self.case(2)).reason, "missing_or_stale_source")
        case = self.case(1)
        case["audit"]["observed_at"] = "2026-11-26T09:00:30Z"
        self.assertEqual(assess_delay(case).reason, "missing_or_stale_source")
        case = self.case()
        case["worker"] = None
        self.assertEqual(assess_delay(case).decision, "collect_evidence")

    def test_identity_mismatch_is_refused(self):
        for target, field, value in [("request", "id", 2),
                                      ("acceptance", "object_id", 2),
                                      ("acceptance", "correlation_id", "d" * 32),
                                      ("context", "service_event_id", "9" * 32)]:
            case = self.case()
            case[target][field] = value
            with self.subTest(target=target, field=field):
                with self.assertRaisesRegex(ValueError, "identity_join_failed"):
                    assess_delay(case)
        case = self.case(1)
        case["worker"]["attempt"]["request_id"] = 2
        with self.assertRaisesRegex(ValueError, "attempt_join_failed"):
            assess_delay(case)

    def test_inactive_worker_routes_to_worker_owner(self):
        case = self.case(1)
        case["audit"]["undelivered"] = 1
        case["worker"]["attempt"] = None
        self.assertEqual(assess_delay(case).decision, "page_worker")

    def test_recent_other_progress_still_requires_old_job_investigation(self):
        case = self.case(1)
        case["worker"]["attempt"] = None
        case["worker"]["last_progress_at"] = "2026-11-26T09:00:44Z"

    def test_deadline_is_not_extended_by_missing_telemetry(self):
```

## Hints and worked answers

### Guided lab answers

Ten divided by twenty is `0.5`, or `50%`. Ten divided by ten thousand is `0.001`, or `0.1%`. Both windows last 600 seconds, so both denial arrival rates are `10 / 600`, about `0.0167/s`. The denominator changes the proportion, while the interval controls the arrival-rate calculation.

For the blocked job, `09:00:45Z - 09:00:00Z = 45` seconds of age. The stored deadline minus the observation time is fifteen seconds. Its heartbeat is one second old, but the last committed progress is forty-three seconds old. The matching attempt is recent and the required local buffer is full. That combination supports paging the application owner and involving the audit owner before the deadline. It does not justify claiming a cross-tenant disclosure.

Changing object ID to `2` breaks the identity relationship. The helper refuses the join rather than calculating a credible-looking decision from mixed requests. With a missing worker at age eight seconds, collect fresh evidence within the short recheck interval. With that evidence still missing at forty-five seconds, the original deadline is near enough that a named owner must act now.

### Independent practice answers

**1. Practice window.** `80 / 2000 = 0.04`, or `4%`. The denial arrival rate is `80 / 600`, about `0.1333/s`. The sample has at least one hundred completed attempts, and the supplied persistence value says there are two successive eligible high windows. The rule returns `route_security_review`. This is twenty times the authored `0.2%` baseline, but that comparison alone does not show why users were denied. The analyzer has not fetched or verified the previous window.

A completed note could say:

> In the synthetic `POST /exports` window, 80 of 2,000 completed attempts were authorization denials: 4%, or about 0.1333 denials/second. The supplied report marks two consecutive eligible high windows, so route a review to AppSec and the application owner. No unauthorized release is demonstrated. One alternative is a client retaining stale workspace membership and retrying after revocation. Next collect a restricted, deduplicated sample of controlled denial reasons and release/client-version context, and verify the prior window's scope and counters. Do not add request IDs or private note content to metric labels.

This note identifies the evidence, decision and uncertainty. The review queue must have an agreed response time. If direct evidence shows unauthorized release while the review is pending, use the immediate incident path rather than waiting for another aggregate window.

**2. Eighty of eighty.** The percentage becomes `100%`. The arrival rate remains about `0.1333/s` if the interval remains 600 seconds. The minimum-volume rule returns `low_volume_review`, because eighty is below one hundred. That affects only the automatic ratio heuristic. A reproducible unauthorized read by Ravi of an Alpha note would justify immediate security escalation even if it were the only request all day.

**3. Worker and individual-job paths.** With no recent audit-blocked attempt and last progress still at `:02`, the forty-five-second-old request returns `page_worker`. A fresh heartbeat alone does not show progress. Moving last progress to `:44` returns `investigate_application`: other work is progressing, but this old job still needs a request-specific explanation. Fifteen seconds remain. Inspect dispatch/claim/retry evidence for this request now and recheck by `:50`, when the ten-second remaining-time rule would page even with other progress.

**4. Collector absence after a committed denial.** First join the local outcome's event ID, correlation ID, request ID and causation reference. Then inspect that outbox row's pending/parked state, delivery attempts and next attempt time, and search the collector by the exact event ID within its permitted scope. An already denied request is not unfinished simply because central delivery lags. Current permission controls release, and a collector delay cannot change a denial into an allowance. If the required local event itself is absent, investigate a different invariant failure rather than assuming this delivery explanation.

**5. Labels and remaining uncertainty.** A controlled route template or outcome is a suitable bounded label. A correlation ID is a useful restricted lookup field. Neither an aggregate denial ratio nor a sampled trace reliably establishes that every currently authorized user can obtain an export within its deadline, that every tenant boundary is enforced or that missing events were durably recorded. Use targeted authorization tests, complete queue/outbox state, freshness and end-to-end outcome evidence for those separate questions.

## What you can now explain

Ten denials can be half the traffic or one request in a thousand. Keep integer counts, a matched denominator, the interval and a clear unit beside the percentage. A zero denominator is unresolved arithmetic, and missing telemetry is unresolved evidence.

For one delayed export, join a known receipt to trusted context before judging time. A fresh heartbeat does not establish committed progress. Request age, remaining deadline, queue state and required-audit health let a reviewer choose a timed watch, a focused investigation or an escalation with a named owner.

For chapter 35, retain the deployment questions exposed by this exercise: which process emits observations, which identity may read/write the queue and outbox, which configuration supplies trusted host/scheme information, and which release artifact is actually running. Carry the existing permission, expiry and required-audit boundaries into the container and proxy review.
