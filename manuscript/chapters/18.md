# 18. Security requirements and private data

“Notes are private” sounds clear. Can a reviewer turn it into a test that permits Mina, refuses Ravi and still refuses Mina after her membership is revoked? If a support export expires tomorrow, what evidence would show that its stored copy was actually deleted?

This chapter turns those expectations into requirements with named data owners, observable results and review dates. You will also choose a small diagnostic export, give each field a purpose and work through an expiry and deletion deadline with a controlled clock.

Begin with chapter 17's `CB-DESIGN-17`, Figure F02, its TB1/TB2 boundary records and control register. Keep chapter 15's `casebook_db.py` and `note_repository.py` for the local checks. The required starting state is their new-database seed: Alpha workspace `1`, Beta workspace `2`, Mina `1`, Ravi `2`, Lee `3`, and notes `101` and `202`. No web service, queue or worker must be running.

By the end, you will be able to:

- Describe confidentiality, integrity and availability as outcomes a user can observe.
- Record risk, uncertainty and ownership without inventing a probability.
- Limit a private-data copy to its purpose and specify both access expiry and deletion.
- Turn a design choice into acceptance criteria and a scoped ASVS evidence record.

The edition targets CPython 3.12.14. The local examples use the Python 3.12-or-later connection interface established in chapter 15. Their actual runtime appears in the verification record. All people, records, timestamps and policy choices below are exercise fixtures.

## 1. Confidentiality, integrity and availability in product language

**Confidentiality** means information reaches only permitted recipients. For Casebook, Ravi must not receive an Alpha note's title or body just because he knows its ID.

**Integrity** means information and state keep their intended meaning. A diagnostic export must describe its own authorized source job. It must not silently mix Alpha's job identity with Beta's result, or report successful deletion when the file remains.

**Availability** means permitted users can obtain the intended service under its stated operating conditions. Mina should be able to read an Alpha note while she is active. When a membership lookup fails, the service must report failure rather than leak data or pretend the note list is successfully empty. Useful availability requirements also name workloads and deadlines; “always available” is not a measurable promise.

A control can support several properties. Chapter 15's note-plus-audit transaction protects integrity by preventing a partial write. A bounded export can protect availability by limiting work. Neither establishes that a particular reader has permission.

### Give a requirement a shape

A **requirement** states an outcome the system must achieve. An **acceptance criterion** states the conditions under which a reviewer can decide whether that outcome holds. An implementation choice, such as using a membership join, explains how a control may satisfy the requirement.

Use a short record with the following fields: an identifier, protected data, triggering operation, permitted actor, required decision, observable result, owner, evidence and review date. Name the point in time at which membership or expiry is checked.

**Table T18-01. Improve an imprecise statement**

| Starting statement | Missing decision | Testable replacement |
| --- | --- | --- |
| Notes are private. | Private from whom, through which paths, and when? | Every service-controlled read requires current active membership in the note's stored workspace; denied results release no private fields. |
| Managers can read notes. | Does management cross workspace boundaries? | Lee's active Alpha manager membership permits Alpha reads and gives no Beta authority. |
| Exports expire tomorrow. | Does expiry block access, remove bytes, or both? | Deny retrieval from the recorded expiry instant; remove managed payload copies by the separate deletion deadline. |
| Support needs everything for debugging. | Which question needs which field? | Include only the agreed diagnostic fields; exclude note text and credentials. |
| Deletion is logged. | Did deletion succeed? | Inspect artifact absence and failed direct retrieval before recording completed deletion. |

### Worked example 1: turn “notes are private” into a two-workspace test

Start with the established fixture, not an attacker payload. Mina belongs to Alpha. Ravi belongs to Beta. Alpha note `101` has body `Alpha private fixture`; Beta note `202` has body `Beta private fixture`.

Predict three results: Mina reads Alpha, Ravi asks for the same Alpha note, and Ravi reads Beta. The expected results are permit, deny and permit. The third case matters: a function that denies every request would pass a denial-only test while breaking the product.

**Exhibit D18-01. Requirement `CB-READ-01`**

| Field | Filled requirement |
| --- | --- |
| Data owner | Casebook product data owner, accountable for the private-workspace rule |
| Protected data | Private note titles, bodies and service-managed copies |
| Trigger | A list, detail, worker source read or export retrieval would release private data |
| Rule | Establish the requester through the trusted identity boundary. Permit a note read only when current stored membership is active in that note's stored workspace. Apply the rule to every returned note. |
| Export refinement | Preserve chapter 17's requester-bound retrieval rule as an additional condition; membership alone does not grant another requester's export. |
| Denied result | No private title, body or artifact bytes; no use of a browser or queue permission flag as authority |
| Revocation timing | A revocation committed before the next authorization check must affect that check. Concurrent release ordering remains an explicit later design task. |
| Implementers | Web maintainer for identity and responses; storage maintainer for scoped queries; worker maintainer for background reads/releases |
| Evidence | Two-workspace permit/deny cases, visitor case, manager scope, list contents and a read after committed revocation |
| Review date | 2026-12-03, or earlier when a new read or retrieval path is added |

The data owner approves the intended data use and privacy rule. The implementers build the controls. Naming a data owner does not give that person an application account or permission to inspect all private notes.

**Table T18-02. Acceptance matrix for `CB-READ-01`**

| Case | Given | When | Observable result |
| --- | --- | --- | --- |
| A18-01 | Mina is active in Alpha | Read workspace `1`, note `101` | Return Alpha's permitted fields |
| A18-02 | Ravi is active only in Beta | Read the same workspace and note | Deny; release no Alpha title or body |
| A18-03 | Ravi is active in Beta | Read workspace `2`, note `202` | Return Beta's permitted fields |
| A18-04 | Lee manages only Alpha | Read Beta note `202` | Deny; management is not global |
| A18-05 | Visitor has no validated identity | Read Alpha note `101` | Deny; no private fields |
| A18-06 | Mina is active in Alpha | List Alpha and then request Beta | Alpha list contains only Alpha notes; Beta list contains none |
| A18-07 | Mina's Alpha membership is revoked and committed | Perform her next Alpha read | Deny, even if an earlier read succeeded |
| A18-08 | Mina's export was queued while active | Revoke before the worker's permission check | No private release or ready artifact from the denied work |

These acceptance criteria define outcomes without inventing an HTTP status before the endpoint contract exists. Repository `None` and empty-list results are local evidence. Web checks must later inspect identity handling, response fields and caches too.

### Run the existing repository against the requirement

`pytest.mark.parametrize` gives the same expectation structure several fixture identities. These tests import the chapter 15 interfaces unchanged and create a new file database per test. They use fixture IDs at the caller boundary; they do not implement a browser session.

**Listing L18-01. Privacy acceptance checks at the repository boundary**

Filename: `tests/test_privacy_requirements.py`.

```python
from contextlib import closing

import pytest

from casebook_db import connect_database, create_schema, seed_database
from note_repository import get_note, list_notes


@pytest.fixture
def privacy_database(tmp_path):
    path = tmp_path / "casebook.sqlite3"
    with closing(connect_database(path)) as connection:
        create_schema(connection)
        seed_database(connection)
    return path


@pytest.mark.parametrize(
    ("user_id", "workspace_id", "note_id", "expected_body"),
    [
        (1, 1, 101, "Alpha private fixture"),
        (2, 1, 101, None),
        (2, 2, 202, "Beta private fixture"),
        (3, 2, 202, None),
        (3, 1, 101, "Alpha private fixture"),
        (None, 1, 101, None),
    ],
)
def test_private_read(privacy_database, user_id, workspace_id, note_id, expected_body):
    with closing(connect_database(privacy_database)) as connection:
        note = get_note(
            connection, user_id=user_id, workspace_id=workspace_id, note_id=note_id
        )
    if expected_body is None:
        assert note is None
    else:
        assert note["workspace_id"] == workspace_id
        assert note["body"] == expected_body


def test_lists_do_not_cross_workspaces(privacy_database):
    with closing(connect_database(privacy_database)) as connection:
        alpha = list_notes(connection, user_id=1, workspace_id=1)
        beta = list_notes(connection, user_id=2, workspace_id=2)
        denied = list_notes(connection, user_id=1, workspace_id=2)
    assert [(row["id"], row["workspace_id"]) for row in alpha] == [(101, 1)]
    assert [(row["id"], row["workspace_id"]) for row in beta] == [(202, 2)]
    assert denied == []


def test_committed_revocation_changes_the_next_read(privacy_database):
    with closing(connect_database(privacy_database)) as reader:
        assert get_note(reader, user_id=1, workspace_id=1, note_id=101) is not None
        with closing(connect_database(privacy_database)) as writer:
            with writer:
                writer.execute(
                    "UPDATE memberships SET active = 0 WHERE workspace_id = ? AND user_id = ?",
                    (1, 1),
                )
        assert get_note(reader, user_id=1, workspace_id=1, note_id=101) is None
```

## 2. Likelihood, impact, uncertainty and risk ownership

**Likelihood** describes how plausible a harmful event is under stated conditions. **Impact** describes its consequence. **Uncertainty** records what the team does not yet know. A **risk owner** is accountable for deciding how the project responds to a risk; that role differs from the engineer implementing one control.

Do not assign a probability just because a template has a numeric box. “The worker is not implemented, so its release path has not been tested” is useful uncertainty. “There is a 3% chance of leakage” without supporting observations is not useful evidence.

**Table T18-03. A small risk register**

| Risk | Plausibility and uncertainty | Impact | Owner and decision | Next evidence |
| --- | --- | --- | --- | --- |
| Cross-workspace detail read | Note IDs can be supplied by a caller. Local queries are checked; web identity integration is still absent. | A Beta user receives Alpha content. | Service owner: require scoped authorization at every entry point. | Tampered selectors under real fixture sessions; inspect response fields. |
| Old permission survives queue delay | Delay is expected in background work. Worker implementation is still proposed. | A revoked member receives private export data. | Service owner: request-time permission is insufficient. | Queue, revoke, run, then inspect job/artifact state. |
| Diagnostic bundle collects too much | Debugging often encourages broad dumps. No field contract would permit accidental expansion. | Extra private content reaches another store or support workflow. | Product data owner: approve a narrow field allowlist. | Inspect the serialized artifact, including its file metadata. |
| Expired artifact remains after cleanup failure | Storage outages and failed deletion are ordinary failures. Provider versions and replicas have not been verified. | A private copy persists beyond its purpose. | Product data owner owns retention; storage maintainer owns removal and failure reporting. | Inject deletion failure; inspect the object and deadline result. |
| Authorization dependency unavailable | Database errors are possible; availability targets need workload evidence. | Legitimate users cannot read, or a fallback leaks data. | Service owner: deny private release on an indeterminate decision and report failure. | Fail the lookup and inspect no private-byte response. |

A low observed frequency does not make an unacceptable data release acceptable. An owner can prioritize work using exposure, impact and evidence gaps. If a required control is missing, a risk label alone cannot turn a missing result into a pass.

A **residual risk** is what remains after the chosen controls. For example, an authorized user may already have downloaded a copy before revocation. Casebook can govern its own future reads and managed copies; it cannot promise to recall bytes from a user's independent device.

Record the review trigger as well as the calendar date. Adding a cache, a public storage URL, another export recipient or a new data field changes the risk even if the scheduled review is weeks away.

## 3. Data inventory, purpose, minimization, retention and deletion

A **data inventory** records what data exists, where it flows and why it is needed. A **purpose** is the specific task the data supports. **Minimization** means collecting and returning only what that task requires.

A **data owner** decides the permitted purpose and retention policy. A storage engineer can implement that policy but should not invent a business need to retain every copy indefinitely. In this chapter, the accountable owner is the Casebook product data owner from chapter 17's C17-07.

### Worked example 2: choose the fields for a support export

The question is narrow: Mina wants to inspect why her export job failed and provide a diagnostic reference if she opens a support case. The proposed diagnostic bundle describes that job. It is not an export of her notes.

The service binds the bundle to Mina and Alpha using trusted records, just as `CB-DESIGN-17` binds other exports. Retrieval remains requester-bound and requires current workspace membership. The word “support” gives neither an operator nor another member automatic download rights. Transfer to a support system would be a separate disclosed workflow with its own recipient and retention requirements.

| Candidate field | Include? | Purpose or reason for exclusion |
| --- | --- | --- |
| `schema_version` | Yes | Interpret the agreed diagnostic format. |
| `source_job_id` | Yes | Correlate this bundle with Mina's authorized source job. |
| `source_job_state` | Yes | Distinguish a failed operation from a completed one. |
| `error_code` | Yes | Use a fixed safe category such as `EXPORT_TIMEOUT`. |
| `correlation_id` | Yes | Find the relevant protected operational event. |
| `created_at`, `expires_at` | Yes | Show when this copy was created and when access ends. |
| Note title and body | No | Not needed to identify this failure category. |
| Password, session cookie or service token | No | Not diagnostic data and must not be copied. |
| Full exception or database query text | No | Can contain private data, paths or bound values. |
| Full membership or user record | No | Required authorization facts stay in controlled server records. |
| User/workspace IDs in the downloaded payload | No | Ownership is stored internally; the narrow diagnostic purpose needs no extra copy here. |

Its existence belongs in the inventory; it is not invisible merely because the browser does not receive it.

### Work through one retention decision

**Retention** is how long a copy is kept for its stated purpose. **Expiry** ends a permission or use period. **Deletion** removes a managed copy from the relevant storage interface. These are distinct events.

The product data owner chooses 24 hours for this exercise's diagnostic payload. The reason is a next-day troubleshooting window without keeping a diagnostic copy after that short task. This is a fictional product decision, not a universal or legal retention period.

All timestamps in the worked case are explicit UTC fixture times. The `Z` suffix means UTC. They do not depend on the reader's local timezone.

**Exhibit D18-03. Retention decision `CB-RETENTION-01`**

| Field | Filled decision |
| --- | --- |
| Data owner | Casebook product data owner |
| Implementer | Storage maintainer; web maintainer owns the independent expiry gate |
| Data and purpose | Requester-bound diagnostic export for one failed export job |
| Start event | Successful creation of this diagnostic payload; store its creation and expiry once |
| Access expiry | `expires_at = created_at + 24 hours`; deny retrieval when `now >= expires_at` |
| Removal deadline | Remove all service-managed payload copies by `delete_by = expires_at + 15 minutes` |
| Fixed example | Created 2026-11-26 10:00 UTC; expires 2026-11-27 10:00 UTC; deletion due by 2026-11-27 10:15 UTC |
| Failure behavior | Expiry still denies access if cleanup fails. Mark removal as pending/retry-required; do not report deletion complete. A missed removal deadline is a failed requirement. |
| Retry behavior | Cleanup is safe to repeat. A retry must not extend creation, expiry or an already established evidence-retention deadline. |
| Payload copies in scope | Live object, temporary payload copies, versions and managed replicas; reconcile orphaned payload objects too |
| Storage precondition | Diagnostic payload storage is excluded from backups and object version retention; provider-managed copies must meet the same removal deadline. Verify this before enabling the feature. |
| Evidence retained | Minimal protected deletion receipt with diagnostic ID, policy version, outcome and completion time; no payload, note text or credential |
| Receipt retention | Seven days after first successful deletion, then remove the receipt and any unneeded locator/ownership mapping under the metadata cleanup policy |
| Original notes | Unchanged; their purpose and retention are separate from this diagnostic copy |
| Review date | 2026-12-03, or earlier if fields, recipients or storage-copy behavior change |

The 15-minute interval is an observable service deadline, not a promise that a cleanup task is merely scheduled to start by then. Completing a task that leaves a version or replica behind does not satisfy the stated scope.

If the storage platform cannot exclude these payloads from a longer backup or version-retention policy, the precondition is false. Change the architecture or explicitly revise the promise with the data owner before release. Do not call active-object removal “all copies deleted” while known recoverable managed copies remain.

Deletion from an ordinary filesystem or object API is not evidence of forensic erasure from physical media. The requirement here concerns service-managed retrievable copies under the stated storage contract. Independent user downloads are outside the system's deletion authority and must be described as such.

### Give every copy a separate inventory row

**Table T18-05. Scope of the retention claim**

| Data or copy | Purpose | Handling decision | Evidence needed |
| --- | --- | --- | --- |
| Original notes and memberships | Operate private workspaces | This decision does not delete them | Compare source rows before and after diagnostic cleanup |
| Diagnostic payload | Short troubleshooting task | Access ends after 24 hours; removal by another 15 minutes | Expiry boundary test plus storage inspection and direct-read failure |
| Staged or orphaned diagnostic payload | Temporary preparation or interrupted work | Reconciler uses immutable creation/expiry information; the same maximum payload deadline still applies | Crash fixture and listing of unreferenced objects |
| Object versions and replicas | Storage implementation detail | None may remain retrievable past the payload deadline | Provider configuration and version/replica checks |
| Backups | Recovery | Exclude this payload class; prove restore does not reintroduce it | Backup configuration and a restore drill |
| Deletion receipt and essential job metadata | Verify cleanup and investigate failures | Keep minimal protected evidence for seven days after first deletion; then remove unneeded mappings | Metadata inventory and later cleanup check |
| An independent copy downloaded by Mina | User-controlled use | Server cannot promise to delete it | Clear product statement; no server-erasure claim |

The receipt is another data item with its own purpose and deadline. It is not proof that all personal data vanished. Keeping an identifier can preserve a link to a person or workspace, so “only metadata remains” still needs access controls and retention.

### Observe expiry, a failed deletion and a successful retry locally

The next program demonstrates one local payload file, controlled timestamps and unchanged source rows. It imports `connect_database`, `create_schema` and `seed_database` from chapter 15's `casebook_db.py`. Keep that file beside it. The program creates a new temporary database and artifact, so it never opens an existing Casebook database.

`datetime` represents a timestamp. `UTC` supplies its timezone; `timedelta` represents a duration. Comparing timezone-aware timestamps lets the fixture check the exact expiry boundary. The program passes times directly rather than sleeping for a day.

The metadata dictionary is an in-memory stand-in for a future durable artifact record. The `purge_artifact` function is a teaching fixture for an internally chosen path, not a public storage API or a complete worker. It reports completion only after removal succeeds and absence is observed.

**Listing L18-02. An observable local retention fixture**

Filename: `retention_demo.py`.

```python
from contextlib import closing
from datetime import UTC, datetime, timedelta
import json
from pathlib import Path
from tempfile import TemporaryDirectory

from casebook_db import connect_database, create_schema, seed_database


CREATED = datetime(2026, 11, 26, 10, 0, tzinfo=UTC)
EXPIRES = CREATED + timedelta(hours=24)
DELETE_BY = EXPIRES + timedelta(minutes=15)


def before_expiry(*, now: datetime, expires_at: datetime) -> bool:
    # A time gate only; identity and current membership are separate gates.
    return now < expires_at


def purge_artifact(path: Path, record: dict, *, now: datetime, remove=None) -> str:
    if now < record["expires_at"]:
        return "not_due"
    try:
        if remove is None:
            path.unlink(missing_ok=True)
        else:
            remove(path)
    except OSError:
        return "retry_required"
    if path.exists():
        return "retry_required"
    record["state"] = "deleted"
    record["artifact_key"] = None
    if record["deleted_at"] is None:
        record["deleted_at"] = now
    return "deleted"


def source_rows(database_path: Path) -> list[tuple]:
    with closing(connect_database(database_path)) as observer:
        return [tuple(row) for row in observer.execute(
            "SELECT id, workspace_id, title, body FROM notes ORDER BY id"
        )]


def main() -> None:
    with TemporaryDirectory(prefix="casebook-retention-") as directory:
        root = Path(directory)
        database_path = root / "casebook.sqlite3"
        with closing(connect_database(database_path)) as connection:
            create_schema(connection)
            seed_database(connection)
        original_rows = source_rows(database_path)
        artifact = root / "support-alpha-001.json"
        payload = {
            "schema_version": 1,
            "source_job_id": "export-alpha-001",
            "source_job_state": "failed",
            "error_code": "EXPORT_TIMEOUT",
            "correlation_id": "cb-demo-001",
            "created_at": "2026-11-26T10:00:00Z",
            "expires_at": "2026-11-27T10:00:00Z",
        }
        artifact.write_text(json.dumps(payload), encoding="utf-8")
        record = {
            "artifact_key": artifact.name,
            "expires_at": EXPIRES,
            "state": "ready",
            "deleted_at": None,
        }
        print("expires_at:", EXPIRES.isoformat())
        print("delete_by:", DELETE_BY.isoformat())
        print("before expiry gate:", before_expiry(
            now=EXPIRES - timedelta(seconds=1), expires_at=EXPIRES
        ))
        print("at expiry gate:", before_expiry(now=EXPIRES, expires_at=EXPIRES))
        print("at expiry file exists:", artifact.exists())
        record["state"] = "expired"

        def failed_removal(path):
            raise PermissionError("synthetic storage failure")

        failed = purge_artifact(
            artifact, record, now=EXPIRES + timedelta(minutes=5), remove=failed_removal
        )
        print("failed cleanup:", failed)
        print(f"after failure: state={record['state']}; file exists={artifact.exists()}")
        assert record["deleted_at"] is None and artifact.exists()

        completed_at = EXPIRES + timedelta(minutes=10)
        result = purge_artifact(artifact, record, now=completed_at)
        assert result == "deleted" and completed_at <= DELETE_BY
        print("retry cleanup:", result)
        print(f"after retry: state={record['state']}; artifact_key={record['artifact_key']}")
        try:
            artifact.read_bytes()
        except FileNotFoundError:
            print("direct artifact read: FileNotFoundError")
        else:
            raise AssertionError("deleted artifact was still readable")
        after_rows = source_rows(database_path)
        assert after_rows == original_rows
        print("source note IDs:", [row[0] for row in after_rows])
        print("repeat cleanup:", purge_artifact(
            artifact, record, now=EXPIRES + timedelta(minutes=11)
        ))
        assert record["deleted_at"] == completed_at
        receipt_until = record["deleted_at"] + timedelta(days=7)
        print("receipt_until:", receipt_until.isoformat())


if __name__ == "__main__":
    main()
```

Run `./.venv/bin/python retention_demo.py` on macOS or Linux, or `.\.venv\Scripts\python.exe retention_demo.py` on Windows.

Expected output:

```text
expires_at: 2026-11-27T10:00:00+00:00
delete_by: 2026-11-27T10:15:00+00:00
before expiry gate: True
at expiry gate: False
at expiry file exists: True
failed cleanup: retry_required
after failure: state=expired; file exists=True
retry cleanup: deleted
after retry: state=deleted; artifact_key=None
```

At expiry, the time gate denies even though the file still exists. The first cleanup fails, so the metadata remains expired with no completed-deletion timestamp. The retry removes the file before the deadline, clears its local locator and makes a direct read fail. Repeating cleanup preserves the first completion time. The source database still has both original notes with unchanged fields.

The local file's disappearance is observed before `TemporaryDirectory` performs its final automatic cleanup. Otherwise, the outer cleanup could conceal a faulty deletion function. The fixture computes a receipt deadline but does not persist or later delete a receipt. It also does not implement membership checks, durable cleanup transactions, object versions, replicas or backups.

Production cleanup needs durable retry state and a reconciliation path for disagreement between metadata and storage. A missing metadata row alone is not evidence that the bytes are absent. Likewise, an expired object reference alone is not evidence of deletion.

## 4. Turn a design decision into an acceptance criterion and ASVS evidence

A requirement needs a path to evidence. Start from the chapter 17 decision, write the observable outcome, choose a check, and record what the check actually covered.

**Table T18-06. The three-requirement handoff**

| ID | Required outcome | Data owner and implementer | Observable result | Review date |
| --- | --- | --- | --- | --- |
| `CB-READ-01` | Current active workspace membership gates every private-note read and copy retrieval, with requester binding where required. | Product data owner; web/storage/worker maintainers implement their boundaries. | A18-01 through A18-08; permitted cases succeed and denied cases return no private fields or ready artifact. | 2026-12-03, or a new read path |
| `CB-SUPPORT-01` | A diagnostic artifact is bound to its authorized requester/source job and contains exactly D18-02's seven fields; no note text, credential, raw exception or substituted job data. | Product data owner; service and worker maintainers implement construction and binding. | Parse actual generated bytes and compare exact field names, types and source-job values; another user's source job produces no artifact. | 2026-12-03, or a field/purpose/recipient change |
| `CB-RETENTION-01` | Diagnostic access ends at 24 hours; managed payload copies are removed by another 15 minutes; minimal receipts expire under their separate seven-day rule. | Product data owner; web maintainer implements expiry, storage maintainer implements removal/evidence. | Test the exact expiry boundary, inject removal failure, observe retry and file/object absence, then inspect receipt cleanup and unchanged source rows. | 2026-12-03, or a storage-copy change |

These are three local Casebook identifiers. They are not ASVS item numbers. They carry product-specific choices that a generic standard cannot supply, such as the 24-hour purpose window and requester-bound export rule.

### Make the deletion pass/fail decision observable

**Table T18-07. Acceptance evidence for retention**

| Check | Required observation | What would fail? |
| --- | --- | --- |
| R18-01: just before expiry | Time gate permits continued evaluation of identity/membership; it is not itself a grant. | Treating time validity as complete authorization. |
| R18-02: exactly at expiry | Retrieval denies; no payload bytes, even if ready state or storage still exists. | Waiting for the cleanup scheduler before denying. |
| R18-03: removal operation fails | Bytes remain, pending/retry state remains, no deletion-complete claim. | Marking deleted or hiding a deadline miss. |
| R18-04: removal completes by deadline | Storage read fails, managed copies are absent, locator is cleared and completion evidence is minimal. | Only a metadata row or visible download link disappears. |
| R18-05: repeated cleanup | Absent object remains absent; original expiry and first receipt deadline do not move. | Retries renew retention or create another artifact. |
| R18-06: source data | Source note IDs and full selected rows match the pre-cleanup snapshot. | Deleting original notes while removing the diagnostic copy. |
| R18-07: storage versions/restore | No managed payload version or restored backup reintroduces the expired artifact. | A successful active-object delete leaves a retrievable copy. |
| R18-08: receipt deadline | Minimal receipt and unneeded diagnostic mapping are removed after their seven-day purpose ends. | Keeping identifying evidence indefinitely. |

R18-01 through R18-06 have a partial local demonstration in L18-02. The time gate is tested separately from real retrieval authorization, and the fixture covers a single local file rather than all managed copies. R18-07 and R18-08 remain planned. A global retention pass requires those storage and metadata checks too.

### Map selected controls to a pinned standard

OWASP's **Application Security Verification Standard**, or **ASVS**, is a set of technical security verification requirements. This edition uses ASVS **5.0.0**. Read the selected version's text before recording an exact item number; identifiers can change between editions.

Use the versioned form `v5.0.0-14.2.7`, rather than an unversioned number. The following selected mappings were checked against the official `v5.0.0` data-protection chapter. They are paraphrases of scope, not claims of complete ASVS coverage.

**Table T18-08. Selected ASVS 5.0.0 mappings**

| Reference | Relevant scope | Casebook evidence and limitation |
| --- | --- | --- |
| `v5.0.0-14.1.1` | Identify sensitive data and assign protection categories. | T18-04 and T18-05 identify payload and metadata copies; the whole application's inventory is still broader. |

## Worked answers

### Exercise 1

A function that always denies would pass Ravi's refusal test. Add Mina reading Alpha note `101` and Ravi reading Beta note `202`. Both must return the expected workspace's permitted fields. Then retain the cross-workspace denial and verify the list path too.

### Exercise 2

The full membership record and email exceed the agreed diagnostic purpose, and a session token must not enter this artifact. Use only D18-02's seven fields, with fixed safe error categories. Keep required ownership facts in protected server records. The remaining job and correlation identifiers still link activity, so protect the bundle rather than calling it anonymous.

### Exercise 3

The stated facts are insufficient to prove that all retrieval paths denied at expiry; the expiry gate needs its own observation. Deletion failed because a managed payload version remains retrievable after the deadline. Inspect that version through an authorized storage test identity and record the missed deadline. The storage maintainer must remove/reconcile the copy; the product data owner must review any change to the promised scope or retention window.

A hidden link or optimistic metadata flag cannot override the storage observation. Do not mark the retention requirement passed merely because normal browser retrieval was disabled.

### Exercise 4

The immutable start event is successful creation of the original diagnostic payload. A retry is not a new troubleshooting purpose or permission grant. Repeated work must preserve the original expiry and removal deadline, and repeated cleanup must preserve the first deletion time used for evidence retention. If a new export is genuinely needed, it requires a new authorized request and a separate artifact record under its own policy.

### Exercise 5

A receipt's diagnostic ID can link to a requester or workspace. Keeping it forever can retain identifying activity after its evidence purpose ends. With a controlled clock, verify that the minimal receipt exists only during its seven-day period and that the receipt and unneeded linkage are removed when that period ends.
