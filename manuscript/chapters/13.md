A launcher gives Casebook the text `"false"` for its debug setting. Will the program turn debugging off? If its service credential is missing, can it stop before doing work and explain the problem without exposing another credential?

This chapter answers both questions. A **setting** controls how a program runs. A **credential** proves an identity to another system. Both can arrive as text, but they need different validation and different treatment in output.

Start in the `casebook-learning` folder from chapter 02, using its virtual environment. You need functions and modules from chapter 06, exceptions from chapter 09, dataclasses from chapter 10 and pytest from chapter 12. No earlier Casebook module is required by these listings. Create the `tests` directory if it does not exist. This chapter makes no network calls and uses only fictional credentials.

By the end, you will be able to:

- Explain which environment and working directory a process receives.
- Trace a text value into a validated boolean under a written precedence rule.
- Describe how a service receives, limits and replaces credentials.
- Check the exact startup diagnostic and keep secret values out of routine output.

The edition targets CPython 3.12.14. The verification record near the end identifies the runtime actually used for this draft.

## 1. Processes, environment inheritance and working directories

A **process** is a running instance of a program. A terminal shell is a process. When it launches Python, Python runs in another process, called its **child**. The shell is that child's **parent**.

An **environment** is a collection of named text values associated with a process. The parent normally passes its current environment to the child when launching it. A launcher can instead supply a selected collection. Python exposes its environment through `os.environ`, a mapping whose keys and values are strings.

An exported shell setting reaches a newly launched Python process. Changing a setting in that Python process does not update the parent shell or an already running sibling. Editing your terminal environment also does not reconfigure an already running service. Its settings need an explicit reload mechanism or a new process.

`os.environ` is initialized when `os` is first imported. Assignments through that mapping update the process environment. For these examples, use `os.environ` rather than lower-level environment mutation. The settings loader will take one copy at startup, so later mapping changes will not silently change its decisions.

A process also has a **working directory**: the folder used to resolve relative file paths. It can differ from the folder containing the script. A service launcher may choose a different directory from your terminal. This explains why a relative settings file may work locally and disappear during deployment.

### Observe only the setting you need

Predict the three lines before running this script. Does `os.environ` convert `false` into a Python boolean?

**Listing L13-01. Observe a process without dumping its environment**

Filename: `process_context.py`.

```python
import os
from pathlib import Path


print(f"script directory: {Path(__file__).resolve().parent.name}")
print(f"working directory: {Path.cwd().name}")
print(f"CASEBOOK_DEBUG: {os.environ.get('CASEBOOK_DEBUG')!r}")
```

`__file__` names this script. `resolve()` obtains an absolute path; `.parent` selects its containing folder. `.name` selects just the last path component. The `!r` conversion shows the representation of a value, including quotes around text. We use it only for this nonsecret setting.

From `casebook-learning`, run on macOS or Linux:

```shell
CASEBOOK_DEBUG=false ./.venv/bin/python process_context.py
```

On Windows PowerShell:

```powershell
$env:CASEBOOK_DEBUG = "false"
.\.venv\Scripts\python.exe process_context.py
Remove-Item Env:CASEBOOK_DEBUG
```

Expected output when the learning folder has the stated name:

```text
script directory: casebook-learning
working directory: casebook-learning
CASEBOOK_DEBUG: 'false'
```

The shell syntax differs, but both commands supply text. On POSIX shells, the assignment on this command applies to that invocation. The PowerShell assignment remains in the shell until removed or replaced.

For a working-directory boundary, create an empty folder named `scratch` inside the learning folder. Enter it and run the script by its parent path.

macOS or Linux:

```shell
mkdir -p scratch

CASEBOOK_DEBUG=false ../.venv/bin/python ../process_context.py
cd ..
```

Windows PowerShell:

```powershell

Set-Location scratch
$env:CASEBOOK_DEBUG = "false"
..\.venv\Scripts\python.exe ..\process_context.py

```

Expected output:

```text
CASEBOOK_DEBUG: 'false'
```

The script has not moved. Its relative file paths would now start from `scratch`. Our loader below avoids that dependency: it reads a supplied mapping or the process environment, with no implicit file lookup.

Do not replace the final line with `print(dict(os.environ))`. A process environment may also contain tokens, passwords and private deployment details.

## 2. Configuration precedence, typed settings and startup validation

**Configuration precedence** is the rule for deciding which source wins when sources overlap. Establish the rule before writing the loader.

**Table T13-01. Sources and validation for this chapter**

| Setting | Source order | Accepted value | Missing value |
| --- | --- | --- | --- |
| `CASEBOOK_DEBUG` | Supplied environment, then built-in default | Text `true` or `false`, ignoring outer whitespace and letter case | Default `False` |
| `CASEBOOK_SERVICE_TOKEN` | Supplied environment only | A string containing a non-whitespace character; preserved exactly | Stop startup |

An explicitly supplied mapping replaces the process environment for the loader. It is useful in tests. We never merge a test mapping with the machine's actual credentials. Unknown names are ignored because a process environment also contains unrelated operating-system settings.

There is no configuration file or command-line override in this chapter. Python does not automatically read a file named `.env`. If a later design adds a file loader, document its order relative to the environment and test collisions. A present but invalid higher-priority value must cause rejection; silently using a lower-priority value hides a configuration error.

### Convert once, before starting work

A **typed setting** is a value converted to its intended Python type and checked before use. A type annotation alone does not convert external text. The function body must do that work.

**Listing L13-03. A small settings boundary**

Filename: `casebook_settings.py`.

```python
import os
from collections.abc import Mapping
from dataclasses import dataclass, field


class SettingsError(ValueError):
    """A configuration problem that prevents startup."""


@dataclass(frozen=True)
class Settings:
    debug: bool
    service_token: str = field(repr=False)


def parse_bool(name: str, raw: str) -> bool:
    normalized = raw.strip().lower()
    if normalized == "true":
        return True
    if normalized == "false":
        return False
    raise SettingsError(f"setting {name} must be true or false")


def load_settings(env: Mapping[str, str] | None = None) -> Settings:
    source = dict(os.environ) if env is None else dict(env)

    token = source.get("CASEBOOK_SERVICE_TOKEN")
    if token is None:
        raise SettingsError(
            "required setting CASEBOOK_SERVICE_TOKEN is missing"
        )
    if not token.strip():
        raise SettingsError(
            "required setting CASEBOOK_SERVICE_TOKEN must not be blank"
        )

    raw_debug = source.get("CASEBOOK_DEBUG")
    debug = False if raw_debug is None else parse_bool(
        "CASEBOOK_DEBUG", raw_debug
    )
    return Settings(debug=debug, service_token=token)
```

`Mapping[str, str]` describes the text-to-text input contract. `None` means “use the real process environment.” The `env is None` check matters: an empty dictionary is a deliberate empty environment. Writing `env or os.environ` would let real machine settings leak into that test.

`dict(...)` takes a copy for this call. `frozen=True` prevents ordinary attribute reassignment after construction. `field(repr=False)` excludes the token from the generated dataclass representation. Neither feature encrypts or erases the token. Code can still read `settings.service_token`, and a dictionary conversion or debugger can reveal it.

The loader checks the required credential first, then parses debug. If both settings are wrong, the missing-credential error wins. It creates the `Settings` object only after validation succeeds. Importing this module does not read credentials or start work.

The token check uses `.strip()` only to recognize blank input. It returns the original token. Altering a credential's characters can change its meaning. Our local policy does not prove the credential is valid at a remote service; that service would still have to authenticate it.

### Trace each value and type

**Listing L13-04. Parse a synthetic environment**

Filename: `trace_settings.py`.

```python
from casebook_settings import load_settings


example_env = {
    "CASEBOOK_DEBUG": "false",
    "CASEBOOK_SERVICE_TOKEN": "fake-casebook-token-for-tests-only",
}
settings = load_settings(example_env)
print(f"input: {example_env['CASEBOOK_DEBUG']!r}")
print(f"debug: {settings.debug!r}")
print(f"type: {type(settings.debug).__name__}")
print(settings)
```

Run `./.venv/bin/python trace_settings.py` or `.\.venv\Scripts\python.exe trace_settings.py`.

Expected output:

```text
input: 'false'
debug: False
type: bool
Settings(debug=False)
```

**Table T13-02. The conversion path**

| Step | Expression or decision | Result | Type |
| --- | --- | --- | --- |
| Read input | `source.get("CASEBOOK_DEBUG")` | `"false"` | `str` |
| Normalize | `raw.strip().lower()` | `"false"` | `str` |
| Compare | `normalized == "false"` | `True` | `bool` |
| Return the chosen value | `return False` | `False` | `bool` |
| Store validated result | `Settings(debug=debug, ...)` | `settings.debug` is `False` | `bool` |

The comparison is true because the input names the false option. The branch therefore returns `False`. The comparison result and the parsed setting have different jobs.

Now change the debug text to `" FALSE "`. It still becomes `False`. Change it to `"off"`, `"0"` or `""`. Each raises `SettingsError` with the message `setting CASEBOOK_DEBUG must be true or false`. Empty text is present input, so it does not select the missing-value default.

## 3. Secret stores, least privilege, rotation and development fixtures

The trace used a **fixture**, a known input for an exercise or test. `fake-casebook-token-for-tests-only` has no authority anywhere. Synthetic fixtures make it safe to inspect failing tests and share examples. Never replace this fixture in a committed test with a real token.

A **secret store** is a system that controls access to credentials and other secret values. A deployment can use its process identity to request a credential, or a launcher can obtain it and deliver it through an environment value or a restricted mounted file. Each delivery method needs access controls. An environment variable is a delivery mechanism; it is not a secret store by itself.

For Casebook, define a small operational contract before connecting a real service:

**Table T13-03. A credential delivery and replacement plan**

| Decision | Casebook plan |
| --- | --- |
| Owner | The engineer responsible for the service integration owns issuance and replacement. |
| Retrieval | The deployed service identity can read only its own integration credential. |
| Authority | The credential permits only the integration operations that process needs. |
| Separation | Development, test and production use separate identities and credentials. |
| Local work | Exercises and automated tests use synthetic values and make no remote calls. |
| Replacement | Issue a new credential, deliver it, reload or restart consumers, verify use, then revoke the old one. |
| Suspected exposure | Revoke or disable the exposed credential promptly; inspect affected activity and replace it. |

**Least privilege** means granting only the authority needed for a named task. Apply it twice: to the identity that reads the secret store and to the credential the target service accepts. An export worker should not receive unrelated administrative credentials.

**Rotation** means replacing a credential. Where the provider permits a short overlap, the replacement sequence in the table can avoid interrupting service. If exposure requires immediate revocation, availability may be interrupted. A restart is not a rotation: it must receive a new value, and the old credential must lose authority. A copied `Settings` object does not observe secret-store changes automatically.

Keep real credentials out of source files, command arguments, screenshots and test reports. Shell commands containing them may enter history. A local `.env` file also needs restricted access and exclusion from version control; an ignore rule does not remove a previously committed secret. If a real credential was committed, revoke it and follow the project's history-cleanup procedure. This chapter creates no real secret file.

These operational choices support the loader but do not change its job. It checks that required configuration exists and has the expected shape. It cannot establish who owns the service credential or whether its authority is suitably limited.

## 4. Public diagnostics, redaction and configuration drift

A **diagnostic** describes a result or failure. Here, “public” means safe for the program's intended output audience. It does not mean publishing infrastructure details through a web endpoint. Startup errors belong to the operator. A future browser route should have its own, smaller error contract.

**Redaction** means removing sensitive content from an output. Prefer choosing safe fields in the first place. Our errors name fixed setting keys and the rule that failed. They never interpolate the supplied values. This also prevents an invalid value containing a newline from adding a fake diagnostic line.

### Worked example 2: reject a missing service credential

Before running the next listing, predict whether it will print `Casebook startup complete` with an empty environment.

We need two output destinations. **Standard output**, available as `sys.stdout`, carries normal output. **Standard error**, available as `sys.stderr`, carries diagnostics. An **exit code** reports the process result to its launcher. This example uses `0` for success and `2` for invalid startup settings. Chapter 14 develops a fuller command contract.

**Listing L13-05. Validate before starting the application**

Filename: `casebook_start.py`.

```python
import sys
from collections.abc import Mapping

from casebook_settings import Settings, SettingsError, load_settings


def start_casebook(settings: Settings) -> None:
    # This local stand-in starts no server and contacts no service.
    print(f"Casebook startup complete; debug={settings.debug}")


def main(env: Mapping[str, str] | None = None) -> int:
    try:
        settings = load_settings(env)
    except SettingsError as error:
        print(f"configuration error: {error}", file=sys.stderr)
        return 2

    start_casebook(settings)
    return 0


if __name__ == "__main__":
    raise SystemExit(main())
```

`main()` returns a number. `SystemExit` passes it to the launcher when the file runs as a script. The `__name__` guard prevents startup when tests import the module. Only `SettingsError` is handled here. An unexpected programming error remains visible to the developer.

### Assert the whole output contract

`capsys` is pytest's fixture for capturing writes to Python's standard output and standard error. `readouterr()` returns the captured text as `.out` and `.err`. Equality below checks every character, including `\n` for the final newline. Checking only that an error contains the setting name could miss a leaked token on the next line.

**Listing L13-07. Settings and startup regression tests**

Filename: `tests/test_settings.py`.

```python
import pytest

import casebook_start
from casebook_settings import SettingsError, load_settings, parse_bool


FAKE_TOKEN = "fake-casebook-token-for-tests-only"


@pytest.mark.parametrize(
    ("raw", "expected"),
    [("true", True), ("false", False), (" TRUE ", True), (" FALSE ", False)],
)
def test_boolean_words(raw, expected):
    assert parse_bool("CASEBOOK_DEBUG", raw) is expected


@pytest.mark.parametrize("raw", ["", " ", "0", "1", "yes", "off"])
def test_unknown_boolean_is_rejected(raw):
    with pytest.raises(SettingsError) as caught:
        parse_bool("CASEBOOK_DEBUG", raw)
    assert str(caught.value) == "setting CASEBOOK_DEBUG must be true or false"


def test_false_survives_loading_and_repr_hides_token():
    settings = load_settings({
        "CASEBOOK_DEBUG": "false",
        "CASEBOOK_SERVICE_TOKEN": FAKE_TOKEN,
    })
    assert settings.debug is False
    assert settings.service_token == FAKE_TOKEN
    assert repr(settings) == "Settings(debug=False)"


def test_missing_debug_uses_default():
    assert load_settings({"CASEBOOK_SERVICE_TOKEN": FAKE_TOKEN}).debug is False


@pytest.mark.parametrize("raw", ["", " ", "\t\n"])
def test_blank_token_is_rejected(raw):
    with pytest.raises(SettingsError) as caught:
        load_settings({"CASEBOOK_SERVICE_TOKEN": raw})
    assert str(caught.value) == (
        "required setting CASEBOOK_SERVICE_TOKEN must not be blank"
    )


def test_empty_mapping_does_not_fall_back_to_real_environment(monkeypatch):
    monkeypatch.setenv("CASEBOOK_SERVICE_TOKEN", FAKE_TOKEN)
    with pytest.raises(SettingsError) as caught:
        load_settings({})
    assert str(caught.value) == (
        "required setting CASEBOOK_SERVICE_TOKEN is missing"
    )


def test_default_source_reads_environment(monkeypatch):
    monkeypatch.setenv("CASEBOOK_SERVICE_TOKEN", FAKE_TOKEN)
    monkeypatch.setenv("CASEBOOK_DEBUG", "false")
    assert load_settings().debug is False


def test_loaded_settings_do_not_change_with_environment(monkeypatch):
    monkeypatch.setenv("CASEBOOK_SERVICE_TOKEN", FAKE_TOKEN)
    monkeypatch.setenv("CASEBOOK_DEBUG", "false")
    settings = load_settings()
    monkeypatch.setenv("CASEBOOK_DEBUG", "true")
    assert settings.debug is False
    assert load_settings().debug is True


def test_missing_token_stops_before_work(monkeypatch, capsys):
    def unexpected_start(settings):
        pytest.fail("application work started before validation succeeded")

    monkeypatch.setattr(casebook_start, "start_casebook", unexpected_start)
    code = casebook_start.main({"UNRELATED_CREDENTIAL": FAKE_TOKEN})
    captured = capsys.readouterr()
    assert code == 2
    assert captured.out == ""
    assert captured.err == (
        "configuration error: required setting CASEBOOK_SERVICE_TOKEN is missing\n"
    )
    assert FAKE_TOKEN not in captured.out + captured.err


def test_invalid_debug_does_not_echo_either_value(capsys):
    invalid_debug = "fake-sensitive-value\nforged log line"
    code = casebook_start.main({
        "CASEBOOK_SERVICE_TOKEN": FAKE_TOKEN,
        "CASEBOOK_DEBUG": invalid_debug,
    })
    captured = capsys.readouterr()
    assert code == 2
    assert captured.out == ""
    assert captured.err == (
        "configuration error: setting CASEBOOK_DEBUG must be true or false\n"
    )
    assert FAKE_TOKEN not in captured.err
    assert invalid_debug not in captured.err


def test_success_has_no_credential_in_output(capsys):
    code = casebook_start.main({
        "CASEBOOK_SERVICE_TOKEN": FAKE_TOKEN,
        "CASEBOOK_DEBUG": "false",
    })
    captured = capsys.readouterr()
    assert code == 0
    assert captured.out == "Casebook startup complete; debug=False\n"
    assert captured.err == ""
    assert FAKE_TOKEN not in captured.out + captured.err
```

Run from the learning folder on macOS or Linux:

```shell
./.venv/bin/python -m pytest -q tests/test_settings.py
```

On Windows:

```powershell
.\.venv\Scripts\python.exe -m pytest -q tests/test_settings.py
```

### Detect configuration drift without publishing secrets

**Configuration drift** means actual settings differ from the intended settings, or from one process to another. If a new worker starts with debug enabled while an older worker keeps it disabled, identical code can behave differently.

Keep an intended nonsecret configuration record for each deployment. Compare the running debug value, application version and configuration revision with that record. A protected operator report may show `debug=False` and a nonsecret credential version identifier. It should not show the token, a prefix of it or a dump of the settings object. A version identifier should be metadata supplied by the secret store, not derived from the credential.

Our success message exposes only the validated debug flag. Our representation test covers only `repr(settings)`. It does not prove that every future log, exception reporter or third-party client will protect secrets. Review each new output boundary when it is added. Restarted consumers must also be checked after a configuration change; changing one terminal proves nothing about other processes.

## Worked answers

### Exercise 1

The missing value selects the nonempty default text `"false"`, so the expression returns `True`. The text `"false"` also produces `True`; empty text produces `False`. The code tests whether text is nonempty instead of parsing the setting's allowed words.

### Exercise 2

Preserve the value. The policy rejects only missing or entirely blank tokens and does not normalize accepted credentials. Add this test to `tests/test_settings.py`:

```python
def test_token_characters_are_preserved():
    token = " fake-token-with-outer-spaces "
    settings = load_settings({"CASEBOOK_SERVICE_TOKEN": token})
    assert settings.service_token == token
```

Run the chapter's pytest command again. With this additional test, expect `22 passed`. A provider-specific rule could instead reject outer spaces, but it would need explicit documentation and tests.

### Exercise 3

The token is missing, so startup returns `2`. Stdout stays empty. Stderr is exactly `configuration error: required setting CASEBOOK_SERVICE_TOKEN is missing` followed by a newline. The debug parser is never reached.

### Exercise 4

One explicit policy would be “environment overrides a file at a configured absolute path; the file overrides built-in nonsecret defaults.” A conflicting file value of `true` and environment value of `false` must yield `False`. Starting from another working directory must still read the chosen file. Also test that an invalid environment value causes rejection instead of falling back to a valid file value. Do not silently add this behavior to the current loader; its published contract has no file source.

## What you can now explain

Environment values enter as text. A documented parser turns accepted text into a boolean, and startup validation rejects missing or invalid required settings before work begins. Synthetic credentials and exact output assertions make that behavior repeatable without exposing secrets.

Keep `casebook_settings.py`, `casebook_start.py` and `tests/test_settings.py` available. Chapter 14 builds command-line contracts and child-process checks using the same distinction between normal output, diagnostics and exit codes.

- Pytest documents [output capture](https://docs.pytest.org/en/stable/how-to/capture-stdout-stderr.html) and [restored environment changes with monkeypatch](https://docs.pytest.org/en/stable/how-to/monkeypatch.html).
- The [OWASP Secrets Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html) discusses access control, credential delivery, rotation, revocation and secret lifecycle ownership.
