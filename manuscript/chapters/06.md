Mina's note viewer and a small reporting script both need the same access decision. How can they use one implementation? When the function checks Mina and then Ravi, what prevents Mina's result from leaking into Ravi's call?

In chapter 04, a script checked sign-in, membership, workspace and role. Chapter 05 showed how shared mutable data can affect another user. This chapter gives the access rule a function interface and keeps the rule independent of printing and stored state.

Begin in `casebook-learning` with its `.venv` interpreter. You need assignments, branches, loops, dictionaries and list copying. The complete listings below belong in that learning folder.

By the end, you will be able to do four things.

- Define a function with explicit arguments and a useful return value.
- Explain local scope, default arguments and a shared mutable default.
- Keep a decision separate from output and make its dependencies visible.
- Import one rules module from two scripts and explain when module code executes.

Run a file on Windows with the following command, replacing the filename as needed.

```powershell
.\.venv\Scripts\python.exe function_basics.py
```

On macOS and Linux, use the following.

```shell
./.venv/bin/python function_basics.py
```

## 1. Define a function and trace its calls

A function groups instructions under a name. The caller supplies arguments, the function performs its work and a `return` statement can give the caller a result.

**Listing L06-01. Naming the quota calculation**

Filename: `function_basics.py`.

```python
def remaining_places(note_limit, current_count):
    return note_limit - current_count


print(remaining_places(3, 2))
print(remaining_places(3, 0))
```

`def` defines a function. The name is `remaining_places`. The names inside its parentheses are **parameters**, names that receive values when the function is called. The definition's header ends with a colon, and the function body is indented four spaces.

The header describes the function's **signature**, the name and parameter arrangement a caller uses. In the first call, the **arguments** are `3` and `2`. They are positional arguments, so their positions determine which parameters receive them.

The expected output is the following.

```text
1
3
```

**Table T06-01. Two calls to the same calculation**

| Call | `note_limit` inside this call | `current_count` inside this call | Returned value |
| --- | --- | --- | --- |
| `remaining_places(3, 2)` | `3` | `2` | `1` |
| `remaining_places(3, 0)` | `3` | `0` | `3` |

Executing the `def` statement creates the function and binds its name. The subtraction runs when you call the function. `return` ends that call and supplies its expression's value to the caller. The surrounding `print` displays that returned value.

A function that reaches its end without a `return` returns `None`. A bare `return` also returns `None`. Choose a return contract deliberately so callers know what value to expect.

### Read local scope

**Scope** describes where a name is available. A parameter is local to its function call. Assigning a local parameter a new value does not reassign a caller's name.

**Listing L06-02. A local reassignment**

Filename: `local_count.py`.

```python
def next_count(current_count):
    current_count = current_count + 1
    return current_count


current_count = 2
updated_count = next_count(current_count)
print(current_count)
print(updated_count)
```

The expected output is the following.

```text
2
3
```

The caller's `current_count` still refers to `2`. The function's local name was rebound to `3`, which became the return value. After the call, the caller binds `updated_count` to that result.

Local names can still refer to shared objects. If a parameter refers to a caller's list and the function appends to it, the caller observes the mutation. Local scope and independent object ownership answer different questions. Chapter 05's aliasing rules still apply inside functions. [Python's execution model](https://docs.python.org/3.12/reference/executionmodel.html)

## 2. Make arguments and defaults explicit

A **keyword argument** supplies the parameter's name at the call site. For example, `remaining_places(note_limit=3, current_count=2)` binds the same values as the first positional call. Keywords make similarly shaped inputs easier to distinguish during review.

A **default argument value** supplies a value when the caller omits that parameter.

**Listing L06-03. A default for a quota calculation**

Filename: `quota_default.py`.

```python
def remaining_places(current_count, note_limit=3):
    return note_limit - current_count


print(remaining_places(2))
print(remaining_places(2, note_limit=5))
```

The expected output is the following.

```text
1
3
```

This separate example changes the earlier parameter order so the required count comes before the optional limit. Existing callers would need updating if you changed an established function that way. The access function below will establish one signature and keep it across both calling scripts.

For security decisions, require the caller to supply the relevant facts explicitly. A missing membership fact should be visible as a missing argument. Our access interface will use **keyword-only parameters**, introduced by a standalone `*` in its parameter list. Arguments after that marker must be supplied by name. Omitting a required argument or passing an unexpected keyword raises `TypeError`.

### Predict a mutable default across calls

Default values are evaluated when a function definition executes. The same default object is available to later calls that omit that argument. A mutable list can therefore accumulate changes across calls.

**Listing L06-04. A role list that survives between calls**

Filename: `role_defaults_bad.py`.

```python
def with_role(role, roles=[]):
    roles.append(role)
    return roles


mina_roles = with_role("member")
print(mina_roles)
ravi_roles = with_role("manager")
print(mina_roles)
print(ravi_roles)
print(mina_roles is ravi_roles)
```

Predict all four output lines before running this deliberate mistake.

```text
['member']
['member', 'manager']
['member', 'manager']
True
```

The default empty list is created once when `def` executes. The first call appends `"member"` and returns that list. The second call appends `"manager"` to the same list. Mina's previously returned reference sees the change too.

| Moment | Default list contents | Who refers to the list? |
| --- | --- | --- |
| Definition executed | `[]` | The function's default argument |
| First call finishes | `["member"]` | The default and `mina_roles` |
| Second call finishes | `["member", "manager"]` | The default, `mina_roles` and `ravi_roles` |

### Create the result within each call

Use `None` to indicate that a starting list was omitted. For this helper's contract, even an explicitly supplied list should retain its original contents. Copy it before building the result.

**Listing L06-05. Independent results from a role helper**

Filename: `role_defaults.py`.

```python
def with_role(role, roles=None):
    if roles is None:
        updated_roles = []
    else:
        updated_roles = roles.copy()
    updated_roles.append(role)
    return updated_roles


mina_roles = with_role("member")
ravi_roles = with_role("manager")
print(mina_roles)
print(ravi_roles)
print(mina_roles is ravi_roles)

starting_roles = ["member"]
updated_roles = with_role("manager", roles=starting_roles)
print(starting_roles)
print(updated_roles)
```

The expected output is the following.

```text
['member']
['manager']
False
['member']
['member', 'manager']
```

The helper demonstrates ownership of a flat list of strings. Its role strings are fictional inputs for a language exercise. The real permission to grant a role needs its own authorization rule. [Python's function argument rules](https://docs.python.org/3.12/tutorial/controlflow.html#more-on-defining-functions)

## 3. Extract the access decision as a pure operation

A **contract** states what a caller supplies, what the function returns and which effects it has. An **interface** is the way callers use that contract, including the function's name and parameters.

Our function will receive facts about the reader and note, then return a boolean. The calling script will turn that result into display text. Here is the contract before the code.

**Table T06-02. Contract for `may_read`**

| Element | Meaning |
| --- | --- |
| `signed_in` | A boolean established by the identity check |
| `membership_active` | A boolean describing current membership in `reader_workspace` |
| `reader_workspace` | A valid workspace identifier for an active membership; a visitor may supply `None` |
| `note_workspace` | A valid workspace identifier from the note record |
| `role` | A role string associated with that membership |
| Return value | `True` for a recognized allowed reader; `False` for a refused reader |
| Effects | Reads its arguments and returns a decision; inputs remain unchanged |

Workspace identifiers in the supported signed-in fixtures are nonempty strings such as `"Alpha"`. The function assumes the caller has obtained and checked these facts. External request validation and loading current records belong at the service boundary in later chapters.

### Worked example 1. Extract the rule from the printing loop

Chapter 04's scenario loop combined fixture setup, branching and printing. Put its decision into a new file named `access_rules.py`. Keep this file beside the two calling scripts you will create below.

**Listing L06-06. The reusable read rule**

Filename: `access_rules.py`.

```python
def may_read(
    *,
    signed_in,
    membership_active,
    reader_workspace,
    note_workspace,
    role,
):
    """Return whether the supplied reader facts permit this note read."""
    if not signed_in:
        return False
    if not membership_active:
        return False
    if reader_workspace != note_workspace:
        return False
    return role in ("member", "manager")
```

The triple-quoted string immediately inside the function is its **docstring**, a description of its purpose. Parentheses allow the signature to span several source lines. The commas separate parameters, and the standalone `*` makes all five keyword-only.

Each early `return False` ends the current call. The next `if` is reached only when the preceding refusal did not occur. Finally, the membership test on the role tuple returns a boolean. An unknown role produces false.

Running this file at this stage produces no output. It defines the function for callers to use.

### Read dependencies at the call boundary

A **dependency** is information or behavior an operation needs. Every decision input here is a parameter. The function uses the facts supplied for that call. It has no module-level variable holding the previous reader or decision.

A **pure function** produces the same result for the same inputs and causes no externally visible changes. A **side effect** is an observable change such as printing, modifying a caller's list or writing a file. Under its stated input contract, `may_read` is a pure decision.

The callers still need to load current facts at the time of each read. Purity makes the rule easy to repeat and inspect; freshness depends on the facts the caller supplies.

### Import the rule and keep printing in the caller

A **module** is a unit of Python code that another module can import. Here the module is the saved file `access_rules.py`. `from access_rules import may_read` makes that function name available in the caller. The module name in the import leaves off `.py`.

**Listing L06-07. One printing loop with two readers**

Filename: `check_access.py`.

```python
from access_rules import may_read

readers = [
    {
        "name": "Mina",
        "signed_in": True,
        "membership_active": True,
        "workspace": "Alpha",
        "role": "member",
    },
    {
        "name": "Ravi",
        "signed_in": True,
        "membership_active": True,
        "workspace": "Beta",
        "role": "member",
    },
]
before = [reader.copy() for reader in readers]

for reader in readers:
    allowed = may_read(
        signed_in=reader["signed_in"],
        membership_active=reader["membership_active"],
        reader_workspace=reader["workspace"],
        note_workspace="Alpha",
        role=reader["role"],
    )
    decision = "Deny"
    if allowed:
        decision = "Allow"
    print(reader["name"], decision)

print("Inputs unchanged", readers == before)
```

Predict the two access results and the final comparison before running the script.

```text
Mina Allow
Ravi Deny
Inputs unchanged True
```

The `before` snapshot copies each fixture dictionary. A shallow copy is sufficient here because its field values are immutable strings and booleans. The final comparison checks their contents after both calls.

**Table T06-03. Two calls within one interpreter run**

| Call | Reader | Local `reader_workspace` | First return reached | Result received by caller |
| --- | --- | --- | --- | --- |
| 1 | Mina | `"Alpha"` | Final role-membership result | `True` |
| 2 | Ravi | `"Beta"` | Workspace-mismatch refusal | `False` |

The second call receives its own argument bindings. It reaches the workspace mismatch and returns false even though the first call returned true. The caller assigns `allowed` again and resets its display decision to `Deny` each iteration.

### Use the same module from a second script

The second caller imports the module itself. It accesses the function through `access_rules.may_read`. It checks Ravi first so you can also compare the calls in the opposite order.

**Listing L06-08. Reporting two decisions in reverse order**

Filename: `report_access.py`.

```python
import access_rules

ravi_allowed = access_rules.may_read(
    signed_in=True,
    membership_active=True,
    reader_workspace="Beta",
    note_workspace="Alpha",
    role="member",
)
mina_allowed = access_rules.may_read(
    signed_in=True,
    membership_active=True,
    reader_workspace="Alpha",
    note_workspace="Alpha",
    role="member",
)

print("Ravi may read", ravi_allowed)
print("Mina may read", mina_allowed)
```

The expected output is the following.

```text
Ravi may read False
Mina may read True
```

Both clients use the same signature and implementation. The boolean result remains useful whether a caller produces a short access label or a report sentence. The current contract supplies a decision; a later audit interface can add a structured reason when needed.

## 4. Trace imports, entry points and packages

When the import system first loads an ordinary module, it executes its top-level code. A `def` statement at that level creates a function. Its body runs on a call. Top-level `print` calls run during loading, which can create surprising output in a caller.

### Worked example 2. Observe top-level execution

Use two small probe files to inspect that behavior independently of the access rule.

**Listing L06-09. A module that announces when it runs**

Filename: `import_probe.py`.

```python
print("Probe loaded")
print(f"Module name {__name__}")

if __name__ == "__main__":
    print("Direct execution")
```

Python supplies the special name `__name__` inside a module. When this file is the directly executed script, its value is `"__main__"`. When imported as `import_probe`, its value is `"import_probe"`.

Run `import_probe.py` using the project interpreter. The expected output is the following.

```text
Probe loaded
Module name __main__
Direct execution
```

Now save the following caller beside it.

**Listing L06-10. Importing a module twice in one run**

Filename: `probe_caller.py`.

```python
import import_probe
import import_probe

print("Caller finished")
```

Run `probe_caller.py` in a fresh interpreter process. The expected output is the following.

```text
Probe loaded
Module name import_probe
Caller finished
```

The first import loads and executes the probe. Python normally caches imported modules in `sys.modules`, a dictionary of loaded modules. The second import uses the existing module, so its top-level prints do not repeat. A new interpreter process has its own module cache.

The `if __name__ == "__main__"` check is called the **main guard**. It keeps its block for direct execution. The probe's guarded message is skipped during import. [Python's main-module guide](https://docs.python.org/3.12/library/__main__.html) · [Import behavior](https://docs.python.org/3.12/reference/import.html)

### Give the rules module a direct-run message

Append the following block at the end of `access_rules.py`, outside the function. Keep its `if` at the left margin.

**Listing L06-11. A main guard for the rules module**

```python
if __name__ == "__main__":
    print("Use check_access.py or report_access.py to inspect decisions")
```

Running `access_rules.py` directly now prints that message. Running either caller still produces its earlier expected output, since the imported rules module skips the guarded print. Save the final module with its function and this guard.

### Understand where an import finds a file

For the commands in this chapter, Python includes the executed script's directory in its module search path. Keeping `check_access.py`, `report_access.py` and `access_rules.py` in one directory lets those local imports resolve.

`sys.path` lists search locations. To inspect which module file was actually loaded, run the following command from `casebook-learning` on Windows.

```powershell
.\.venv\Scripts\python.exe -c "import access_rules; print(access_rules.__file__)"
```

On macOS and Linux, use the following.

```shell
./.venv/bin/python -c "import access_rules; print(access_rules.__file__)"
```

`-c` executes the supplied Python source string. `__file__` identifies the loaded module's file in this ordinary file-based example. Its output should name your learning folder's `access_rules.py`.

**Module shadowing** occurs when a file with a conflicting name is loaded instead of the module you intended. For example, a local `json.py` can shadow Python's standard-library `json` module. Use project-specific module names, such as `access_rules.py`, and inspect `__file__` when an import resolves unexpectedly. Fix the filename and start a fresh interpreter before checking again. [Python's module search path](https://docs.python.org/3.12/tutorial/modules.html#the-module-search-path)

### Recognize a package when the project grows

A **package** groups modules under a dotted import name. A conventional regular package directory contains an `__init__.py` file. For example, a directory `casebook_rules` containing `__init__.py` and `access.py` can expose a function through `from casebook_rules.access import may_read` when its parent directory is on the search path.

The package's `__init__.py` also runs when that package is first imported. Keep its top-level work deliberate. Python supports namespace packages too, which have different layout rules. The current chapter uses the simpler single-file `access_rules` module, so keep the three access files together for the next exercises. [Python's package tutorial](https://docs.python.org/3.12/tutorial/modules.html#packages)

## Guided lab. Reuse the rule and check call independence

Start with `access_rules.py`, `check_access.py` and `report_access.py` from Listings L06-06 through L06-08. Add the guard from Listing L06-11 to the rules file.

1. Predict the outputs of both clients, including the unchanged-input comparison.
2. Run `check_access.py`. Confirm Mina is allowed, Ravi is denied and the input comparison is true.
3. Run `report_access.py`. Check that reversing the request order preserves both decisions.
4. In the Mina fixture in `check_access.py`, change only `membership_active` to `False`. Predict the selected return and run the script. Both access decisions should now be denials, and inputs should still compare equal to the snapshot.
5. Restore Mina's active membership. Change her role to `"unknown"`, predict the result and run again.
6. Restore her role. Change Ravi's role to `"manager"` while leaving his workspace as Beta. Predict the workspace refusal and run again.
7. Restore both fixtures, then omit Mina's membership argument in the direct call in `report_access.py`. Run once to observe the missing-argument `TypeError`, then restore the keyword.
8. Run both clients once more. Their outputs should match the original predictions. Check the loaded rules path using the `-c` command above.

Make each temporary change independently and restore it before the next one. The final files should describe an active Mina in Alpha and an active Ravi in Beta, both with the member role. Your rule should require all five keyword arguments and have no mutable defaults or saved reader state.

## Worked answers

### Exercise 1

The parameters are `current_count` and `note_limit`. The supplied arguments bind `current_count` to `2` and `note_limit` to `5`. The result is integer `3`, from `5 - 2`.

### Exercise 2

Both calls omit the `roles` argument and use the same default list created by the definition. `mina_roles` refers to that list, so it observes the second append. Making a parameter keyword-only changes how callers supply it; the mutable default would still be shared. Listing L06-05 creates a result list inside each call instead.

### Exercise 3

All five parameters are keyword-only. The positional call raises `TypeError` before entering the function body. Supply explicit keywords, as the two chapter clients do.

### Exercise 4

The caller receives `None` if the function reaches its end without returning a value. Return `True` on allowed paths and `False` on refusal paths. Let the caller choose whether and how to display that result.

### Exercise 5

Each of the probe's two top-level print statements runs once in that caller process. The main guard is false during import, so `Direct execution` is skipped. Starting the caller again creates a new process, whose first import executes the probe's top-level code again.

### Practice check

`check_access.py` produces `Mina Allow`, `Ravi Deny` and `Inputs unchanged True`, on separate lines. Its two calls use the same implementation with fresh parameter bindings. Ravi's workspace refusal supplies false independently of Mina's earlier true result.

`report_access.py` checks Ravi before Mina and prints `Ravi may read False` and `Mina may read True`. The order change preserves the decisions. The final rules function reads only its supplied facts, returns a boolean on every path and retains no call-specific state in module variables or defaults.

## Glossary

| Term | Meaning in this chapter |
| --- | --- |
| Argument | A value supplied when calling a function |
| Contract | The expected inputs, results and effects of an operation |
| Default argument value | A value used when a caller omits an optional argument |
| Dependency | Information or behavior an operation requires |
| Docstring | A description written as the first string in a function or module |
| Interface | How a caller uses an operation's contract |
| Keyword-only parameter | A parameter whose argument must be supplied by name |
| Local scope | The region in which a function call's local names are available |
| Main guard | A condition selecting work for direct execution of a module |
| Module | A unit of Python code available through imports |
| Module shadowing | Loading a conflicting module name instead of the intended module |
| Package | A grouping of modules under a dotted import name |
| Parameter | A name in a function definition that receives an argument |
| Pure function | A function whose result depends only on its inputs and which causes no external changes |
| Side effect | An observable change beyond returning a value |
| Signature | A function's name and parameter arrangement |
