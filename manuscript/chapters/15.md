# 15. Relational data and transactions

Can Mina read an Alpha note while Ravi cannot? If creating a note also requires an audit record, what should remain in the database when the audit insert fails?

This chapter moves Casebook's synthetic records into SQLite. You will store two workspaces, bind a name containing an apostrophe as data, and inspect committed rows after both success and rollback. A database error alone is not evidence that earlier writes were undone. We will reopen the database and check.

Start in `casebook-learning` with the virtual environment from chapter 02. You need collections, functions, context managers, exception handling and pytest from earlier chapters. Chapter 06's `may_read` rule required current active membership in the note's workspace and a known role. Here, SQL reads those facts from stored memberships. The earlier function's signature remains unchanged; these standalone listings do not import it or any earlier module.

By the end, you will be able to:

- Describe tables, keys and constraints, and read basic SQL statements.
- Bind external values while selecting SQL identifiers from a fixed allowlist.
- Join notes to current memberships and keep every read inside its workspace.
- Commit related writes together, inspect a rollback and apply a small schema migration.

The edition targets CPython 3.15.2. These examples use the explicit `autocommit` connection interface introduced in Python 3.12. The verification record identifies the actual Python and SQLite versions used. SQLite comes through Python's `sqlite3` module; this chapter installs no database server and needs no service credential.

## 1. Tables, rows, keys, constraints and basic SQL

A **relational database** stores related records in named tables. A **table** contains rows with named columns. A **row** represents one record. SQL, short for **Structured Query Language**, describes which records to select or change.

Our database uses integer keys internally while keeping the established workspace names `Alpha` and `Beta`.

**Table T15-01. The starting records**

| Table | Key | Starting data |
| --- | --- | --- |
| `workspaces` | `id` | `1` = Alpha; `2` = Beta |
| `users` | `id` | `1` = Mina; `2` = Ravi; `3` = Lee |
| `memberships` | `(workspace_id, user_id)` | Mina is an active Alpha member; Ravi is an active Beta member; Lee is an active Alpha manager |
| `notes` | `id` | `101` = Alpha's Release plan; `202` = Beta's Pricing review |
| `audit_events` | `id` | Initially empty |

A **primary key** identifies one row. A **composite key** uses several columns together. The membership key permits one membership per user and workspace. A **foreign key** requires a referenced row to exist. For example, a note's workspace must exist.

A **constraint** is a rule enforced by the database. `NOT NULL` requires a value. `UNIQUE` prevents duplicate keys. `CHECK` rejects values that fail an expression. These rules protect stored relationships even if one caller forgets a check. They do not establish who the caller is.

### Read a small SQL statement

```sql
SELECT id, title
FROM notes
WHERE workspace_id = ?
ORDER BY id;
```

`SELECT` names the returned columns. `FROM` names the table. `WHERE` keeps matching rows. `ORDER BY` defines their order; without it, do not depend on the row order. The `?` is a **placeholder**, filled with a bound value when Python executes the statement. The final semicolon ends the SQL statement.

The other statements used below are `CREATE TABLE` to define storage, `INSERT` to add rows and `UPDATE` to change selected rows. `DELETE FROM memberships WHERE ...` would remove selected memberships, although our revocation example instead sets their `active` field to `0`. A missing `WHERE` in an update or delete can affect every row.

Python's `connection.execute(sql, parameters)` runs one statement and returns a **cursor**, an object from which results can be fetched. `fetchone()` returns one row or `None`; `fetchall()` returns the remaining rows. `executemany()` repeats one parameterized statement with several parameter collections.

### Make transaction behavior explicit

A **connection** is Python's session with the database. A **transaction** groups database work under one commit or rollback decision. A **commit** accepts its changes. A **rollback** discards its uncommitted changes.

Our connection setup first enables foreign-key enforcement outside a transaction, then sets `autocommit=False`. In this mode Python keeps a transaction open. `with connection:` commits when the block finishes normally and rolls back if an exception escapes it. After either operation, Python opens another transaction. The block does not close the connection.

`contextlib.closing(...)` supplies that separate cleanup responsibility. Do not use nested `with connection:` blocks as if they were nested transactions. Each repository function below owns its transaction boundary and must not be called inside a caller's unfinished unit of work.

SQLite's foreign-key setting is per connection. Changing it inside an active transaction has no effect. Our setup enables it first and verifies that it took effect.

**Listing L15-01. The database schema and synthetic seed records**

Filename: `casebook_db.py`.

```python
from pathlib import Path
import sqlite3


SCHEMA = (
    """
    CREATE TABLE workspaces (
        id INTEGER PRIMARY KEY CHECK (id > 0),
        name TEXT NOT NULL UNIQUE
    )
    """,
    """
    CREATE TABLE users (
        id INTEGER PRIMARY KEY CHECK (id > 0),
        display_name TEXT NOT NULL CHECK (length(display_name) BETWEEN 1 AND 80)
    )
    """,
    """
    CREATE TABLE memberships (
        workspace_id INTEGER NOT NULL REFERENCES workspaces(id),
        user_id INTEGER NOT NULL REFERENCES users(id),
        role TEXT NOT NULL CHECK (role IN ('member', 'manager')),
        active INTEGER NOT NULL CHECK (active IN (0, 1)),
        PRIMARY KEY (workspace_id, user_id)
    )
    """,
    """
    CREATE TABLE notes (
        id INTEGER PRIMARY KEY CHECK (id > 0),
        workspace_id INTEGER NOT NULL REFERENCES workspaces(id),
        author_id INTEGER NOT NULL,
        title TEXT NOT NULL CHECK (
            length(title) BETWEEN 1 AND 200 AND length(trim(title)) > 0
        ),
        body TEXT NOT NULL CHECK (length(body) <= 4000),
        UNIQUE (workspace_id, id),
        FOREIGN KEY (workspace_id, author_id)
            REFERENCES memberships(workspace_id, user_id)
    )
    """,
    """
    CREATE TABLE audit_events (
        id INTEGER PRIMARY KEY,
        workspace_id INTEGER NOT NULL,
        note_id INTEGER NOT NULL,
        actor_id INTEGER NOT NULL,
        event TEXT NOT NULL CHECK (event = 'note.created'),
        request_id TEXT NOT NULL CHECK (length(request_id) BETWEEN 1 AND 64),
        UNIQUE (workspace_id, request_id),
        FOREIGN KEY (workspace_id, note_id)
            REFERENCES notes(workspace_id, id),
        FOREIGN KEY (workspace_id, actor_id)
            REFERENCES memberships(workspace_id, user_id)
    )
    """,
    "CREATE INDEX notes_workspace_title ON notes(workspace_id, title, id)",
)


def connect_database(path: Path) -> sqlite3.Connection:
    connection = sqlite3.connect(path, autocommit=True, timeout=2.0)
    try:
        connection.row_factory = sqlite3.Row
        connection.execute("PRAGMA foreign_keys = ON")
        enabled = connection.execute("PRAGMA foreign_keys").fetchone()[0]
        if enabled != 1:
            raise RuntimeError("foreign key enforcement is required")
        connection.autocommit = False
        return connection
    except BaseException:
        connection.close()
        raise


def create_schema(connection: sqlite3.Connection) -> None:
    with connection:
        for statement in SCHEMA:
            connection.execute(statement)
        connection.execute("PRAGMA user_version = 1")


def seed_database(connection: sqlite3.Connection) -> None:
    with connection:
        connection.executemany(
            "INSERT INTO workspaces(id, name) VALUES (?, ?)",
            [(1, "Alpha"), (2, "Beta")],
        )
        connection.executemany(
            "INSERT INTO users(id, display_name) VALUES (?, ?)",
            [(1, "Mina"), (2, "Ravi"), (3, "Lee")],
        )
        connection.executemany(
            """INSERT INTO memberships(workspace_id, user_id, role, active)
               VALUES (?, ?, ?, ?)""",
            [(1, 1, "member", 1), (2, 2, "member", 1), (1, 3, "manager", 1)],
        )
        connection.executemany(
            """INSERT INTO notes(id, workspace_id, author_id, title, body)
               VALUES (?, ?, ?, ?, ?)""",
            [
                (101, 1, 1, "Release plan", "Alpha private fixture"),
                (202, 2, 2, "Pricing review", "Beta private fixture"),
            ],
        )
```

`sqlite3.Row` lets a result be read by column name as well as by position. `dict(row)` later produces a plain dictionary. SQL uses `0` and `1` for the inactive and active flags in this schema.

`PRAGMA` is SQLite's command for settings and database metadata. We use `user_version` as a small schema version marker. `timeout=2.0` here configures waiting for database locks. It is not a deadline for an entire transaction or arbitrary SQL query.

The setup catches `BaseException` only to close a partially configured connection, then immediately re-raises. It does not turn programming errors or cancellation into success.

The two seeded notes represent an existing inventory; their historical audit activity is outside this fixture. The note-plus-audit guarantee below applies to new writes through `create_note`. The foreign keys do not require every note to have an audit row: direct SQL could bypass that application rule.

The composite foreign keys keep an audit event's workspace consistent with its note and actor. A foreign key can prove that a membership row exists. It cannot prove that the membership is currently active. Our application queries must check `active = 1`.

`create_schema` and `seed_database` expect a new empty database. They deliberately fail on repeated initialization. The walkthrough uses a new temporary database each run, so there is no instruction to delete an existing database.

## 2. Parameter binding, identifiers and allowlisted query options

A **bound parameter** carries a value separately from SQL instructions. A name containing an apostrophe is ordinary data. The driver handles its representation.

Do not assemble a quoted SQL value with string concatenation, an f-string or manual replacement of apostrophes. That can change how SQL is parsed. Parameter binding also handles Unicode without treating punctuation as SQL syntax.

### Worked example 1: store O’Connor and O'Connor

The curly apostrophe in `O’Connor` and the straight apostrophe in `O'Connor` are different Unicode characters. We will store both, one after the other, as Lee's display name. His user ID remains `3`; display text does not become his identity.

**Listing L15-02. Names supplied as bound values**

Filename: `bound_names.py`.

```python
from contextlib import closing
from pathlib import Path
from tempfile import TemporaryDirectory

from casebook_db import connect_database, create_schema, seed_database


def main() -> None:
    with TemporaryDirectory(prefix="casebook-names-") as directory:
        path = Path(directory) / "names.sqlite3"
        with closing(connect_database(path)) as connection:
            create_schema(connection)
            seed_database(connection)
            for name in ("O'Connor", "O’Connor"):
                with connection:
                    connection.execute(
                        "UPDATE users SET display_name = ? WHERE id = ?",
                        (name, 3),
                    )
                # A fresh connection checks the committed value.
                with closing(connect_database(path)) as observer:
                    row = observer.execute(
                        "SELECT id, display_name FROM users WHERE id = ?", (3,)
                    ).fetchone()
                    print(f"{row['id']} | {row['display_name']}")


if __name__ == "__main__":
    main()
```

### Values and identifiers have different jobs

A table name, column name or sort direction is an SQL **identifier** or instruction. A placeholder represents a value, not arbitrary SQL structure. `ORDER BY ?` with the value `"title"` does not select the title column for ordering.

An **allowlist** maps a small set of public choices to fixed SQL fragments. Our list operation accepts `sort="id"` or `sort="title"`. It selects the fragment from code. The workspace, user and limit remain bound values. The f-string in that one query inserts only the selected trusted fragment.

## 3. Joins, workspace filters and indexes

A **join** matches related rows from tables. Here, a note joins a membership when their workspace IDs agree and the membership belongs to the current user. The query then requires an active membership with a known role.

A caller may request workspace `1`, but that request does not establish membership. The service must obtain `user_id` from its trusted authentication boundary. In these standalone exercises, the test supplies fixture IDs. A future web caller must not accept its identity from a request field.

The list query and the detail query both apply the membership join. A secure list alone does not secure a direct read by note ID.

**Listing L03. Queries with bound values and a workspace filter**

Filename: `note_repository.py`.

```python
import sqlite3


SORT_SQL = {
    "id": "n.id ASC",
    "title": "n.title COLLATE BINARY ASC, n.id ASC",
}


class AccessDenied(PermissionError):
    pass


def list_notes(
    connection: sqlite3.Connection, *, user_id: int | None,
    workspace_id: int, sort: str = "id", limit: int = 20,
) -> list[dict]:
    if sort not in SORT_SQL:
        raise ValueError("unknown note sort")
    if type(limit) is not int or not 1 <= limit <= 100:
        raise ValueError("limit must be an integer from 1 to 100")
    order = SORT_SQL[sort]
    with connection:
        rows = connection.execute(
            f"""
            SELECT n.id, n.workspace_id, n.title
            FROM notes AS n
            JOIN memberships AS m
              ON m.workspace_id = n.workspace_id
             AND m.user_id = ?
             AND m.active = 1
             AND m.role IN ('member', 'manager')
            WHERE n.workspace_id = ?
            ORDER BY {order}
            LIMIT ?
            """,
            (user_id, workspace_id, limit),
        ).fetchall()
    return [dict(row) for row in rows]


def get_note(
    connection: sqlite3.Connection, *, user_id: int | None,
    workspace_id: int, note_id: int,
) -> dict | None:
    with connection:
        row = connection.execute(
            """
            SELECT n.id, n.workspace_id, n.title, n.body
            FROM notes AS n
            JOIN memberships AS m
              ON m.workspace_id = n.workspace_id
             AND m.user_id = ?
             AND m.active = 1
             AND m.role IN ('member', 'manager')
            WHERE n.workspace_id = ? AND n.id = ?
            """,
            (user_id, workspace_id, note_id),
        ).fetchone()
    return None if row is None else dict(row)


def create_note(
    connection: sqlite3.Connection, *, user_id: int, workspace_id: int,
    note_id: int, title: str, body: str, request_id: str,
) -> None:
    for value in (user_id, workspace_id, note_id):
        if type(value) is not int or value < 1:
            raise ValueError("identifiers must be positive integers")
    if not isinstance(title, str) or not title.strip() or len(title) > 200:
        raise ValueError("title must contain 1 to 200 characters")
    if not isinstance(body, str) or len(body) > 4000:
        raise ValueError("body must be text of at most 4000 characters")
    if not isinstance(request_id, str) or not 1 <= len(request_id) <= 64:
        raise ValueError("request_id must contain 1 to 64 characters")

    with connection:
        cursor = connection.execute(
            """
            INSERT INTO notes(id, workspace_id, author_id, title, body)
            SELECT ?, ?, ?, ?, ?
            WHERE EXISTS (
                SELECT 1 FROM memberships
                WHERE workspace_id = ? AND user_id = ? AND active = 1
                  AND role IN ('member', 'manager')
            )
            """,
            (note_id, workspace_id, user_id, title, body, workspace_id, user_id),
        )
        if cursor.rowcount != 1:
            raise AccessDenied("active workspace membership required")
        connection.execute(
            """
            INSERT INTO audit_events(workspace_id, note_id, actor_id, event, request_id)
            VALUES (?, ?, ?, 'note.created', ?)
            """,
            (workspace_id, note_id, user_id, request_id),
        )
```

`AS n` and `AS m` introduce short table aliases. `n.workspace_id` means the workspace column from the note. `EXISTS` asks whether a matching row exists. The create operation inserts a note only when the stored membership permits it. A member or manager may create in their own workspace under this chapter's local write policy.

`rowcount` tells us how many rows that insert affected. Zero means the membership condition failed, so the function raises `AccessDenied`. Neither write commits until the whole block exits normally.

### Trace a read across the workspace boundary

**Table T15-02. Expected fixture reads**

| Current user | Requested workspace | Requested note | Detail result |
| --- | --- | --- | --- |
| Mina (`1`) | Alpha (`1`) | `101` | Alpha note |
| Mina (`1`) | Beta (`2`) | `202` | `None` |
| Ravi (`2`) | Beta (`2`) | `202` | Beta note |
| Ravi (`2`) | Alpha (`1`) | `101` | `None` |
| Lee (`3`) | Alpha (`1`) | `101` | Alpha note |
| Lee (`3`) | Beta (`2`) | `202` | `None` |
| Visitor (`None`) | Alpha (`1`) | `101` | `None` |
| Revoked Mina (`1`) | Alpha (`1`) | `101` | `None` |

Lee's manager role does not bypass the workspace join. A visitor has no matching user ID. An inactive membership fails the `active` condition. The API returns `None` for both an inaccessible note and an absent note; later web chapters choose the corresponding response contract.

The read functions fetch their results before leaving their transaction block. A subsequent call starts from a new transaction snapshot, rather than retaining an earlier membership result. The tests also revoke Mina through another connection before the next read.

### Index the access path without changing its meaning

An **index** is an additional data structure that helps the database find or order rows. The membership primary key supports lookup by workspace and user. The notes index begins with `workspace_id`, then `title` and `id`, matching the filtered title-order query.

Indexes improve access paths; they do not enforce authorization. Removing an index may make a query slower. Removing the membership predicate changes which private records may be returned.

`EXPLAIN QUERY PLAN` lets an operator inspect a query's chosen access path. Plans vary with SQLite version, statistics and data size. Do not assert exact plan text in these privacy tests. Verify the returned rows first, then measure representative workloads when choosing indexes. Each index also consumes storage and adds write work.

## 4. Transactions, rollback, migrations and the limits of SQLite demonstrations

Our write rule is concrete: creating a note must also store one `note.created` audit event in the same database transaction. That event records identifiers and an operation name, without duplicating the private note body.

**Atomicity** means the related changes are accepted together or discarded together. It does not follow merely from executing the statements next to each other. Both statements must share a transaction, and the failure must reach the rollback boundary.

The `UNIQUE(workspace_id, request_id)` constraint prevents two audit events using the same request identifier in one workspace. We deliberately reuse an already committed identifier to make the second audit insert fail. This is a local failure fixture. It is not an idempotent retry interface; chapter 20 develops that separate contract.

### Worked example 2: inspect success and rollback from a new connection

Predict the stored state in three stages: after seeding, after creating note `102`, and after trying to create note `103` with the already used audit request ID. Will note `103` survive because its insert ran before the failing audit insert?

**Listing L15-03. Inspect committed rows after each transaction**

Filename: `sqlite_walkthrough.py`.

```python
from contextlib import closing
from pathlib import Path
import sqlite3
from tempfile import TemporaryDirectory

from casebook_db import connect_database, create_schema, seed_database
from note_repository import create_note, get_note, list_notes


def show_stored(path: Path, label: str) -> None:
    # An operator-only inspection of synthetic data, not a reader endpoint.
    with closing(connect_database(path)) as observer:
        notes = [tuple(row) for row in observer.execute(
            "SELECT id, workspace_id, title FROM notes ORDER BY id"
        )]
        events = [tuple(row) for row in observer.execute(
            """SELECT workspace_id, note_id, actor_id, event, request_id
               FROM audit_events ORDER BY id"""
        )]
    print(label)
    print("notes:", notes)
    print("audit:", events)


def main() -> None:
    with TemporaryDirectory(prefix="casebook-sqlite-") as directory:
        path = Path(directory) / "casebook.sqlite3"
        with closing(connect_database(path)) as connection:
            create_schema(connection)
            seed_database(connection)
            show_stored(path, "after seed")

            print("Mina Alpha IDs:", [row["id"] for row in list_notes(
                connection, user_id=1, workspace_id=1
            )])
            print("Ravi Alpha detail:", get_note(
                connection, user_id=2, workspace_id=1, note_id=101
            ))
            print("Ravi Beta IDs:", [row["id"] for row in list_notes(
                connection, user_id=2, workspace_id=2
            )])

            create_note(
                connection, user_id=1, workspace_id=1, note_id=102,
                title="برنامه انتشار", body="Synthetic Alpha draft",
                request_id="request-001",
            )
            show_stored(path, "after success")

            try:
                create_note(
                    connection, user_id=1, workspace_id=1, note_id=103,
                    title="Must roll back", body="Synthetic rejected draft",
                    request_id="request-001",
                )
            except sqlite3.IntegrityError as error:
                print("audit failure:", error.sqlite_errorname)
            else:
                raise AssertionError("the duplicate audit request should fail")
            show_stored(path, "after rollback")


if __name__ == "__main__":
    main()
```

```

notes: [(101, 1, 'Release plan'), (202, 2, 'Pricing review')]
audit: []
Mina Alpha IDs: [101]
Ravi Alpha detail: None
Ravi Beta IDs: [202]
after success
notes: [(101, 1, 'Release plan'), (102, 1, 'برنامه انتشار'), (202, 2, 'Pricing review')]
audit: [(1, 102, 1, 'note.created', 'request-001')]
audit failure: SQLITE_CONSTRAINT_UNIQUE
after rollback
notes: [(101, 1, 'Release plan'), (102, 1, 'برنامه انتشار'), (202, 2, 'Pricing review')]

```

The successful transaction leaves both note `102` and its audit event. In the failed transaction, the note `103` insert succeeds first. The audit insert then violates its unique constraint. `IntegrityError` escapes the connection block, so the block rolls back the note insert too. The walkthrough catches the exception only after that rollback.

The final stored rows exactly match the state after success. Note `103` is absent, and the original event remains. These observations come from fresh connections, so they do not merely show uncommitted state visible to the writer.

Catching the audit error *inside* the `with connection:` block and continuing normally would allow the note insert to commit. `INSERT OR IGNORE` would also hide this required audit failure. Both would break the rule.

The inspection function deliberately selects all stored fixture rows. It is an operator demonstration, not an application read interface. Reader-facing code must use the scoped repository queries.

### Move the schema forward with a migration

A **migration** is a named, ordered change to a stored schema or its data. Editing `CREATE TABLE` in a source file does not change tables already on disk. This small migration moves version `1` to version `2` by adding a flag whose default preserves existing notes as unarchived.

**Listing L15-04. A versioned SQLite migration**

Filename: `casebook_migrations.py`.

```python
import sqlite3


def migrate_to_v2(connection: sqlite3.Connection) -> None:
    with connection:
        version = connection.execute("PRAGMA user_version").fetchone()[0]
        if version == 2:
            return
        if version != 1:
            raise ValueError("expected schema version 1 or 2")
        connection.execute(
            """ALTER TABLE notes ADD COLUMN archived INTEGER NOT NULL DEFAULT 0
               CHECK (archived IN (0, 1))"""
        )
        connection.execute("PRAGMA user_version = 2")
```

The column change and version marker commit together. A failure escaping the block rolls back both. Repeating this migration at version `2` makes no further change. Version `0`, representing an uninitialized database in this exercise, is rejected.

This migration changes storage only. The repository does not yet hide archived notes. That behavior would need a written policy, changed read queries and tests. A new column does not implement a product rule by itself.

Apply migrations through one controlled owner. For an actual deployment, prepare a backup and recovery procedure, test the change on representative data and check compatibility with code still running during rollout. Our function is a single-process teaching artifact, not a migration coordinator.

### Know what this demonstration establishes

SQLite stores this database locally and has no separate server identity boundary. Anyone with sufficient access to its files or process can bypass these repository functions. Protect the database, journal files and backups with operating-system access controls. Neither parameter binding nor workspace filtering encrypts stored note bodies.

SQLite permits several readers but only one writer at a time. Lock contention, transaction snapshots and error handling require further tests when work becomes concurrent. An authorization read observes the transaction's database state; this sequential demonstration does not establish ordering guarantees for a revocation racing a note release. Chapters 23 and 28 return to authorization paths and concurrent work.

Ordinary SQLite tables also use flexible typing. This schema's checks protect named relationships and value bounds; they do not replace input validation or establish identical behavior in another database. PostgreSQL or a later ORM needs its own constraint, query and concurrency tests. An audit row in this local database also does not demonstrate the durability or availability of an external audit service.

def stored_rows(path):

def add_alpha(connection, *, note_id=102, request_id="request-001"):

@pytest.mark.parametrize(

def test_names_are_data(database_path, name):
