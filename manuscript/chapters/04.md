## 1. Combine the facts behind a decision

Casebook's read rule requires an active membership in the note's workspace at the time of the read. In this chapter's small model, a signed-in person with role `member` or `manager` may read a note in their own active workspace. Other role values receive a denial.

A **condition** is an expression interpreted as true or false. The operators `and`, `or` and `not` let you combine conditions.

| Expression | Result for boolean operands | Example question |
| --- | --- | --- |
| `a and b` | True when both are true | Is the reader signed in and an active member? |
| `a or b` | True when at least one is true | Is this a member role or a manager role? |
| `not a` | The opposite truth value | Is the reader missing an active membership? |

For example, `role == "member" or role == "manager"` contains two complete comparisons. Write the name being compared in both. The expression `role == "member" or "manager"` supplies a nonempty string as its second operand. That string tests as true, so it cannot enforce the intended role rule.

### Build Mina's result one fact at a time

These values are fictional facts supplied for the exercise. In a working service, the application loads identity and membership from trusted records. A person's claim that their role is `manager` needs verification before it can become an authorization input.

**Listing L04-01. The conditions for Mina's request**

Filename: `access_conditions.py`.

```python
reader_name = "Mina"
signed_in = True
membership_active = True
reader_workspace = "Alpha"
note_workspace = "Alpha"
role = "member"

same_workspace = reader_workspace == note_workspace
known_role = role == "member" or role == "manager"
can_read = signed_in and membership_active and same_workspace and known_role

print(f"Same workspace {same_workspace}")
print(f"Known role {known_role}")
print(f"May read {can_read}")
```

Predict the three booleans before running the file. Then compare your prediction with the expected output.

```text
Same workspace True
Known role True
May read True
```

Trace the meaning of `can_read` in words. Mina is signed in. Her membership is active. Her workspace matches the note's workspace. Her role is recognized. All four conditions hold.

Change only `reader_workspace` to `"Beta"`. The workspace comparison becomes false, so `can_read` becomes false. A manager role must also pass the workspace condition. Lee's role gives authority inside Alpha.

### Short-circuit evaluation

Python evaluates boolean operations from left to right. For `and`, a false operand determines the result, so Python skips the remaining operands. For `or`, a true operand determines the result, so Python skips the remaining operands. This behavior is called **short-circuit evaluation**.

**Listing L04-02. Skipping a comparison when the count is missing**

Filename: `known_count.py`.

```python
current_count = None
note_limit = 3
count_known = current_count is not None
quota_permits = count_known and current_count < note_limit

print(count_known)
print(quota_permits)
```

The phrase `is not None` asks whether the value is different from the `None` object. The expected output is the following.

```text
False
False
```

`count_known` is false. Python therefore skips `current_count < note_limit`, avoiding the unsuitable comparison between `None` and an integer. Under this example's policy, an unknown count cannot permit creation.

The guard establishes only that the count is present. It still assumes any present count is a valid nonnegative integer. Text such as `"0"` requires further input handling, as chapter 03 explained.

### Group the rule so its meaning stays visible

`not` has higher precedence than `and`, and `and` has higher precedence than `or`. Use parentheses to make a combined rule easy to review. For example, `same_workspace and (role == "member" or role == "manager")` requires a workspace match for both roles.

Without those parentheses, `same_workspace and role == "member" or role == "manager"` would allow the manager comparison to decide the result even when the workspace comparison is false.

`and` and `or` can return operand values other than booleans. For instance, `"" or "unknown"` returns the string `"unknown"`. The access conditions above use boolean operands so the combined result is a boolean. [Python's boolean operations](https://docs.python.org/3.15/reference/expressions.html#boolean-operations)

## 2. Select a branch with an explicit default

An **if statement** selects instructions according to a condition. A **branch** is one possible path through the decision.

Start with a small sign-in observation before implementing the full read rule.

**Listing L04-03. Choosing which message to display**

Filename: `sign_in_message.py`.

```python
signed_in = True

if signed_in:
    print("Signed in")
else:
    print("Visitor")

print("Sign-in check complete")
```

The colon after each header starts a block. The four spaces before each indented `print` identify the instructions inside that block. Keep the `else` aligned with the `if` it belongs to. The final `print` is outside both blocks and runs after the decision.

The expected output is the following.

```text
Signed in
Sign-in check complete
```

Changing `signed_in` to `False` selects the `else` block. The first line becomes `Visitor`, and the final line still runs. Use a code editor configured for four spaces per indentation level.

### Worked example 1. Decide whether Mina may read the note

Use `elif`, meaning “else if,” to check another condition when the preceding condition was false. Python checks an `if`/`elif` chain in order. It executes the first matching branch and skips the remaining branches. If every condition is false, `else` supplies the fallback.

**Listing L04-04. A read decision with reasons**

Filename: `access_decision.py`.

```python
reader_name = "Mina"
signed_in = True
membership_active = True
reader_workspace = "Alpha"
note_workspace = "Alpha"
role = "member"

if not signed_in:
    decision = "Deny"
    reason = "sign-in required"
elif not membership_active:
    decision = "Deny"
    reason = "active membership required"
elif reader_workspace != note_workspace:
    decision = "Deny"
    reason = "workspace mismatch"
elif role == "member":
    decision = "Allow"
    reason = "active workspace member"
elif role == "manager":
    decision = "Allow"
    reason = "active workspace manager"
else:
    decision = "Deny"
    reason = "unrecognized role"

print(f"{reader_name} {decision}")
print(reason)
```

The expected output is the following.

```text
Mina Allow
active workspace member
```

Trace the conditions in their execution order.

| Condition reached for Mina | Value | What executes next |
| --- | --- | --- |
| `not signed_in` | `False` | Check membership. |
| `not membership_active` | `False` | Compare workspaces. |
| `reader_workspace != note_workspace` | `False` | Check the member role. |
| `role == "member"` | `True` | Assign `Allow` and the member reason. |
| Manager condition and final `else` | Skipped | Continue at the first unindented `print`. |

Every branch assigns both `decision` and `reason`. The final `else` explicitly denies unrecognized roles. This is **deny by default**. The program grants access only after its recognized allow conditions are satisfied. Later service chapters will apply that rule before releasing any private content. [OWASP authorization guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

### Trace a visitor, a member and an unknown role

For the following table, the note belongs to Alpha. The unknown-role example is deliberately signed in with an active Alpha membership, so the role fallback gets exercised.

**Table T01. Values before and after each access decision**

| Scenario | Signed in | Active membership | Reader workspace | Role | First selected branch | Decision |
| --- | --- | --- | --- | --- | --- | --- |
| Visitor | `False` | `False` | `None` | `"visitor"` | `if not signed_in` | Deny |
| Mina | `True` | `True` | `"Alpha"` | `"member"` | `elif role == "member"` | Allow |
| Unknown role | `True` | `True` | `"Alpha"` | `"unknown"` | Final `else` | Deny |

For the visitor, the first condition is true, so the remaining checks are skipped. For Mina, the three refusal conditions are false and the member condition is true. For the unknown role, all five conditions are false and the fallback executes.

Now consider Ravi, who has active Beta membership. Set his name, workspace and member role in Listing L04-04. The workspace mismatch branch denies the request before either role branch can allow it.

To model Mina leaving Alpha, keep her name, workspace and role but set `membership_active = False`. The active-membership refusal branch should produce `Deny`. A role label from earlier in the account's life cannot substitute for current membership.

## 3. Repeat a bounded amount of work

A **loop** repeats a block of instructions. A `for` loop visits items supplied by an iterable. An **iterable** is a value that can provide items one at a time. A `while` loop repeats while its condition remains true.

### Count repetitions with `for` and `range`

`range(3)` supplies the integers `0`, `1` and `2`. Its stop value is excluded. In `for attempt in range(3)`, Python assigns each supplied integer to `attempt` and executes the indented block once for that value.

**Listing L04-05. Three local inspection attempts**

Filename: `attempt_numbers.py`.

```python
for attempt in range(3):
    print(f"Inspection {attempt + 1}")

print("Finished")
```

The expected output is the following.

```text
Inspection 1
Inspection 2
Inspection 3
Finished
```

The program adds one only for its displayed label. The loop values remain `0`, `1` and `2`. With `range(1, 4)`, the start is explicitly `1` and the supplied values are `1`, `2` and `3`. You can also specify a step. `range(0, 6, 2)` supplies `0`, `2` and `4`.

With `range(0)`, there are no values. The loop body executes zero times and `Finished` is still printed. An empty sequence can therefore skip an entire block. Names first assigned only inside that block may remain undefined.

### Change state with `while`

A `while` loop tests its condition before every iteration. An **iteration** is one execution of the loop body. Some operation must make progress toward a false condition or an explicit exit if the work is intended to finish.

**Listing L04-06. Filling the last quota place**

Filename: `fill_quota.py`.

```python
note_limit = 3
current_count = 2

while current_count < note_limit:
    current_count = current_count + 1
    print(f"Created note {current_count}")

print(f"Final count {current_count}")
```

The expected output is the following.

```text
Created note 3
Final count 3
```

This loop simulates successful note creation by changing a number. The starting count is known and valid. Real storage and concurrent updates arrive in later chapters.

The increment is the progress step. If you remove it, the count stays at two and the condition stays true, creating an **infinite loop**. If you accidentally run such a loop in a terminal, press Ctrl+C to interrupt it. Then inspect the update before running it again.

### Stop with `break` and skip with `continue`

`break` exits the nearest enclosing loop immediately. `continue` skips the rest of the current iteration and begins the next iteration. In a `while` loop, that means checking the condition again.

The next listing uses two optional arguments of `range` to start at one and stop before five.

**Listing L04-07. Distinguishing a skipped item from a stopped loop**

Filename: `skip_and_stop.py`.

```python
for item_number in range(1, 5):
    if item_number == 2:
        continue
    if item_number == 4:
        break
    print(f"Checked item {item_number}")

print("Inspection ended")
```

The expected output is the following.

```text
Checked item 1
Checked item 3
Inspection ended
```

Item two reaches `continue`, so it skips the final `print` in the loop body. Item four reaches `break`, so the loop ends before printing it. The final unindented `print` runs after the loop.

These control statements affect which work actually completes. When reviewing a loop that checks permissions, identify whether an exit skips required checks or whether a skipped item is still used later. Keep a check and the action it protects in an execution order you can trace. [Python's control-flow tutorial](https://docs.python.org/3.15/tutorial/controlflow.html)

## 4. Trace boundaries and repeated decisions

A trace records the relevant values before and after a step. It helps you distinguish a comparison mistake from an update in the wrong place.

### Worked example 2. The last admitted note

Suppose Alpha already has two notes and receives two more creation requests. The first should use the final place. The second should be refused by the quota. Assume the reader's permission and count validity have already been checked.

**Listing L04-08. Two requests near a three-note limit**

Filename: `quota_requests.py`.

```python
note_limit = 3
current_count = 2

for request_number in range(1, 3):
    if current_count < note_limit:
        current_count = current_count + 1
        decision = "Allow"
    else:
        decision = "Deny"

    print(f"Request {request_number} {decision} count {current_count}")
```

Predict both output lines before running the file. The expected output is the following.

```text
Request 1 Allow count 3
Request 2 Deny count 3
```

**Table T04-01. Count before and after each request**

| Request | Count before comparison | `current_count < 3` | Selected action | Count afterward |
| --- | --- | --- | --- | --- |
| 1 | `2` | `True` | Increment the count and assign `Allow`. | `3` |
| 2 | `3` | `False` | Assign `Deny` and leave the count at three. | `3` |

The program checks the current count before incrementing it. Each iteration assigns a decision, so a refusal cannot accidentally reuse the preceding `Allow` value.

An **off-by-one error** admits or processes one item too many or too few because a boundary is wrong. Replacing `<` with `<=` in this example allows the second request at count three and produces count four. The trace tells you exactly which comparison changes the outcome.

### Check an empty batch

Change only `range(1, 3)` to `range(1, 1)` in Listing L04-08. The start already equals the excluded stop, so there are no iterations. The script prints nothing and leaves the count at two.

The name `decision` is assigned inside the loop. With that empty batch, the name is never assigned. Adding `print(decision)` after the loop in this script would raise `NameError`. If you need a batch summary, design a summary value that has a defined meaning even for zero requests.

### Run the three access scenarios in one file

You can iterate over named scenarios too. The parentheses in the next listing group three strings into a **tuple**, an ordered sequence. For now, read `for scenario in (...)` as “assign each listed scenario to the name, in order.” Chapter 05 explains tuples and other collections in detail.

**Listing L04-09. Repeating the read decision for three fixtures**

Filename: `access_scenarios.py`.

```python
note_workspace = "Alpha"

for scenario in ("visitor", "member", "unknown"):
    role = scenario
    reader_workspace = "Alpha"
    signed_in = scenario != "visitor"
    membership_active = signed_in

    if not signed_in:
        decision = "Deny"
    elif not membership_active:
        decision = "Deny"
    elif reader_workspace != note_workspace:
        decision = "Deny"
    elif role == "member":
        decision = "Allow"
    elif role == "manager":
        decision = "Allow"
    else:
        decision = "Deny"

    print(f"{scenario} {decision}")
```

A **fixture** is known data chosen for an exercise or test. The assignments before the `if` chain manufacture these three fictional cases. They supply active membership for the member and unknown-role cases so those role checks can be reached. The visitor's workspace placeholder is unused because the sign-in refusal happens first. In a service, trusted identity and membership records supply those facts independently of a role label.

Write your expected three-line output before looking below.

```text
visitor Deny
member Allow
unknown Deny
```

Compare the selected branch in each iteration with Table T01. The visitor is refused at the first branch. The member reaches the member branch. The unknown role reaches the fallback. Every iteration makes a fresh decision.

## Worked answers

### Exercise 1

`current_count is not None` evaluates to `False`. Python skips `current_count < 3` and the expression returns `False`. The guard prevents that particular comparison with a missing count. It does not check every possible invalid input type.

### Exercise 2

The original expression produces `True`. The workspace/member combination is false, but the manager comparison is true. The grouping `same_workspace and (role == "member" or role == "manager")` produces `False` for this fixture and requires the workspace match for both roles. ## Glossary

| Term | Meaning in this chapter |
| --- | --- |
| Branch | One path through a conditional statement |
| Condition | An expression interpreted as true or false |
| Deny by default | Grant access only when recognized allow conditions are satisfied |
| Fixture | Known data selected for an exercise or test |
| Infinite loop | A loop whose execution never reaches an exit on its own |
| Iterable | A value that supplies items for iteration |
| Iteration | One execution of a loop body |
| Loop | A statement that repeats a block of work |
| Off-by-one error | A boundary mistake that includes or excludes one extra item |
| Short-circuit evaluation | Skipping an operand once the boolean operation's result is determined |
| Trace table | A record of values and selected actions as instructions execute |
| Tuple | An ordered sequence of values, introduced fully in chapter 05 |
